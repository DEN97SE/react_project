1С:ШИНА. СХЕМА КАБИНЕТА ПОСТАВЩИКА, AMQP 1.0

1. В тестовом проекте создать схему Integration_KP_AMQP.
2. Добавить/переиспользовать системы Astor, DocumentManager, BackendKP.
3. Первый проход: FromAstor → ToDO_Reference. Каналы 1С связываются с Astor и ДО.
4. Второй: FromDO → ToBackend. FromDO связан с ДО; ToBackend — отправитель AMQP 1.0.
5. Обратно: FromBackend → ToDO_Backend. FromBackend — получатель AMQP 1.0;
   ToDO_Backend связан с ДО.
6. Справочники на бэкенд публикует ДО после своего приёма/применения. Нельзя
   разветвить исходное сообщение Astor сразу в ДО и бэкенд при требуемом порядке.

Рисунок показывает имена экземпляров, не гарантирует названия компонентов палитры.
В установленной Шине проверить поддержку именно AMQP 1.0. Не переносить настройки
exchange/routing key из AMQP 0-9-1 как универсальную модель AMQP 1.0.

Настройки AMQP, которые должен определить владелец стенда:
  продукт и версия брокера;
  узел/порт, TLS, проверка сертификата и доверенный центр;
  способ аутентификации, права публикации/потребления;
  исходящий target для данных кабинета;
  входящий source для результатов/событий бэкенда;
  хранение сообщений, лимит размера, потребительский credit, повторная доставка;
  delivery outcome/settlement, политика ошибок/истечения и отдельный разбор ошибок.

Входное тело FromAstor — готовый JSON UTF-8, не JSON-строка внутри JSON.
В заголовках отправителя из Астора:
  ТипСообщения = astor.reference.snapshot;
  ИдентификаторПакета = message_id JSON;
  РевизияПакета = revision;
  ContentType = application/json; charset=utf-8.
Нельзя подменять прикладной message_id новым транспортным ID на каждом повторе.

Контракт снимка:
  schema_version: 1
  message_id: UUID-строка
  message_type: astor.reference.snapshot / supplier.reference.snapshot
  source_system: astor-master / do-master
  dataset: supplier-reference
  scope: configured-formats
  revision: положительное целое
  mode: snapshot
  generated_at: ISO 8601 UTC
  content_hash: SHA-256 нормализованного payload
  payload: categories, formats, territories, structural_units;
           category_format_assignments нужен внутреннему пакету Астор → ДО.

Канонизация текущего прототипа: ключи объектов сортируются функцией JSON
из КХ_КП_СлужебныйОбмен, порядок массивов сохраняется, хеш UTF-8 без BOM.
Это не объявляется реализацией RFC 8785. Межъязыковую совместимость хеша согласовать
по одинаковым тестовым примерам до независимого расчёта бэкендом.

Результат бэкенда — отдельное сообщение supplier.reference.result:
  свой message_id;
  correlation_id: message_id исходного сообщения ДО;
  revision, status (applied/rejected), error при отказе.
Приём брокером и settlement доставки не заменяют applied.

На стороне ДО необходимы:
  дедупликация входящих message_id и проверка конфликта повторного ID;
  ревизия в пределах source_system + dataset + scope;
  отказ от замены свежего снимка устаревшим;
  устойчивая фиксация приёма до подтверждения;
  применение необходимых проекций и постановка публикации в локальной транзакции;
  сопоставление UUID сотрудников Астора с исполнителями ДО по явной таблице;
  сохранение исполнителя и основания распределения в действующих КП.

Обмен КП — следующий поток, отдельный от справочников:
  supplier.offer.submitted / supplier.offer.withdrawn / supplier.offer.updated.
  Исходное КП, производное КП и строка имеют разные устойчивые ID.
  Статус КП, состояние КП и состояние строки не объединяются в одно поле.

При тестировании транспорта воспроизвести:
  повтор сообщения, потерю подтверждения, отключение брокера, превышение размера,
  отказ доступа, невалидный JSON, старую ревизию, перезапуск потребителя.
  Невалидное сообщение не должно бесконечно немедленно возвращаться в ту же очередь.

Ограничение: без экспорта проекта, физического AMQP-стенда и входящего обработчика
ДО этот документ является точным заданием на настройку и проверку, но не готовым
проверенным импортом Шины и не кодом прикладного процесса ДО.

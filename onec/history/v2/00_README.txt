3. МИНИМАЛЬНОЕ ПОДКЛЮЧЕНИЕ К ДЕЙСТВУЮЩЕМУ ОТПРАВИТЕЛЮ

16_ASTOR_NativeSenderPatch.txt:
  один блок в начало цикла ОтправитьСообщенияВШину, до обработки Объект/сериализации.

17_ASTOR_ManualSender.txt:
  одна новая экспортная процедура в том же Интеграция1СШина для ручного теста.
  Она обрабатывает только ВнешняяСистема = KP_SUPPLIER.

Интеграция1СШинаПереопределяемый не менять.
ПереводВJSONДляШины не менять: для KP_SUPPLIER уже готовый JSON идёт мимо него.
Другие обмены сохраняют прежний путь отправки. Их кодировку этот комплект не меняет.

Почему отдельная ветка нужна:
  общий переопределяемый отправитель жёстко выбирает СервисИнтеграцииВЭДО;
  общая функция записывает текст в ANSI и добавляет перевод строки;
  неизвестный внешний сериализатор мог бы повторно преобразовать наш JSON.
Новый отправитель использует известный СервисыИнтеграции API, но пишет точные
UTF-8-байты. Он закрывает оба потока и удаляет свой временный файл.

Обязательные условия:
  KP_SUPPLIER НЕ включать в КХ_ОбменШиныОпера.СистемыСобственнойОчереди().
  Наш канал НЕ должен быть внутренним EDO-каналом, исключаемым общим запросом.
  Фоновый отправитель и ручной тест не должны одновременно обрабатывать одну очередь.

Управляемой форме назначить ПриСозданииНаСервере из файла 14;

Настройки заполняются фактическими именами из метаданных/Шины:
  СервисИнтеграции — сервис Астора для этого маршрута, а не имя AMQP-брокера.
  КаналИсходящий — точное имя канала этого сервиса, используемое индексатором API.
  УзелПолучатель — код узла ДО в Шине, а не свободное описание организации.
  КодОтправителя — код узла Астора, согласованный с проектом Шины.
Из вашего стандартного переопределяемого метода известна формула astor + КодСЕ;
использовать её, если именно этот код зарегистрирован на тестовом маршруте.

Имена FromAstor и ToDO_Reference на рисунке — имена экземпляров компонентов.
Они могут отличаться от сгенерированных имён каналов сервиса в конфигурации.
Коды и имена маршрута нельзя выдумать из картинки.

Перед сменой маршрута разобрать ожидающие сообщения. Канал/получатель в очереди
заморожены; отправитель откажет при несовпадении с текущими настройками.
Сервис и код отправителя берутся из текущих настроек: менять их при непустой
очереди следует как отдельное переключение, а не обычное редактирование поля.

5. ПОСЛЕДОВАТЕЛЬНОСТЬ ПРОВЕРКИ

A. Синтаксический контроль всех новых модулей/форм и точечной вставки.
   Проверить отсутствие функции Состояние() и ссылок на старые имена КП_* модулей.

B. ПроверитьФормат: 8 проверок SHA256 по известным векторам, стабильности ключей,
   сохранения null/boolean, целого пакета, повреждённого хеша и нулевой ревизии.
   Это проверки, которые должны исполниться в вашей 1С; их результат здесь не получен.

C. СформироватьПакет: предпросмотр без записи в очередь.
   Убедиться, что GUID корня/форматов соответствуют базе; проверить иерархию,
   технические уровни, территории, СЕ и актуальное распределение.

D. Заполнить тестовые настройки, Включен = Истина, ЗаписатьНастройки.
   Нажать ЗарегистрироватьИзменения.
   Ожидается одна новая строка ОчередьШины для KP_SUPPLIER с ОжидаетОтправки.
   В КП_СостояниеСправочников должна измениться ревизия/хеш в той же транзакции.

E. Повторить ЗарегистрироватьИзменения без изменения данных.
   Ожидается ЕстьИзменения = Ложь; новой строки очереди нет.

F. Изменить тестовое имя выбранной категории/СЕ в тестовой базе, повторить сборку.
   Новая ревизия, новый message_id, новый ИдентификаторОбъекта очереди;
   старый ещё не отправленный пакет не затёрт.

G. ОтправитьТолькоКабинет. Проверить строку очереди:
   успех передачи сервису → Отправлено + ID транспорта;
   ошибка → Ошибка + диагностический текст;
   Включен = Ложь → строка остаётся в прежнем состоянии без отправки.
   В тестовом получателе проверить кириллицу и совпадение JSON с СтроковыйОбъект.

H. Имитировать потерю соединения на тестовом маршруте, восстановить, повторить отправку.
   JSON message_id и тело сохраняются. ID транспорта при повторной попытке может измениться.
   Получатель обязан распознавать повторный прикладной message_id.

I. Проверить штатную квитанцию: ДоставкаПодтверждена и ДатаЗагрузки.
   Это подтверждение текущего транспорта, не результат применения бэкендом.

J. На принимающей стороне проверить старую ревизию после новой и ошибочный пакет.
   Старые данные не должны заменять новые; невалидный пакет не активируется.

7. ПРАВИЛА ДАННЫХ И ОГРАНИЧЕНИЯ

Выборка категорий сохраняет правило исходника: категории актуального распределения
плюс родители до настроенного корня. Пустая выборка категорий останавливает сборку.
level — глубина от корня с 1; бизнес-соответствие уровням ТЗ сверить до публикации.
GUID корня и форматов сохранены из исходника. СЕ ограничены опубликованными форматами
и объединяемыми направлениями. СтроковыйИдентификатор СЕ сохранён: проверить уникальность.
is_active — boolean; opened_at — YYYY-MM-DD/null. Внутреннее распределение уходит в ДО.

Единый момент СрезПоследних не делает все чтения справочников одной согласованной
версией БД. Перед промышленной эксплуатацией выбрать согласованное чтение или
надёжный контроль изменений во время сборки. Построение цепочек пока читает родителей;
на больших объёмах нужен замер и пакетная оптимизация.

Полный снимок требует защиты от неожиданного массового уменьшения и согласованного
правила деактивации. Текущий код блокирует только полностью пустые категории.
Изменённый состав, единицы с пустыми связями и неоднозначные КМ/форматы проверить
на реальных обезличенных выборках перед автоматической активацией на получателе.

В исходной очереди есть отмена ошибочных сообщений по возрасту и удаление старых
строк. Их политика распространяется на KP_SUPPLIER. Проверить сроки, чтобы не удалять
неподтверждённые данные; считать передачу законченной только по согласованным квитанциям.
Отдельно испытать раннюю квитанцию до записи ID транспорта и повтор после потери ответа.

8. СХЕМА И ГРАНИЦА С ДО/БЭКЕНДОМ

Смотреть scheme.png или scheme.pdf и 20_BUS_Runbook.txt.
Схема исходника: Astor → FromAstor → ToDO_Reference → DocumentManager.
После обработки в ДО: DocumentManager → FromDO → ToBackend → AMQP 1.0 → бэкенд.
Обратно: бэкенд → FromBackend → ToDO_Backend → DocumentManager.

AMQP-брокер пока не назван; source/target, TLS, учётные данные и правила хранения
задаются на стороне Шины по фактическому AMQP 1.0-компоненту. Это настройки стенда,
а не значения, которые можно корректно восстановить из присланных скриншотов.

Код штатного входящего обработчика ДО не предоставлен. В договорённости для ДО:
проверка пакета, дедупликация по message_id, контроль ревизий, сохранение снимка,
локальное сопоставление сотрудников и фиксация дальнейшей отправки в одной транзакции.
Готовность этой части и бэкенда не заявляется кодом Астора.

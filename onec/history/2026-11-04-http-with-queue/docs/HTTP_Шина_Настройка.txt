ШИНА: HTTP-МАРШРУТЫ КАБИНЕТА ПОСТАВЩИКА, 04.11.2026

Это инструкция настройки, не BSL для модуля Шины. Язык и API Шины отличаются от 1С:Предприятия. Имена ниже — имена экземпляров, свойства компонентов сверяются в вашем проекте.

СХЕМА:
1. Справочники: Astor → FromAstor → HTTP_Reference → BackendKP.
2. Ответ того же HTTP-запроса: HTTP_Reference → BuildHTTPResult → ToAstor_Result → Astor.
3. КП: DocumentManager → FromDO_RequestOffers → HTTP_GetOffers → ToDO_Offers → DocumentManager.
4. Изменения КП: DocumentManager → FromDO_OfferChanges → HTTP_UpdateOffer → ToDO_OfferResult → DocumentManager.
5. Действующие FromDO → ToAstor и FromAstor → ToDO оставить отдельными маршрутами внутреннего обмена.
6. AMQP-компоненты этого кабинета отключить после остановки прежнего маршрута и разбора ожидающих сообщений. Другие обмены не отключать.

HTTP_Reference:
  Метод PUT.
  URL: фактический адрес HTTPS API, не пример company.com.
  Путь: согласованный ресурс полного снимка. /categories из ТЗ требует проверки всех шести наборов.
  Тело: исходные байты JSON FromAstor, не JSON-строка внутри JSON и не только payload.categories.
  Content-Type: application/json; charset=utf-8.
  Accept: application/json.
  X-API-Key: защищённая настройка подключения Шины, не JSON/репозиторий.
  Idempotency-Key: message_id исходного пакета (предлагается; требуется поддержка бэка).
  X-Correlation-ID: message_id исходного пакета (предлагается).
  Таймаут/общий бюджет: 30 с по ТЗ; уточнить лимиты шлюза/клиента.
  Перенаправления: отключить, API-ключ на другой адрес не передавать.
  TLS: проверять цепочку и имя сертификата.

При повторе не менять method/URL/application message_id/JSON. У внутренних повторов одной доставки Шины attempt_id остаётся прежним. При новой отправке из Астора attempt_id меняется.

Успех выбранного контракта — HTTP 200 после атомарного применения всех шести наборов. Код в HTML/теле не подменяет статус HTTP. Если API возвращает ошибки с кодом 200, обработку адаптировать до включения. Не включать generic success-on-any-2xx.

После HTTP Шина формирует внутренний JSON (НЕ формат ответа бэка):
{
  "message_type": "supplier.reference.http-result",
  "correlation_id": "message_id исходного пакета",
  "revision": 1,
  "content_hash": "content_hash исходного пакета",
  "attempt_id": "параметр ИдентификаторПопыткиHTTP исходного сообщения",
  "http_status": 200,
  "retry_after_seconds": 0
}

revision/content_hash копируются из исходного JSON. Хеш — хеш payload по текущему BSL, не SHA всех байтов запроса. Межъязыковую канонизацию требуется проверить на общих примерах; RFC 8785 не заявлен.

Если ответа нет, http_status = 0. Реальные 4xx/5xx сохранить. retry_after_seconds — длительность из Retry-After; HTTP-date преобразовать в неотрицательную длительность по часам Шины. Не уменьшать серверную паузу. Тела ответов/Authorization/X-API-Key в квитанцию не копировать. В журнале оставлять message_id, attempt_id, revision, метод, обезличенный путь, код, длительность, техническую причину без секретов/персональных данных.

Результат отправить через исходящий канал 1С, связанный с Astor. Входящий обработчик Астора должен направлять только внутренний тип supplier.reference.http-result в:
  КХ_КП_ТранспортШины.ОбработатьРезультатКабинета(ТекстJSON)
До вызова проверить сервис/канал/отправителя. Штатный receipt для KP_SUPPLIER не использовать. Сигнатуры фактического обработчика события во вложениях нет: по скриншоту её нельзя достоверно восстановить.

Повторы в поставке выполняет Астор: >=60 с после временной ошибки, >=900 с при потере квитанции. В Шине не включать бесконечные дополнительные повторы. Если нужны короткие повторы 1/2/4/8 с из ТЗ, ограничить их общим бюджетом 30 с, учитывать Retry-After и вернуть один итоговый внутренний результат после всех попыток. Длинный Retry-After передавать Астору без блокирующего ожидания. Считать сообщение FromAstor завершённым лишь после устойчивой постановки внутреннего результата в ToAstor_Result; сбой допускает повтор того же HTTP-запроса.

GET КП:
  GET /commercial-offers?startDate=<URL-encoded ISO 8601 UTC>.
  Инициатор ДО. GET не должен менять/помечать прочитанными КП.
  Ответ и контекст курсора вернуть в ДО. Продвигать курсор после сохранения всех страниц.
  Пагинация, границы дат, сортировка и устойчивые идентификаторы согласовываются отдельно.

PUT КП:
  PUT /commercial-offers/{offerId}; offerId кодировать как один сегмент пути.
  Разрешённые поля ответственных/статусов/строк — по контракту.
  Семантику неполного PUT уточнить, чтобы не удалить непереданные данные.
  Подтверждать исходящую запись ДО после обработки ответа HTTP.

ПЕРЕКЛЮЧЕНИЕ:
A. Остановить старую публикацию. Не отправлять одновременно по AMQP/HTTP.
B. Просмотреть только KP_SUPPLIER в ОчередьШины. Разобрать неизвестные результаты старого транспорта по message_id, не чистить регистр целиком.
C. Проверить новый API: все шесть наборов, атомарность, безопасный повтор, устаревшая revision.
D. Заполнить сервис/канал/коды Астора. ВерсияHTTPМаршрута — новая версия ресурса. HTTPКонтрактПодтвержден = Истина после C.
E. Подключить результат; проверить фильтры Opera/ПК. KP остаётся исключённым из общего отправителя.
F. Старые ожидающие сообщения не переписывать. После разбора перевести их в Отменено штатной формой и создать новый снимок с продолжающейся ревизией. Не использовать SQL. Если форма не позволяет редактирование, нужна отдельная административная обработка.
G. Защита общего обработчика сервисов для тестовой базы остаётся. Использовать изолированные подключения и предусмотренный запуск обработки; автоматически защиту не обходить.
H. Проверить: 200, 400, 401, 409, 413, 429+Retry-After, 503, таймаут после применения, потеря/повтор результата, ранний результат, поздняя ошибка старой попытки, перезапуск Астора/Шины.
I. Включить сборку и отправку отдельными расписаниями. Технический повтор не повышает revision.

После исправления доступа для того же маршрута:
  КХ_КП_ТранспортШины.ПовторитьHTTPПакет("UUID исходного пакета");
После исправления данных:
  КХ_КП_ОбменАстор.ПодготовитьИзменения(Истина);

НЕ ВЫПОЛНЕНО: импорт/компиляция проекта Шины, привязка фактического события 1С, загрузчик КП ДО, проверка рабочего API.

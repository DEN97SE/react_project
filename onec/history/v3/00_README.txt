1. ЧТО ПРОХОДИТ ИЗ АСТОРА В КАБИНЕТ

Астор → FromAstor → ToDO → ДО → From_DO → отправка в кабинет → бэкенд.
Шина остаётся транспортом; согласованный внешний протокол — AMQP 1.0.
Физический прямой канал Астор → бэкенд не нужен для этой последовательности:
данные Астора доходят до кабинета через ДО.

Полный payload нового пакета:
  categories — дерево категорий;
  formats — форматы;
  territories — территории/регионы;
  structural_units — СЕ;
  responsible_users — ответственные сотрудники;
  category_format_assignments — категория + формат → КМ/байер.

responsible_users формируется из того же распределения, что назначения:
GUID, имя, табельный номер и роли category_manager / buyer.
Сотрудник с двумя ролями не дублируется.
ДО передаёт весь пакет дальше; распределение и ответственных не вырезает.
Подробное правило — 22_DO_PayloadRule.txt.

Новые пакеты имеют schema_version = 2. Старые пакеты схемы 1 допускаются
проверкой для завершения ранее накопленной очереди. Новый сборщик создаёт
полный снимок схемы 2; старые отсутствующие поля проверка не выдумывает.

Базовый профиль исполнения: серверный, неглобальный, без привилегированного режима,

3. ГДЕ НАСТРОЙКИ

Одна функция ПолучитьНастройки() в КХ_КП_ОбменАстор:
  Включен — сначала Ложь, после настройки тестового маршрута Истина;
  СервисИнтеграции — фактическое имя сервиса Астора;
  КаналИсходящий — фактическое имя его исходящего канала;
  УзелПолучатель — DO (подтверждён вашим скриншотом);
  КодОтправителя — код Астора в проекте Шины;
  МаксимальныйРазмерСообщения — лимит байт, начальный ориентир 5 МиБ.

Настройки находятся в коде, не в новой константе/регистре.
Код стандартного отправителя у вас строит отправителя как astor + КодСЕ:
применить фактический код, зарегистрированный в проекте.
Имя FromAstor на рисунке может отличаться от имени канала в метаданных сервиса.
Секретов AMQP в эти поля не добавлять: подключение брокера находится в Шине.
Сервис и код отправителя не хранятся отдельными полями очереди и берутся из функции.
Менять их при непустой очереди следует как явное переключение маршрута.

4. КАК ИСПОЛЬЗУЕТСЯ ШТАТНАЯ ОЧЕРЕДЬ

Новый пакет регистрируется вашим существующим методом:
  Интеграция1СШина.ЗарегистрироватьОбъектВОчереди(...)

ВнешняяСистема = KP_SUPPLIER.
ИдентификаторОбъекта — новый UUID для каждого нового снимка.
СтроковыйОбъект — точный JSON, неизменный при повторе доставки.
Объект — существующая служебная строка внутреннего представления структуры.
Для KP_SUPPLIER в неё добавлены хеш, ревизия, ID пакета и хеш маршрута.
Это содержимое прежнего поля, а не новые ресурсы регистра.

ID транспорта в ИдентификаторСообщения очереди не заменяет message_id JSON.
Статусы, даты, ошибки и квитанции обслуживает штатный механизм.

Сравнение изменений:
  читается максимальная ревизия KP_SUPPLIER из существующих записей;
  сравнивается хеш payload и маршрута;
  при отсутствии изменений новая запись не создаётся;
  при изменениях — новая ревизия и новый UUID, старый пакет не затирается.

В очередь не добавляются фиктивные строки состояния. Последний реальный снимок
сохраняется при штатной очистке как точка сравнения. См. обязательную вставку 21.
При переходе с ранее работавшего варианта сначала сверить ревизию с получателем,
особенно если прежняя очистка уже удаляла последние сообщения.
Если вручную стереть все записи, история исчезнет; нужна согласованная начальная
синхронизация. Восстановление прежней ревизии из пустого регистра не заявляется.

5. ЧЕТЫРЕ ТОЧЕЧНЫХ ИЗМЕНЕНИЯ В Интеграция1СШина

16 — ранняя ветка KP_SUPPLIER в ОтправитьСообщенияВШину.
     Она идёт до внешнего сериализатора и фиксированного сервиса ВЭДО.
17 — экспортная ручная отправка только кабинета для испытания.
19 — дополнение существующего служебного Объект в СтруктуруЗаписиОчереди.
21 — защита последнего снимка при УдалениеСтарыхЗаписейОчереди.

Интеграция1СШинаПереопределяемый и сериализаторы других систем не менять.
Запись в ANSI остаётся у прежних обменов; наш JSON уходит точными UTF-8-байтами.

KP_SUPPLIER не включать в СистемыСобственнойОчереди(): общая выборка исключит его.
Не использовать исключаемый внутренний EDO-канал для нашего маршрута.
Новая сборка и защитная очистка синхронизируются блокировкой существующего
измерения ВнешняяСистема = KP_SUPPLIER. Проверить применимость управляемых блокировок.

6. ПРОВЕРКА

Сначала тестовая копия и тестовый маршрут; синтаксический контроль всех текстов.

Управляемая форма 14: Ревизия (Число 15,0, начальное 1), ТекстПакета и
РезультатПроверок (Строка неограниченной длины), соответствующие поля и кнопки.
Обычный вариант — 18. Кнопок сохранения настроек больше нет.

Команды:
  ПроверитьФормат — 10 проверок формата/хеша/совместимости/ответственных;
  ПоказатьМаршрут — показывает параметры из функции;
  СформироватьПакет — только предпросмотр;
  ЗарегистрироватьИзменения — штатная регистрация новой версии при изменениях;
  ОтправитьТолькоКабинет — обработка только KP_SUPPLIER.

Проверить по порядку:
1. Предпросмотр содержит все шесть массивов, включая responsible_users.
2. Первая регистрация создаёт одну строку ОжидаетОтправки.
3. Повтор без изменений не создаёт строку.
4. Изменение КМ/байера в исходном регистре меняет payload и новую ревизию.
5. Повтор передачи сохраняет тело и прикладной message_id.
6. Кириллица корректна в ДО и на выходе в кабинет.
7. Штатная квитанция обновляет транспортный ID/статус/дату, не теряя Объект.
8. Штатная очистка удаляет старые завершённые строки, сохраняет последний снимок;
   повторная сборка после неё без изменений не создаёт лишний пакет.
9. Старая ревизия не активируется вместо новой на получателе.
10. После ДО сохраняются responsible_users и category_format_assignments.

Дата регистрации не используется как номер версии: при одинаковой секунде
выбирается максимальная числовая ревизия из маркеров сообщений.
Одновременный сборщик, изменивший очередь во время чтения, вызывает повтор сборки.

7. ЧТО ОСТАЁТСЯ УСЛОВИЕМ ИСПЫТАНИЯ

Применимость расширения/контекстов, реальные имена сервисов/каналов и выполнение
запросов проверяются на вашей базе. Код здесь не компилировался в 1С.
Снимок всё ещё требует согласованного чтения нескольких таблиц при параллельных
изменениях; один момент СрезПоследних не гарантирует это автоматически.

У вас ОбработкаСообщенийСервисаИнтеграции() выходит в тестовой базе.
Проверить отдельные тестовые подключения и предусмотренный запуск обработки;
не считать статус Отправлено доказательством физической доставки.
Защиту тестовой базы этот комплект не снимает.

Отмена ошибочных сообщений по возрасту остаётся штатной. Если последний снимок
отменён, сборщик явно сообщает об этом; после устранения причины
ПодготовитьИзменения(Истина) создаёт новый снимок, а не мутирует старый retry.
Квитанция доставки не равна применению данных бэкендом.

Входящий обработчик ДО и настройки брокера в материалах отсутствуют. Здесь заданы
полный состав передачи и схема; фактическое выполнение на этих участках не заявляется.

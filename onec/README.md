# Кабинет поставщика: действующая HTTP-схема без прикладного регистра очереди

Решение пользователя от 05.11.2026: новый обмен вообще не читает и не записывает ОчередьШины. Шина остаётся, внешний транспорт — HTTP/HTTPS. Новых регистров/констант нет; Интеграция1СШина, её переопределяемый модуль и модули Opera/ПК для этого обмена не меняются.

За основу взяты присланные пользователем рабочие схема и код Integration/KP. Внешний Authorization остаётся как в них; X-API-Key из исходного ТЗ не подставляется автоматически.

## Текущие файлы

- modules/КХ_КП_ДанныеАстора.txt — сборка шести наборов данных, только чтение Астора.
- modules/КХ_КП_СлужебныйОбмен.txt — JSON/парсинг/хеш без хранения состояния.
- modules/КХ_КП_ОбменАстор.txt — настройки, сборка полного JSON и явный запуск отправки.
- modules/КХ_КП_ТранспортШины.txt — прямой вызов СервисыИнтеграции, configuration = Astor, исходное тело UTF-8.
- modules/КХ_КП_ТестыОбмена.txt — подготовленные проверки JSON без отправки и чтения базы.
- bus/Integration.txt — адаптация рабочего кода Шины; сохранены имена обработчиков и узлов, Content-Type уточнён до UTF-8.
- bus/sources/ — транскрипции присланных Integration и KP; это не экспорт проекта.
- docs/architecture.md и docs/HTTP_Шина_Настройка.txt — текущие потоки и реальные ограничения.
- history/2026-11-04-http-with-queue/ — ОТОЗВАННЫЙ вариант с прикладным регистром. Не устанавливать.

Старые КХ_ОбменШиныОбщий, вставки в КХ_ОбменШиныОпера и КХ_КП_HTTPКонтракт для текущего маршрута не требуются. Если общий модуль уже используется другими интеграциями, не удалять его из базы без проверки их ссылок. Новая поставка не меняет обмены Opera/ПК.

## Перед первой отправкой

Остановить ранее установленные задания кабинета, вызывавшие ПодготовитьИзменения, ОтправитьСообщенияКабинета и ОчиститьОчередьКабинета. Эти методы отозваны. Не очищать общий регистр и не изменять чужие задания.

Новые общие модули — серверные неглобальные, оба клиентских контекста и вызов сервера выключены. Включен в ПолучитьНастройки по умолчанию Ложь. СервисИнтеграции и КаналИсходящий — реальные ИМЕНА метаданных сервиса и исходящего канала Астора, не автоматически имена узлов схемы Шины. КодОтправителя/КодПолучателя — коды участников действующего подключения.

Проверить в тестовом подключении, что сообщение канала Astor_to_kp имеет параметр configuration со значением Astor. Маршрутизатор читает именно параметры сообщения. Наличие одноимённого поля JSON недостаточно.

```bsl
ТекстJSON = КХ_КП_ОбменАстор.СформироватьJSON();
// Просмотреть состав, сверить с действующим API бэка до включения отправки.
Результат = КХ_КП_ТранспортШины.ОтправитьJSON(ТекстJSON);
```

ОтправитьJSON допускает готовый рабочий JSON вместо новой сборки. Он проверяет синтаксис и корневой тип, но не пересериализует тело и не добавляет оболочку payload/revision. ИдентификаторПакета передаётся параметром сообщения только для корреляции; его сохранение в HTTP-ответе/канале пока не подтверждено. Дедупликация бэком не объявляется реализованной.

ОтправитьПолныйСнимок каждый раз собирает и отправляет весь набор. Сравнения с прошлым хешем, автоматической регистрации изменений, устойчивой ревизии и сохранённой квитанции нет. Полноценный режим «только по изменению» требует реальной точки регистрации/события изменения; память процесса и часы не подставляются вместо неё.

## Готовность

Синтаксическая структурная проверка Python проходит; это не компилятор 1С. Компиляция/выполнение BSL и языка Шины, SQL на данных базы, события входящего сервиса и HTTP на рабочем стенде не проверены.

Входящий обработчик Астора и параметры HTTP-узлов (метод, URL, путь, политика ошибок) не предоставлены. Поэтому не заявляются готовая обработка ответа, сквозной успех и импорт схемы. ОтправленоВШину означает только возврат штатного вызова отправки. В проекте пользователя входящий KP.GET — приём тела с сайта и передача в ДО, а не GET-опрос бэка. Не заменять эту схему на polling без отдельного решения.

# Интеграция кабинета поставщика

Здесь сохранены текущие TXT-модули 1С, исходные вложения и история разработки. Работа относится к Астору, ДО и 1С:Шине. Бэкенд разрабатывает другая сторона.

## Актуальные решения

- Справочники и ответственные передаются **Астор → 1С:Шина → AMQP 1.0 → бэкенд кабинета**. ДО не является транзитным звеном этого потока.
- Обмен коммерческими предложениями кабинета с ДО — отдельный маршрут. Существующий обмен Астора с ДО сохраняется отдельно.
- Используется существующий регистр `ОчередьШины`. Новые регистры и константы не создаются.
- **`Интеграция1СШина` изменять нельзя.** Предлагавшаяся ранее изменённая копия отозвана и находится только в `history/withdrawn`.
- Общий перечень собственных систем вынесен в `КХ_ОбменШиныОбщий`. В `КХ_ОбменШиныОпера` заменяется только одна функция-обёртка; это сохраняет старую точку входа штатного модуля.
- Передаваемый пакет содержит категории, форматы, территории, СЕ, ответственных сотрудников и распределение категория/формат → КМ/байер.

Версии со слов пользователя: Астор «Торговый дом 7 SE» 7.0.33.7, платформа 8.3.27; ДО 3.0; Шина 8.1.3. Физические настройки AMQP-брокера и входящего обработчика ещё не проверены.

## Где что находится

| Каталог | Содержимое |
|---|---|
| `modules/` | Актуальные модули: отдельный UTF-8 TXT на каждый модуль. Длинные выражения и запросы записаны одной строкой |
| `fragments/` | Замена одной функции существующего `КХ_ОбменШиныОпера`; **не полный текст модуля** |
| `sources/` | Исходный BSL, его исходная TXT-копия, README вложения, первоначальный список собственных систем и контрольные суммы вложений |
| `requirements/` | Исходное ТЗ DOCX и извлечённый текст. Последующие решения из этой инструкции имеют приоритет при расхождениях |
| `docs/` | Актуальная схема и запись результатов проверки |
| `history/` | Предыдущие варианты и схемы. Они сохранены для истории, **не для установки** |

## Общий реестр систем

Новый общий модуль: [КХ_ОбменШиныОбщий](modules/КХ_ОбменШиныОбщий.txt).

Он предоставляет:

```bsl
КХ_ОбменШиныОбщий.СистемыСобственнойОчереди();
КХ_ОбменШиныОбщий.СистемыОбмена("Opera");
КХ_ОбменШиныОбщий.СистемыОбмена("PriceCheker");
КХ_ОбменШиныОбщий.СистемыОбмена("StructuralUnits");
КХ_ОбменШиныОбщий.СистемыОбмена("KP_SUPPLIER");
КХ_ОбменШиныОбщий.СистемыДействующихОбменов();
```

`PriceCheker` сохраняется именно в существующем написании. Порядок первых пяти меток сохранён: `Opera`, `PriceCheker`, `OperaChange`, `OperaState`, `StructuralUnits`.

В существующем модуле `КХ_ОбменШиныОпера` заменяется только эта функция:

```bsl
Функция СистемыСобственнойОчереди() Экспорт
    Возврат КХ_ОбменШиныОбщий.СистемыСобственнойОчереди();
КонецФункции
```

Полный список служит для исключения систем из штатных обработок. Каждый собственный отправитель должен выбирать только свою группу. Для прежнего общего обработчика пяти меток предусмотрен `СистемыДействующихОбменов()`.

Метка `KP_SUPPLIER` **по умолчанию ещё не включена** в общий список: `ВключенСобственныйОбработчикКабинета()` возвращает `Ложь`. Перед подключением нужно проверить фильтры существующих отправителей Opera/ПК и подключить отдельный обработчик кабинета. Активация не должна привести к тому, что старый отправитель заберёт сообщения нового обмена.

После подключения владельца очереди эту метку оставляют в реестре. Оперативная пауза кабинета задаётся отдельным `Включен` в `КХ_КП_ОбменАстор`, а не возвратом записей в штатный обработчик.

## Модули кабинета

| Модуль | Назначение |
|---|---|
| `КХ_КП_ДанныеАстора` | Сборка справочников и ответственных из исходного регистра |
| `КХ_КП_СлужебныйОбмен` | JSON, хеш, оболочка и проверка пакета |
| `КХ_КП_ОбменАстор` | Подготовка изменений и регистрация через существующий экспортный регистратор |
| `КХ_КП_ТранспортШины` | Собственный отправитель, статусы, результат кабинета и очистка только `KP_SUPPLIER` |
| `КХ_КП_ТестыОбмена` | Предусмотренные проверки для исполнения в 1С |

Текущий `ПолучитьНастройки()` выключает обмен по умолчанию. Реальные имена сервиса, канала, отправителя и код бэкенда в Шине нужно заполнить по стенду. Значение `DO` для потока справочников не используется.

Для обычного приложения контексты новых общих модулей должны соответствовать работающим собственным модулям этой конфигурации. Синтаксический контроль и доступность конкретных API проверяются в самой базе.

Подготовленные точки вызова:

```bsl
КХ_КП_ТестыОбмена.ВыполнитьПроверки();
КХ_КП_ОбменАстор.СформироватьПакетДляШины(1);
КХ_КП_ОбменАстор.ПодготовитьИзменения();
КХ_КП_ТранспортШины.ОтправитьСообщенияКабинета();
КХ_КП_ТранспортШины.ОбработатьРезультатКабинета(ТекстJSON);
КХ_КП_ТранспортШины.ОчиститьОчередьКабинета();
```

Для расписания подготовлен `КХ_КП_ОбменАстор.СборкаПоРасписанию`. Регистрацию и отправку выполнять раздельно. Для одного обмена нужен один активный отправитель; повторная доставка должна распознаваться получателем по прикладному `message_id`.

Результат кабинета — согласуемый контракт: `message_type = supplier.reference.result`, `correlation_id = message_id` исходного пакета, `revision`, `status = applied/rejected`. Привязка фактического входящего события сервиса к обработчику ещё не выполнена.

## Статус проверки

Проверены структура текстов, межмодульные ссылки, сохранение прежних пяти меток и разделение групп. Новые модули вызывают только существующий экспортный регистратор `Интеграция1СШина.ЗарегистрироватьОбъектВОчереди`.

**Не выполнены:** компиляция и исполнение в 1С, запросы на данных баз, фактическая запись/отправка, привязка обработчиков, доставка через Шину и AMQP, сквозная проверка бэкенда. Подготовленные листинги не означают готовое развёртывание.

В исходном коде общий обработчик сервисов интеграции выходит для тестовой базы. Для испытания нужны изолированные тестовые подключения и предусмотренный запуск обработки сервисов; защиту тестовой базы этот комплект не снимает.

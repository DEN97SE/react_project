ТЕКУЩЕЕ РЕШЕНИЕ 05.11.2026: СУЩЕСТВУЮЩАЯ ОЧЕРЕДЬ, HTTP, УСПЕХ БЭКА, TTL 3 СУТОК

1. Рабочая схема сохраняется: Astor_to_kp → маршрутизатор → Http_kp_Astor → преобразование результата → From_kp_Astor → Astor.
2. Астор сначала регистрирует готовый JSON существующим экспортным методом. Собственный обработчик выбирает только KP_SUPPLIER и свой маркер KP_HTTP_BUFFER_V1. configuration=Astor устанавливает готовый отправитель.
3. Общий список исключений должен содержать KP_SUPPLIER. Существующие Opera/ПК не должны выбирать всю расширенную группу; проверить их реальные запросы. Изменение Интеграция1СШина/переопределяемого модуля запрещено и не требуется.
4. HTTP-метод/URL/endpoint и Authorization брать из рабочей настройки, не выдумывать. Тело JSON передаётся без оболочки payload/revision.
5. После итогового HTTP-ответа создать внутренний отчёт supplier.http.result. packet_id/attempt_id копируются из ИдентификаторПакета/ИдентификаторПопытки исходного сообщения. Код HTTP переносится реальный, 0 — ответа нет. applied=true только при подтверждённом применении; 202/постановка в очередь бэка не подходят. Поведение 200 с бизнес-ошибкой в теле сверить по фактическому API.
6. HTTP_Отчет_Функция.txt содержит только чистую функцию форматирования на API, уже использованном в вашем KP. Она сама не подключена к узлу. Присланные методы ОбновлениеМетрик только читают код и пока не формируют отчёт. Проверить сохранение параметров исходного запроса после HTTP и вставить преобразование перед From_kp_Astor.
7. Входящий обработчик сервиса Астора создать средствами Конфигуратора, проверить канал/отправителя, прочитать текст внутреннего отчёта и передать в КХ_КП_ПриемАстор.ОбработатьОтчетШины. Сигнатуру события и API чтения его тела нужно подтвердить на платформе, в предоставленном коде этого обработчика нет.
8. Только после этого включать автоматическую обработку. Успешный возврат из отправителя сохраняет строку. HTTP 200+applied=true удаляет одну строку. Временные ошибки дают отложенный повтор, невременные останавливают пакет до TTL. Повторный/поздний ответ не создаёт строку снова.
9. Время жизни — 259200 секунд от регистрации в UTC, попытки его не продлевают. На границе срока новая отправка не начинается. Физическое удаление при следующем запуске очистки, например каждые 5 минут. Удаляются и ошибки/остановленные пакеты, в журнале ID+статус без тела JSON/секретов. Это выбранная политика потери недоставленных данных через 3 суток, отдельного архива нет.
10. Пауза Включен останавливает новые регистрации/отправки, но не срок жизни, приём ответов и очистку. Не убирать метку исключения при паузе.

ТОЧКИ ЗАПУСКА:
Результат = КХ_КП_ОбменАстор.ОтправитьПолныйСнимок(); // только постановка
КХ_КП_ОчередьКабинета.ОтправитьОжидающие();          // отдельное задание
КХ_КП_ОчередьКабинета.ОчиститьИстекшие();           // отдельное задание

Нужен один активный отправитель. По умолчанию локальная временная ошибка повторяется не ранее 60 с, потеря результата — не ранее 900 с. Реальный интервал зависит от расписания. Идентичный ID пакета и тело сохраняются, меняется только ID попытки. Бэку нужна безопасная повторная обработка и защита порядка/версий полных снимков. Если Шина повторяет сама, отчёт отдавать после окончательного результата одной доставки; не отправлять промежуточные отказы как окончательные.

ВХОДЯЩИЕ КП:
Бэк → HTTP-сервис KP.GET → message_kp → kp_to_DO → ДО остаётся отдельным маршрутом. Этот обработчик не опрашивает бэк. Переход на POST требует изменения клиента и шаблона. Ответ «Передано в Шину для доставки в ДО» не доказывает запись КП в ДО.

ТЕСТЫ:
Список проверок полного ключа, раннего/старого/повторного результата, TTL и чужих интеграций — в reuse-and-queue-72h.md. Компиляция, SQL, события, реальные HTTP и эти сценарии пока не выполнялись. Старые строки других форматов автоматически не мигрируются и не удаляются.

# Повторное использование и жизненный цикл пакета

Решения 05.11.2026: использовать существующий регистр; удалять только после подтверждённого успеха бэка; срок жизни 259200 секунд. Это не срок хранения успешных пакетов: успешный удаляется сразу после подтверждения.

## Минимальный новый слой

Готовый публичный регистратор сохраняет строку в штатной структуре. Готовый UTF-8 отправитель создаёт сообщение сервиса интеграции и передаёт исходный JSON с configuration=Astor. Сборка данных и JSON-утилиты сохраняются. Защищённые модули не редактируются.

Новый адаптер нужен для поведения, которого нет в предоставленном общем API: фиксированного дедлайна, безопасного выбора собственных пакетов, блокировки на короткую транзакцию, проверки ответа и удаления одной записи. Приватные функции штатного модуля не вызываются. Существующая процедура фиксации штатного статуса не подходит: это не экспорт, она использует неполный ключ и не реализует удаление после подтверждения кабинета.

Общий список исключений не равен фильтру собственного отправителя Opera/ПК. Дополнение перечня допустимо только вместе с проверкой, что чужой собственный отправитель не забирает KP_SUPPLIER. Код таких отправителей целиком не предоставлен; автоматическая проверка их запросов не заявляется.

## Состояния

- Регистрация: готовый JSON + стабильный ID пакета, статус ОжидаетОтправки, фиксированный СрокUTC.
- Резервирование попытки: блокировка только наших строк, новый ID попытки, ожидание ответа до следующего повтора. Фактический сетевой вызов — после фиксации локальной транзакции.
- Принято сервисом интеграции: сохраняем транспортный ID в маркере, строку не удаляем.
- Итоговый временный отказ HTTP: Ошибка, следующая попытка не раньше max(60 с, Retry-After).
- Невременный отказ/нет подтверждения применения: Отменено без немедленного повтора, запись сохраняется до TTL.
- Успех бэка: HTTP 200 + явный applied=true, удаляется только строка по полному ключу.
- Истёк TTL: отправка не начинается; строка удаляется с записью об истечении срока в журнале.

Обработчик сохраняет ранний результат, не воссоздаёт строку после удаления, игнорирует позднюю ошибку старой попытки и повтор того же отрицательного результата. Поздний успех того же неизменного пакета завершает его даже при более новой попытке. Для уже удалённого/неизвестного ID возвращается безопасный no-op; тело повторно не регистрируется.

## Привязка результата — ещё требуется

В рабочем Integration пока нет создания отчёта; его методы ОбновлениеМетрик только читают КодОтветаHttp. Добавлена чистая функция форматирования HTTP_Отчет_Функция.txt на основе использованного в KP API СериализацияJson.ЗаписатьОбъект. Она не устанавливает сама обработчики и не доказывает сохранение параметров исходного запроса после HTTP.

Нужно в реальном проекте поставить преобразование HTTP-ответа перед From_kp_Astor и передать:

```json
{
  "message_type": "supplier.http.result",
  "packet_id": "параметр ИдентификаторПакета исходного запроса",
  "attempt_id": "параметр ИдентификаторПопытки исходного запроса",
  "http_status": 200,
  "applied": true,
  "retry_after_seconds": 0
}
```

Смысл applied=true определяется контрактом бэка. Если 200 означает только приём в его очередь, true ставить нельзя. Нужен окончательный результат применения. Если повторяются запросы в самой Шине, отчёт отправляется после последнего результата одной доставки, иначе промежуточный отказ можно принять за окончательный.

Событие сервиса интеграции Астора создаётся Конфигуратором, проверяет отправителя и канал, извлекает JSON отчёта и вызывает:

```bsl
КХ_КП_ПриемАстор.ОбработатьОтчетШины(ТекстJSON);
```

Либо уже проверенный обработчик передаёт поля напрямую в ОбработатьРезультатHTTP. Сигнатура события и API извлечения тела именно из его параметра не выдуманы. Без этой привязки и безопасных повторов автообмен включать нельзя.

## Проверки на копии базы

1. Чужая запись с другой ВнешняяСистема и схожими узлом/каналом/ID остаётся неизменной.
2. Конфликт ID+узел до регистрации не перезаписывает существующее сообщение.
3. После возврата отправки запись существует; после подтверждённого успеха отсутствует.
4. Успех, пришедший до возврата отправки, не создаёт запись снова.
5. Старый отказ после новой попытки не меняет её состояние.
6. Повторный отрицательный результат не продлевает Retry-After; повторный успех безопасен.
7. Перед 72 часами строка ещё действительна, на границе уже не отправляется, после очистки удалена.
8. Ретраи не меняют TTL, ID пакета и тело. Прерывание процесса и потеря ответа требуют проверки дедупликации бэка.
9. Ошибочные/остановленные пакеты также удаляются после 72 часов; в журнале есть ID и статус.
10. Старые форматы и чужие интеграции не очищаются. Оперативная пауза не снимает исключение KP и не обнуляет срок.

Эти сценарии перечислены для исполнения на стенде. Структурный скрипт не заменяет проверки реальных транзакций, гонок, прав и доставки.

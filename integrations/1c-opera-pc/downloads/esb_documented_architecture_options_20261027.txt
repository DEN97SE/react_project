Источник и границы

Прочитан файл пользователя 1C_ESB_help_for_review.txt (1 713 782 байта). В нём 30 ответов HTTP 200: 29 страниц с документацией, а корневой /docs/help/ вернул форму входа. Текст страниц извлечён из HTML с восстановлением кодировки. Это локальная справка program58, не результат доступа к публичному сайту.
Проверены разделы об участниках, группах, адресации AMQP, маршрутизации, HTTP, хранящих каналах и публичных очередях.
Примеры программного массового создания участников, выдачи API-ключей и изменения членства в группы в этой подборке отсутствуют. Их работоспособность по данной подборке не подтверждена.

Что документация подтверждает

1. Одну информационную систему можно использовать в разных процессах одного приложения. Обмены независимы; для Канал1СИсточник и Канал1СНазначение создаются отдельные очереди.
Источник: http://program58:9090/docs/help/topics/participant-groups/
Цитата: «В рамках одного приложения одни и те же информационные системы могут быть задействованы в разных процессах интеграции одновременно. В таком случае процессы обмена сообщениями будут протекать независимо».

Следствие: отдельный участник ASTOR_0050 может быть одновременно включён в группы источников Opera и PC. Отдельные информационные системы astor_opera_... и astor_pc_... для одной базы не обязательны. В базе можно сохранить два объекта сервиса интеграции, настроив их на одного участника соответствующих процессов. Конкретное подключение и применение настроек всё равно проверяется пилотом.

2. Группа позволяет описать однотипные системы одним узлом на схеме; во время исполнения Шина создаёт необходимые экземпляры и очереди участников.
Источники:
http://program58:9090/docs/help/topics/integration-process-project-element/
http://program58:9090/docs/help/topics/participant-group/
Цитата: «В момент старта процесса интеграции ... для каждой информационной системы из группы ... создаст одну очередь ... Канал1СНазначение, и одну очередь ... Канал1СИсточник. К этим двум очередям будет иметь доступ только та информационная система, для которой эта очередь была создана».

Следствие: 500 участников не требуют 500 нарисованных веток. Но runtime-очереди, их данные, учётные записи и мониторинг всё равно существуют. Компактность рисунка не устраняет эксплуатационную нагрузку.

3. RecipientCode выбирает участника группы без узла-маршрутизатора. Коды можно задавать отправителем или в трансляторе; несколько кодов разделяются запятой. При отсутствии явных получателей предусмотрена рассылка всем возможным системам.
Источники:
http://program58:9090/docs/help/topics/participant-groups/
http://program58:9090/docs/help/topics/amqp-connection/
Цитата: «По указанному коду будет выполняться маршрутизация сообщения соответствующему участнику процесса без использования узла-маршрутизатора».

Следствие: при адресной AMQP-доставке наш КодПолучателя уже решает нужную задачу. Строить развилку из 500 условий по store_id не нужно.

4. МаршрутизаторПоСодержимому выбирает следующие узлы схемы. Если обработчик отсутствует, сообщение идёт всем непосредственно следующим узлам. Это другой механизм, чем выбор участника внутри общей группы.
Источник: http://program58:9090/docs/help/topics/message-routing/

5. Для HTTP-узла поддерживаются POST и обработчик ПодготовкаЗапроса. Тело входного сообщения по умолчанию становится телом HTTP-запроса; из ответа формируется следующее сообщение. URI можно хранить в свойстве участника и использовать в общем узле через %{Участник.Uri}.
Источники:
http://program58:9090/docs/help/topics/http-integration-scheme-node/
http://program58:9090/docs/help/topics/participant-groups/
Свойство ИгнорироватьКодОтвета при Ложь требует именно HTTP 200. Если backend использует 201/202 и асинхронное применение, обработку этих статусов и последующего прикладного ACK надо проектировать явно.

6. У пользовательского справочника информационных систем есть обязательный Код длиной 36. Пример документации также использует Длина: 36. UUID помещается, но ранее предложенные префиксы плюс полный UUID длиной 45-48 символов выходят за этот предел.
Источник: http://program58:9090/docs/help/topics/information-systems-catalog/
Корректируем прежний пример именования: короткий уникальный стабильный код базы, например ASTOR_0050; код бэка PC может быть UUID store_id. Их сопоставление хранится в реестре. Фактические метаданные проекта имеют приоритет; увеличивать длину ради примера не требуется.
Начиная с совместимости 8.0 документ описывает пользовательский справочник с контрактом, а не прежний системный справочник. Поэтому старые примеры Std::ИнтеграционнаяШина::ИнформационныеСистемы из PDF нельзя переносить как готовый API без проверки.

7. Узлы каналов 1С обладают хранением сообщений. Дополнительный сохраняющий маршрут около них не следует добавлять автоматически. Для сложной обработки между узлами поддерживаются каналы со свойством ЭтоКанал; документация отдельно описывает ограничение повторных доставок и сохранность очередей при изменении схемы.
Источник: http://program58:9090/docs/help/topics/channel-that-stores-messages/
Прикладное подтверждение сохранения товаров нашими бэками остаётся отдельным контрактом. Сам факт передачи сообщения в канал не заменяет processed.

Вариант 1. Прямая адресная AMQP-доставка каждому PC-бэку

В каждой базе 1С один участник, включённый в процессы Opera и PC.
У каждого самостоятельного PC-бэка отдельный участник, учётные данные и очереди. Его код можно сделать равным store_id.
Opera получает все товары в один BackendOpera. PC-пакет адресуется UUID своего бэка. ACK адресуется исходному участнику 1С из source_node.
Процессов два; схема в редакторе общая; отдельные ветки магазинов не рисуются.

Для 500 отдельных баз 1С и 500 самостоятельных PC-бэков это порядка 1000 участников плюс центральные системы и ЦО. Порядок величины, а не точный эксплуатационный расчёт: число runtime-очередей зависит от числа каналов и участия в процессах.
Плюсы: индивидуальные очереди и независимые подключения, малые изменения товарного формата, магазин может работать со своей очередью отдельно.
Затраты: жизненный цикл участников, ключей, разрешений и мониторинг большого количества подключений. Нужен массовый регламент; автоматическая выдача ключей/членство пока не подтверждены найденной справкой.
Выбирать, если магазинные бэки действительно должны самостоятельно получать сообщения из Шины и центра доставки нет.

Вариант 2. Центральный получатель PC, аналогично Opera

Базы 1С -> процесс PC -> один логический сервис Backend_PC -> нужная магазинная база/сервис по store_id.
Backend_PC обязан принимать пакеты всех магазинов и выбирать правильную цель. Работники центрального сервиса могут конкурировать за общую очередь, если каждый способен обработать любой магазин; чужой store_id не является основанием отбросить корректный пакет.
Один участник базы 1С участвует в обоих процессах. BackendOpera остаётся общим. Центральный Backend_PC сохраняется и для справочника магазинов.

Для 500 напрямую подключённых баз 1С остаётся порядка 500 участников-источников плюс несколько центральных, а не отдельные участники каждого PC-бэка. Собственные адреса баз 1С по-прежнему нужны для ACK и запросов восстановления.
Плюсы: меньше магазинных AMQP-подключений и ключей, текущий получатель Backend_PC уже соответствует этой модели, общий справочник не требует переноса, отдельный новый шлюз перед Шиной не обязателен.
Затраты: распределение и устойчивую обработку store_id реализует центральный PC-сервис. Если существующий «центр» является только панелью настроек, потребуется серверный обработчик доставки; одной смены настройки недостаточно.
ACK processed возвращается после сохранения в согласованной конечной цели. Долговечное принятие во внутреннюю очередь центра нельзя молча объявить применением в магазинной базе, если контракт означает конечное сохранение.

Транспорт до центрального PC-сервиса можно оставить текущим AMQP. Если разработчикам удобнее HTTP, документация позволяет заменить конечную доставку узлом HTTP с одним URI и обработкой ответа. Это вариант транспорта той же центральной архитектуры, а не обязательное создание дополнительного самостоятельного шлюза.
Для HTTP нужно явно сохранить адрес источника 1С и связь batch_id/store_id, проверить ответ бизнеса и возвратить прикладной ACK. HTTP 200 без проверки тела не подтверждает обработку всего пакета.
Полный протокол callback/запросов восстановления при асинхронном HTTP не реализован найденным примером автоматически; его надо согласовать и проверить отдельно.

Это рекомендуемый вариант при приоритете простого администрирования и готовности разработчиков PC сопровождать центральную доставку.

Вариант 3. HTTP-доставка непосредственно магазинным API

Один общий HTTP-узел связан с группой PC-бэков; URI берётся из реквизита участника. Получатель выбирается адресом участника через RecipientCode. В редакторе схема остаётся общей.
Магазинный backend предоставляет HTTP API, который сохраняет пакет и возвращает прикладной результат. Адреса, аутентификация и возврат ACK настраиваются согласованно.
Плюсы: магазинным бэкам не нужен собственный AMQP-клиент; используются штатные HTTP-узлы и свойства участников.
Затраты: участники и адреса каждого магазина остаются, нужны доступность API из сети Шины, управление доступом, повторы и разбор ответа. Если цель именно сократить число управляемых систем, этот вариант решает задачу лишь частично.

Вариант 4. Единый шлюз для всех баз 1С

Базы 1С передают данные одному посреднику, он взаимодействует с Шиной и возвращает ответы в собственные почтовые ящики магазинов.
Так можно сократить число участников Шины с обеих сторон, но появляются собственные протоколы доставки, авторизации, хранения, повторов и распределения ACK. При использовании HTTP вместо штатного сервиса потребуется изменить транспорт в базах 1С.
Это самостоятельная разработка, не документированная кнопка «объединить все базы». Для текущей задачи не рекомендую начинать с этого, пока нет требований, которые оправдывают дополнительный посредник.

Что предлагаю выбрать

1. Сохранить два компактных процесса Opera и PC.
2. Использовать одного участника на каждую отдельную базу 1С в обоих процессах. Коды короткие и стабильные, укладывающиеся в 36 символов. Все базы не объединять под одним общим адресом приёма ACK.
3. Opera направлять в единый BackendOpera.
4. PC направлять в единый Backend_PC, который обслуживает все магазины по store_id, если разработчики готовы реализовать этот серверный обработчик.
5. Если центральная обработка PC не подходит, оставить вариант 1 с адресными участниками бэков и планировать их массовое подключение.
6. Общий справочник магазинов от выбранного ЦО сохранить отдельным потоком; не заменять его получателя UUID одного магазинного товарного бэка.

Это уточнение прежних рекомендаций: отдельные источники Opera и PC для одной базы не обязательны; префикс с полным UUID не подходит для документированного кода длиной 36; новый отдельный шлюз перед Шиной не требуется для центральной доставки PC.

Пилот и текущая работа

Текущая проверка 44 v2 уже пройдена. Новая архитектура не внедрялась: ключи, участники, адреса, тела пакетов и активная full-сессия не менялись этим анализом.
Сначала проверить фактическую отправку и возврат прикладного ACK через ExchPriceChecker в текущем пилоте.
До смены источников/получателей составить перечень активных сессий, запросов и неподтверждённых batch_id. Изменение SourceNode в уже сохранённом теле и изменение полного ключа не являются безопасным способом миграции.
Для выбранного варианта провести два магазина одновременно: раздельное сохранение товаров, ACK своей базе, повтор, недоступность одного магазина, запрос full только нужному магазину и сохранность общего справочника.
Точное число очередей, требуемые ресурсы брокера и поведение при изменении членства участников проверить на установленной версии и пилотной нагрузке; компактная схема не означает нулевой нагрузки.

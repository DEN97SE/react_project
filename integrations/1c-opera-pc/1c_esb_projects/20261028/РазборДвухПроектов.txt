Разбор выгрузок ExchangeVEDO 2.0-2.xasm и Opera_PC 1.0-38.xasm.
28.10.2026. Исходные архивы сохранены без изменения. Код не компилировался и приложения не публиковались.

Формат

Оба XASM являются ZIP-архивами с открытыми исходниками: XBSl - встроенный язык, YAML - описание проекта, процессов, справочников и HTTP-шаблонов. Читать и сопоставлять их возможно.
Это выгрузки кода и метаданных. В этих архивах нет снимка существующих записей участников, выданных ключей, очередей сообщений и фактически действующих настроек подключения.

ExchangeVEDO

Проект admin::ExchangeVEDO, версия сборки 2.0-2, совместимость 8.0.
Справочник участников admin::ExchangeVEDO::ВнутреннийEDO::ИнформационныеСистемы.
Процессы: ExchangeVEDO, InternalDataEDO, ExchangeTMS.
HTTP-сервис InfoBases: корневой URL infobases.
Шаблон /infosystem: GET - список ИС; POST - создание ИС.
Шаблон, названный Data, на самом деле имеет URL /gettoken; метод GET, параметр kod.
Поэтому имя элемента Data нельзя принимать за путь /Data. Полный URL приложения требует учёта реального префикса публикации.

InfoBases.xbsl совпадает по назначению с ранее присланным фрагментом: создание пользователя, генерация clientid/clientsecret, создание ИС с DefaultUser и назначение процесса/группы.
GET gettoken возвращает clientid и secretid, где secretid содержит секрет. POST возвращает clientid и clientsecret. Адаптер обязан учитывать это различие либо новый контракт выпускается с сохранением совместимости.

ДобавитьУчастника и ДобавитьУчастниковВГруппы не объявлены пользовательскими методами в модуле ExchangeVEDO.xbsl. Процесс интеграции порождает серверный тип с операциями работы с участниками; присланный работающий код обращается к этим операциям. Требование прислать отдельные пользовательские тела этих двух помощников снимается. Точные сигнатуры и поведение повторного включения всё ещё проверяются средствами разработки/пилотом.

Настройки доступа

На InfoBases в целом Вызов=РазрешеноАдминистраторам.
У GET и POST /infosystem явно указано Вызов=РазрешеноВсем.
У /gettoken указано Вызов=РазрешеноАдминистраторам.
Нужно проверить эффективное разрешение с учётом вложенных правил и аутентификации установленной версии. Нельзя утверждать по одному обработчику, что сервис закрыт администраторам, когда на конкретном POST стоит более широкое разрешение. Также нельзя приравнивать РазрешеноВсем к доказанному анонимному доступу без проверки механизма доступа.
Для нашей выдачи учётных данных определить узкую политику регистрации и разрешённый набор магазинов/групп.

Opera_PC

Проект Komandor::Opera_PC, версия сборки 1.0-38, совместимость 8.0.
Справочник участников: Komandor::Opera_PC::Основной::Exch.
Он реализует контракт СправочникИнформационныхСистем.Объект, поле Код длиной 36, автоматическая нумерация выключена.
Реквизиты: Код, Наименование, Описание, ПользовательПоУмолчанию, ИдТокена.

Уточнение прежнего первичного комментария: в обоих YAML набор реквизитов совпадает. В модуле ЭДО используются английские обозначения Name/Description/DefaultUser; это не доказательство иных реквизитов схемы данных. В адаптации требуется заменить тип/источник справочника на Exch и проверить доступные обозначения полей компилятором, не создавать дубли полей.

Процесс Opera:
- группа источников магазинных баз: MagazyniOpera;
- группа бэков: BackendOpera;
- товарная линия FromOpera -> ToOpera;
- обратная линия FromBackend -> ToBackend.

Процесс PC:
- группа источников магазинных баз: MagazinyPriceChecker;
- группа бэков: BackendPriceChecker;
- товарная линия FromShops -> ToShops;
- обратная линия FromBackend -> ToBackend.

В обоих процессах один и тот же Exch, что соответствует одному участнику магазина в двух процессах. Именно участника с Код=GUID своей СЕ можно назначать сразу в MagazyniOpera и MagazinyPriceChecker. BackendPriceChecker для источника 1С вместо магазинной группы не выбирается.
В архиве Opera_PC сервиса InfoBases либо другого HTTP-сервиса регистрации нет.

Готовность маршрутов

В обоих YAML используются прямые линии каналов 1С. Узлы HTTP и маршрутизаторы, для которых сохранились методы в XBSl, в этих YAML не подключены: сами по себе такие методы на действующую схему не влияют.
Маршрутизаторы в XBSl возвращают пустой массив, поскольку добавление узлов закомментировано. Это не означает, что текущая прямая схема теряет все сообщения; ошибка возникнет, если такой обработчик позже реально привязать к новому узлу маршрутизатора.
Участники и их членство назначаются при выполнении приложения. Список действующих участников из XASM не проверен.

Как переносить HTTP-регистрацию

1. Добавить новый InfoBases в наше приложение Opera_PC. Для простоты доступа разместить в подсистеме Основной: типы Opera и PC сейчас имеют ОбластьВидимости=ВПодсистеме.
2. Использовать справочник Exch, не переносить второй справочник участников из ExchangeVEDO.
3. Создавать/находить одну ИС по GUID СтруктурнойЕдиницы. Для существующей записи брать связанного пользователя из этой ИС, а не искать его по представлению/названию.
4. Назначать этого участника и пользователя в процесс Opera и его группу MagazyniOpera, затем в процесс PC и его группу MagazinyPriceChecker. Первоначальные ключи выдаются один раз для назначенного пользователя.
5. Проверить повторное создание/включение и параллельные запросы. Повтор скрипта не должен создавать новых пользователей, дублировать ИС либо молча ротировать ключ.
6. Возвращать единый ответ для нашего клиента: код ИС, clientid, clientsecret, версия параметров; при необходимости два адреса сервисов. Старые публичные маршруты ЭДО и его потребителей не менять.
7. На стороне 1С применить индивидуальный ответ к ExchOperaPC и ExchPriceChecker штатным УстановитьНастройки. Отправлятор запускает эту операцию на каждой базе, не выводя секреты.

Сохранность проекта

При добавлении HTTP-сервиса сохранить идентификаторы существующих процессов, каналов, маршрутов и справочника Opera_PC. Замена всего проекта копией ЭДО для этой задачи не нужна.
Новые элементы получают собственные идентификаторы. Сходство идентификаторов справочников в двух исходных проектах не является основанием импортировать второй справочник в наше приложение.
Версию сборки изменять только в подготовленном кандидате; чтение и извлечение этих файлов не обновило действующее приложение.
В текущей очереди 1С есть сохранённые отправители MagazyniOpera/Magazyni_PC. Переход на GUID участника планируется отдельно и не выполняется скрытно при получении ключей.

Следующая практическая работа

По полученным исходникам можно подготовить отдельного кандидата Opera_PC с HTTP-регистрацией и индивидуальные TXT-коды для просмотра/вставки. После этого требуется компиляция проекта в среде Шины и пилот: новый магазин, повтор регистрации, получение ключей, членство в обоих процессах, сохранение настроек 1С, фактическая доставка и ACK. Сейчас выполнено только чтение и сопоставление исходников.

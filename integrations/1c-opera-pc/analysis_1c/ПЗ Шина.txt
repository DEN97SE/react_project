Постановка задачи для 1С-разработчика
Тема: Настройка выгрузки данных в шину 1С для проекта «Прайс-чекеры» (Этап 1 / MVP) Дата: 14.08.2026
1. Цель и контекст
Необходимо настроить в конфигурации 1С:АСТОР СЕ (магазина) формирование и отправку полного пакета данных о товарах в шину данных 1С.
Архитектурное правило: Backend магазина не делает прямых запросов к 1С. 1С:АСТОР СЕ выступает единственным источником, который сам собирает данные из своих регистров, формирует итоговый пакет и отправляет его в шину. Backend только получает данные из шины и сохраняет в локальной базе.
2. Состав данных для выгрузки (MVP)
Для каждого товара (номенклатуры) необходимо сформировать единый пакет в формате «Карточка товара для прайс-чекера», где ключом является Штрихкод или GUID, а внутри объекта передаются все связанные данные.

1. Штрихкоды и Единицы измерения
Регистр сведений «Штриховые коды»
• Штрихкод• Ссылка на Номенклатуру• Единица измерения
У одной номенклатуры может быть несколько штрихкодов (например, для штуки и для коробки). Все они должны быть переданы, но привязаны к одной и той же номенклатуре.
2. Мастер-данные товара
Справочник «Номенклатура»
• Наименование (Вкладка «доп. Свойства и Категории» – параметр «Наименование для ценника/(этикетки?)»)• Страна (Вкладка «Основное» – параметр «Страна»)• Состав вкладка Состав(так же есть на вкладке онлайн продажи) и КБЖУ(вкладка Онлайн продажи) (если заполнены в карточке номенклатуры)
Признак «Собственное производство» (Вкладка «доп. Свойства и Категории» – параметр «Категория товара» = Собственное производство) не передаётся, но необходим для условий на следующих этапах. Состав и КБЖУ передаются, если они есть в АСТОР (выводятся на главный экран в MVP).
3. Регулярные цены
Регистр сведений «Цены номенклатуры»
• Номенклатура• Цена• Категория цен (для привязки к конкретной СЕ/магазину)
Цена едина для номенклатуры. Пересчитывать цену в зависимости от отсканированного штрихкода (упаковки) не нужно. В регистре есть поле «структурная единица», в документе основании такого поля нет.
4. Акционные цены и условия
Регистр сведений «Рекламные акции и цены» / Документ-основание «Назначение рекламных акций»
• Номенклатура• Акционная цена (в регистре «Цена», в документе основания «Основная цена во время акции»)• Вид акции (в регистре нет, в документе основания «Вид акции»: Спец. цена, M по N, Скидка %, Цена на товары индикаторы)• Период действия (ДатаНачалаПериод и ДатаОкончанияПериод)
Отправляем первую найденную активную акцию для данной СЕ. Пересечения акций контролируются бизнесом вручную, на стороне 1С дополнительную фильтрацию дублей делать не требуется. Акции отправляются в шину в момент начала периода их действия (или при изменении). Backend самостоятельно проверяет попадание даты сканирования в период «с-по».
3. Требования к механизму отправки в шину
Первичная загрузка (Initial Sync): При первом подключении магазина к системе шина должна получить полный срез всех актуальных данных (все штрихкоды, номенклатуру, цены и акции) для формирования локальной базы Backend.
Инкрементальные обновления (Delta Sync): При любом изменении данных (смена цены, добавление/снятие акции, редактирование карточки товара, изменение штрихкода) 1С:АСТОР СЕ должна отправлять в шину полный обновленный пакет по конкретной номенклатуре/штрихкоду. Отправки только GUID + измененного значения недостаточно. Backend должен получить все поля карточки целиком.
Гарантия доставки: Отправка должна происходить с ожиданием подтверждения получения от Backend. Данные удаляются из очереди шины только после получения положительного ответа (ACK) от Backend.
4. Что НЕ нужно выгружать на этапе MVP
Чтобы не тратить ресурсы на разработку и передачу лишних данных, на текущем этапе строго исключить из выгрузки:
Остатки по СЕ (планируется на Этапе 2).
Сроки годности (вынесено в глобальный проект компании).
Данные программы лояльности «Копилка» (Loymax не связан с 1С:АСТОР).
5. Критерии приёмки (Definition of Done)
Настроен регламентный механизм первичной полной выгрузки всех товаров магазина в шину.
Настроены обработчики событий (или регламентные задания), которые формируют и отправляют в шину полный пакет «Карточка товара» при изменении цены, акции или свойств номенклатуры.
Реализован механизм ожидания подтверждения от Backend перед удалением сообщения из очереди шины.
В передаваемом JSON/XML пакете отсутствуют поля остатков, сроков годности, изображений и данных лояльности.
Проведен тест: изменение цены на тестовой номенклатуре в 1С:АСТОР СЕ приводит к отправке в шину полного пакета с новой ценой, который успешно принимается тестовым Backend.

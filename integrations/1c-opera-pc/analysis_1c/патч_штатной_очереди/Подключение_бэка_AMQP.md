# Прямое подключение бэка к 1С:Шине

Основание: присланный пример «Отправка и получение сообщений по протоколу AMQP из стороннего приложения» и последние две схемы интеграции. Подключение к реальному серверу не выполнялось.

## Архитектура

Бэк подключается непосредственно к индивидуальным очередям участника каналов 1С по AMQP 1.0. Пример использует библиотеку Node.js `amqp10`, а не протокол AMQP 0-9-1. Обычный клиент только для 0-9-1 не является совместимой заменой.

Существующие узлы `Канал1СИсточник` и `Канал1СНазначение` сохраняются. `RabbitMqИсточник` / `RabbitMqНазначение` нужны для интеграции с отдельным RabbitMQ, который текущий вариант не требует. Регистры `ОчередьШины` в базах Астора и индивидуальные очереди каналов на сервере Шины — разные уровни хранения.

## Направления по фактическим стрелкам схем

| Процесс | Кто | Откуда/куда | Назначение |
|---|---|---|---|
| ExchangeOpera | Астор | Отправляет в FromShopsOpera | Full/delta-пакеты товаров и остатков |
| ExchangeOpera | Бэк | Получает из ToShopsOpera | Пакеты от магазинов |
| ExchangeOpera | Бэк | Отправляет в FromBackend | Обратные сообщения, например прикладные подтверждения |
| ExchangeOpera | Астор | Получает из ToBackend | Обратные сообщения бэка |
| PriceChekerExc | Бэк | Отправляет в FromBackendShops | Запрос магазина и штрихкода |
| PriceChekerExc | Астор | Получает из ToBackendShops | Запрос на сбор карточки |
| PriceChekerExc | Астор | Отправляет в FromShops | Ответ на запрос |
| PriceChekerExc | Бэк | Получает из ToShops | Карточка либо явный результат ошибки/отсутствия |

Имена `ToShopsOpera`, `ToBackend` и `ToBackendShops` не совпадают с интуитивным направлением: ориентироваться на таблицу, стрелки и связи участников, а не переименовывать их по догадке. Внутренние программные обработчики узлов, если есть, ещё нужно проверить; скриншоты показывают соединения, а не их исполнение.

## Настройка участия

1. Опубликовать актуальные схемы.
2. Убедиться, что информационные системы магазинов включены в группы `MagazinyOpera` / `MagazinyPriceChecker` нужных процессов.
3. Информационную систему бэка включить в `BackendOpera` / `BackendPriceChecker`. Можно использовать одну зарегистрированную систему для двух групп либо раздельные учётные записи по принятой политике. Принадлежность группам задаёт доступные индивидуальные очереди.
4. Запустить процессы интеграции. Отсутствие ошибок в редакторе не проверяет подключение и доставку.
5. Проверить код узла Астора. Существующий код строит его как `astor` + `СЕ.Код`; это не `store_id` карточки, который ранее формировался из `СЕ.СтроковыйИдентификатор`. Для маршрутизации по магазинам нужно явное соответствие двух идентификаторов.

Секреты информационных систем вводятся в настройках/секрет-хранилище соответствующего приложения. Не помещать их в исходники, примеры или чат.

## Последовательность подключения из присланного примера

1. Выполнить HTTP POST `{protocol}://{host}:{http_port}/auth/oidc/token`, используя ключ и секрет клиента информационной системы бэка. В примере это Basic authentication и тело `grant_type=client_credentials`.
2. Пример берёт `id_token` из ответа. С этим токеном выполнить GET `{protocol}://{host}:{http_port}/applications/{application}/sys/esb/runtime/channels`, заголовок `Authorization: Bearer <token>`.
3. В возвращённом `items` найти нужные каналы и получить их `destination`. Фактические значения `channel` проверить в ответе сервера; нельзя вручную конструировать имя индивидуальной очереди из имени узла.
4. Подключиться AMQP 1.0-клиентом к серверу Шины. Пример использует порт **6698**, virtual host `/applications/{application}`, токен одновременно как username и password и SASL PLAIN. Это параметры примера; фактический порт, транспорт и требования защищённого подключения подтвердить в настройках установленного сервера.
5. Создать sender для `destination` канала отправки и receiver для `destination` канала получения согласно таблице выше.

Название приложения берётся из его URL `/applications/{application}`. На скриншоте конфигуратора указан сегмент `Price-cheker`; сверить с URL опубликованного приложения, включая регистр и написание. HTTP-порт для получения токена/метаданных и AMQP-порт — разные параметры. Внешний бэк должен использовать доступный ему адрес сервера, а не переносить `localhost` со скриншота.

Реальный ответ API, срок жизни токена, обновление аутентификации и восстановление соединения данным разбором не проверены.

## Подтверждения и данные

Документ доказывает способ подключения, но его обработчик входящего сообщения только выводит тело в консоль. В примере не реализованы транзакция базы бэка, идемпотентность и подтверждение после сохранения. `durable: true` у исходящего сообщения само по себе этих гарантий не даёт.

Для AMQP 1.0 требуется настроить settlement/disposition в выбранном клиенте так, чтобы успешная обработка подтверждалась после фиксации данных бэком. Нельзя переносить методы `basic.ack` из AMQP 0-9-1 как будто они являются API этого клиента.

Если Астору нужно подтверждение именно бизнес-обработки, бэк отправляет отдельный ответ через `FromBackend` → `ToBackend` с исходным `batch_id` и магазином. Это предложенное использование существующего обратного маршрута, а не уже реализованный обработчик. Штатная `ОбработатьКвитанцию` ищет по транспортному `ИдентификаторСообщения`: прикладной `batch_id` нельзя просто передать вместо него без сопоставления/адаптации. Подтверждение транспорта и прикладной ответ — разные события.

Для ПрайсЧекеров запрос содержит `request_id`, `store_id`, строковый `barcode`; ответ сохраняет исходный `request_id`. Перед маршрутизацией к отдельной базе магазина определить её код участника. Нельзя полагаться на широковещательную доставку запроса всем 500 магазинам. Точный механизм задания адресата и параметры маршрута проверяются по свойствам каналов и обработчикам схем.

## Сквозная проверка

- Получить список каналов под учётной записью бэка и подтвердить доступ к ожидаемым направлениям обоих процессов.
- Передать один тестовый пакет Оперы; получить и проверить JSON, магазин, цену, акцию, остаток и кириллицу.
- Остановить бэк до обработки, затем восстановить; проверить накопление и получение пакета.
- На тестовых данных остановить потребителя после фиксации данных до подтверждения; повторная доставка безопасна и не откатывает более новую версию.
- Проверить обратное подтверждение и его связь с конкретным пакетом Астора.
- Отправить запрос ПрайсЧекера в конкретный магазин; получить коррелированный ответ, отдельно проверить неизвестный товар и недоступный магазин.

Эти проверки в текущем чате не выполнялись: доступа к рабочим базам Астора и серверу Шины нет.

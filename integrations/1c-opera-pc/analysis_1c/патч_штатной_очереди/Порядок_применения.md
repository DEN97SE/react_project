# Кандидат адаптации к существующей ОчередьШины

Это точечные вставки по присланным исходникам и последним скриншотам. Они не применены к базе, не скомпилированы в 1С и не являются завершением интеграции. Исходные вложения сохранены. Проверка в тестовой базе обязательна.

Полученный затем документ «Пример 5. Отправка и получение сообщений по протоколу AMQP из стороннего приложения» подтверждает прямое AMQP 1.0-подключение бэка к каналам 1С. Для этого варианта сохраняются существующие узлы `Канал1СИсточник` / `Канал1СНазначение`; внешний RabbitMQ и замена узлов на RabbitMq-адаптеры не требуются. См. файл `Подключение_бэка_AMQP.md`.

## Подтверждённые факты

- В `СтруктураЗаписиВнешнейСистемы` сейчас поддержана только `АРМСупервайзера`; для остальных систем возвращается `Неопределено`.
- Отправитель существующей очереди использует `Интеграция1СШинаПереопределяемый`, где выбран только `СервисИнтеграцииВЭДО`.
- На последнем скриншоте сервис называется точно `ExchangePriceCheker`, в нём видны каналы `Komandor_PriceCheker_Основной_ExchangeOpera_FromShopsOpera` и `Komandor_PriceCheker_Основной_ExchangeOpera_ToBackend`.
- Существующая `ПереводВJSONДляШины.ЗаписьВнешняяСистема_JSONСообщение` ожидает данные для сериализации, а не готовую JSON-строку в поле `Данные`.
- Модули на скриншоте уже разделены: `КХ_ДанныеОпера`, `КХ_ДанныеПрайсЧекеры`, `КХ_ОбменШиныОпера`, `КХ_ОбменШиныПрайсЧекеры`. Их текущее содержимое не предоставлено: старый объединённый модуль нельзя выдавать за их полную актуальную версию.

## Что меняется

1. В `ОбменДаннымиЧерезСервисыИнтеграции` заменить только функцию из `01_СтруктураЗаписиВнешнейСистемы.bsl`. Она сохраняет ветку АРМ, добавляет внешние системы `Opera` и `PriceCheker`, разбирает сохранённый JSON в структуру. Существующий преобразователь затем сериализует объект, а не строку. Сам `ПереводВJSONДляШины` менять не требуется.
2. В `Интеграция1СШинаПереопределяемый` заменить только функцию из `02_ОтправитьСообщениеВШину.bsl`. Существующую `КодТекущегоУзлаВШине` сохранить. Новый путь выбирает `ExchangePriceCheker`; для остальных типов/каналов сохраняется прежний сервис ЭДО. Новые заголовки добавляются только товарным типам, структура заголовков вызывающего кода не изменяется.
3. В `КХ_ОбменШиныОпера` добавить функцию из `03_РегистрацияПакетаОпера.bsl`. Вызывать её после формирования полного full/delta-пакета вместо регистрации в собственном регистре и прямой отправки того же пакета. Функция принимает готовую структуру и явного получателя, сохраняет JSON штатным методом. Она не проверяет весь бизнес-контракт: до вызова должен выполняться валидатор пакета.

Новые значения заголовка `ТипСообщения`: `OperaProducts` и `PriceCheckerResponse`. Это предложенные имена, а не найденные в вашей схеме типы. До применения сверить фильтры/обработчики Шины и требования бэка. Для full и delta Оперы тип общий, различие остаётся в JSON `kind`. Для входящего запроса ПрайсЧекера новый обработчик ещё не подключён.

Идентификатор записи — UUID `batch_id`. Каждый новый пакет получает собственный UUID; повтор сохраняет UUID и содержимое. Нельзя заново регистрировать другой снимок под старым ID или использовать GUID товара в качестве общего ключа сообщений двух проектов. Транспортный ID при повторной отправке может измениться: бэк дедуплицирует по проекту/магазину и `batch_id`.

В данной цепочке существующий преобразователь экранирует все символы вне ASCII, поэтому текст JSON перед транспортом состоит из ASCII-символов. Кириллица восстанавливается JSON-парсером бэка. Это позволяет оставить прежний низкоуровневый отправитель с ANSI на данном этапе, не меняя другие интеграции. Для произвольной прямой передачи неэкранированного JSON требуется отдельная проверка и явная UTF-8.

## Ограничения, которые остаются

- Это ещё не перенос алгоритма полной выгрузки: нельзя оставлять выборку только из `КХ_ОчередьPriceChekerШина`, просто заменив конечную отправку. Нужны источник порций, устойчивое состояние full-сессии и регистрация дельты. Отдельный собственный регистр для этого патч не создаёт. На production сохранять действующий механизм до завершения и проверки нового пути; не запускать два отправителя одного потока одновременно.
- В текущем регистре остаются показанные ранее риски параллельной обработки, замещения по неполному отбору, изменения статуса после отправки и обработки только одной строки по ID квитанции. Уникальная запись на пакет снижает риск поглощения нового изменения, но не заменяет проверку транзакций и защиты от конкурирующих отправителей.
- Удаление старых записей без проверки статуса и отмена старых ошибок остаются без изменений. До промышленного применения для новых проектов настроить согласованную политику сохранения неподтверждённых пакетов, не нарушив другие обмены.
- Источник квитанции ещё не установлен. `ДоставкаПодтверждена` не считается доказательством сохранения бэком без проверки места формирования квитанции.
- Оба канала со скриншота учтены только для выбора сервиса, в том числе для квитанций. Это не утверждение об их направлении. Регистрация Оперы использует `FromShopsOpera`, как исходный отправитель; направление и настройки проверить в свойствах канала. Имя `ToBackend` само по себе не устанавливает, что это входящий запрос или ACK.
- Каналы ПрайсЧекеров на последнем скриншоте не показаны. Для данных типа `PriceCheckerResponse` новый сервис уже выбирается; каналы и обработчики запросов/ответов, включая `request_id`, ещё требуют подключения. Если их квитанции идут с типом `receipt`, добавить точные имена соответствующих каналов в выбор сервиса.
- На следующем скриншоте Шины каналы ПрайсЧекеров уже показаны: магазин получает запрос через `ToBackendShops`, отвечает через `FromShops`; бэк отправляет в `FromBackendShops`, получает из `ToShops`. В конфигураторе Астора пока показаны только два канала Оперы: для реализации ПрайсЧекеров нужно получить фактические полные имена его каналов после обновления метаданных сервиса из опубликованной схемы. Вставки не выдумывают отсутствующие в скриншоте конфигуратора имена. Для типа `PriceCheckerResponse` выбор сервиса уже предусмотрен, для квитанций добавить подтверждённые имена каналов.
- Регламентное задание на скриншоте имеет имя `КХ_ОбработкаОчередиPriceChecker`; имя метода обрезано и начинается с `КХ_ОбменШиныПрайсЧеке…`. Полное имя, расписание и тело метода не известны. Параметры «3 повтора / интервал 10» относятся к аварийному завершению задания и не доказывают повторы доставки отдельных сообщений.
- Адрес сервиса с `localhost` проверяется из процесса сервера 1С. Сетевая доступность этим разбором не проверена.

## Проверка в тестовой базе

1. Проверить синтаксис и доступность вызываемых методов. Подтвердить имя сервиса и каналов, имена типов сообщений и код узла.
2. Сформировать одну карточку тестового товара с кириллицей, ценой и остатком. Зарегистрировать пакет с новым `batch_id`; проверить одну запись `ОчередьШины`, `СтроковыйОбъект` и правильный канал. В существующих данных ничего не удалять.
3. Запустить действующий отправитель очереди. Проверить, что на Шине тело — JSON-объект с `products`, а не JSON-строка; товар, цена, остаток и кириллица совпадают с пакетом. Новая регистрация сама по себе не отправляет сообщение.
4. Проверить внешний обмен АРМ/ЭДО на представительном тестовом сообщении, поскольку заменяются функции общего механизма.
5. На тестовом пакете проверить недоступность Шины, повтор без изменения `batch_id`, отсутствие потерь после перезапуска, безопасный дубль у бэка, корреляцию поздней квитанции и корректную обработку двух одновременных отправителей. Эти проверки патчем ещё не выполнены.

До успешных сквозных проверок это кандидат изменений, а не готовый промышленный обмен.

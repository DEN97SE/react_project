# Астор → 1С:Шина → бэкенд: разбор и целевая схема

Основание: семь приложенных файлов, два скриншота и уточнения пользователя. Это статический разбор исходников и предложение по реализации. Исполнение в Асторе, настройка работающей Шины и сквозной тест с бэкендом не проводились.

Подтверждено пользователем: платформа 1С:Предприятие 8.3.27, версия Шины указана как 8.1.3; у каждого магазина своя база Астора, отдельно существует ЦО. Релиз Астора не указан. Наличие ЦО не доказывает актуальность его остатков: для оперативных запросов базой-источником следует выбирать магазин, если отдельная проверка не обосновывает использование ЦО.

Рабочим модулем отправки пользователь подтвердил `КХ_ОтправкаДанныхPriceChekerOpera`. Замечания к другим вариантам относятся к истории приложенных исходников и не означают наличия этих синтаксических ошибок в рабочем модуле.

Подготовлен отдельный кандидат `КХ_ДанныеPriceChekerOpera_с_остатками.bsl` и сравнение `Остатки.diff`. Он добавляет расчёт остатков в общий сборщик full/delta/ответа по штрихкоду и отсутствующий метод `ПолучитьНоменклатуруДляПолнойВыгрузкиPriceChecker`. Список полной выгрузки включает все неудалённые элементы номенклатуры текущей базы без групп, как в исходном варианте обмена; отбор ассортимента магазина не добавлен. Исходные вложения сохранены.

Кандидат предназначен для переноса изменений в существующий общий модуль `КХ_ДанныеPriceChekerOpera`, а не для создания нового общего модуля с суффиксом. Название файла отличает его от оригинала. Источник остатков и состав складов взяты из присланной старой выгрузки: это физический остаток по непомеченным на удаление складам СЕ, без вычета резервов. `stock.quantity` передаётся строкой с тремя знаками, `stock.updated_at` — временем расчёта. Существующая функция даты с `+07:00` сохранена и требует проверки пояса сеанса. Сборщик не подключает подписки на изменение остатков, не исправляет очередь и маршруты; эти работы остаются обязательными. Выполнение запроса и компиляция кандидата в 1С ещё не проверены.

## 1. Актуальные требования

Уточнения пользователя имеют приоритет над старым ПЗ:

| Проект | Режим | Направление | Состав |
|---|---|---|---|
| Опера, приоритет | Первичная полная выгрузка, далее изменения | Астор → Шина → бэк | Полные карточки товаров, включая остатки |
| ПрайсЧекеры | Запрос по штрихкоду и магазину | Бэк → Шина → Астор → Шина → бэк | Найденная карточка, включая остаток выбранной СЕ, либо явный результат ошибки/отсутствия |

Для ПрайсЧекеров полная и инкрементальная выгрузка всей номенклатуры не требуются. Для Оперы изменение остатка также является основанием для обновления. Общий формат карточки и сбор данных можно использовать в обоих проектах; маршруты и сценарии должны различаться.

Требование AMQP относится к участку бэк ↔ Шина. В представленном коде Астор использует `СервисыИнтеграции`; необходимость заменять этот участок на AMQP не установлена.

Старое ПЗ отдельно исключало сроки годности и лояльность. Пользователь отменил исключение остатков; отмена остальных ограничений не заявлена.

## 2. Что уже есть и что расходится с требованиями

### Направления перепутаны относительно текущей задачи

В обоих модулях обмена полная и дельта-выгрузка отправляются в `PriceChekerExc_FromShops`, внешняя система записана как `PriceCheker`. При этом `ОбработатьЗапросOpera` принимает `store_id` и `barcode` и отвечает через `ExchangeOpera_FromShopsOpera`.

Это фактическое поведение исходников. Для текущей задачи механизм full/delta нужен Опере, обработчик запроса — ПрайсЧекерам. Одного переименования процедур недостаточно: нужно согласованно изменить каналы, подписки, маршруты Шины, внешнюю систему в очереди и обработчики входящих сообщений. Физические имена объектов уточняются по экспорту проектов.

Оба скриншота показывают схему `PriceChekerExc`, каналы 1С и остановленное состояние на момент снимка. По ним нельзя установить устройство второй схемы, наличие AMQP-подключения и действующие правила доставки.

### Данные и остатки

`КХ_ДанныеPriceChekerOpera.bsl` содержит сбор номенклатуры, штрихкодов, цены и акции, формирование full/delta и получение карточки по штрихкоду. В этом файле нет запроса остатков и поля `stock`.

В `Модуль_полной_выгрузки_20260819.txt` уже есть заготовка источника остатков: `РегистрНакопления.ПартииНоменклатуры.Остатки`, связь `МестоХранения` со `Склады.Ссылка`, ограничение `Склады.Владелец = &СтруктурнаяЕдиница`, сумма `КоличествоОстаток` по номенклатуре. Есть и формирование `stock.quantity` / `stock.updated_at`. Но получение акций и разбиение на пакеты там оставлены заглушками: весь модуль не заменяет актуальный сборщик.

Источник остатков можно взять за основу после проверки метаданных и бизнес-смысла: физический или доступный остаток, состав складов, резервы, единица количества. При успешном расчёте отсутствие строки остатков означает ноль; ошибка расчёта не должна превращаться в нулевой остаток. Нулевые и отрицательные остатки должны передаваться согласно согласованному правилу, иначе бэк не узнает об обнулении.

### Подтверждённые проблемы исходников

| Место | Проблема | Последствие |
|---|---|---|
| `КХ_ОтправкаДанныхPriceChekerOpera.bsl:24` | Вызов `ПолучитьНоменклатуруДляПолнойВыгрузкиPriceChecker`, отсутствующего в приложенном `КХ_ДанныеPriceChekerOpera.bsl` | Представленная пара модулей не образует законченный путь полной выгрузки |
| Тот же модуль, `ОтметитьПакетОтправленным`, строки 400–424 | После `Прочитать()` вызывается `Записать(Истина)` без очистки набора; затем отдельно создаётся запись с идентификатором отправленного сообщения | Прочитанная ожидающая запись сохраняется, а не удаляется; возможны повторные отправки и повторный выбор одной порции при full |
| Тот же модуль, `ОтправитьПакетPriceCheker` | Отметка «Отправлено» фиксируется раньше вызова отправки, тело пакета в показанном регистре не сохраняется | При сбое между операциями нет показанного механизма восстановления именно этого пакета |
| Выборка очереди в модулях обмена | Выбираются только `ОжидаетОтправки` с пустым ID; показанного восстановления ошибок и тайм-аутов ожидания ответа нет | Записи со статусом «Ошибка» и зависшие отправки не получают повторную обработку этим путём |
| `КХ_ОбменPriceChekerOpera.bsl:440,606` | Лишняя `)` в `ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()))` | Синтаксические ошибки в этом варианте файла |
| `Очередь_PriceChecker_Шина.txt:442,579` | Повторно объявлена `УстановитьОшибкуНоменклатурамОчереди` | Файл нельзя использовать целиком как один модуль без устранения дублирования |
| `ОбработатьЗапросOpera` в модулях обмена | Исключение перехватывается и записывается в регистр; явный ответ об ошибке не отправляется, `Отказ` не устанавливается | Бэк может не получить ответа, а повтор обработки зависит от платформенного механизма |
| `ПолучитьКарточкуOpera` | Разрешает обработку только в ЦО; full/delta, напротив, не работают в ЦО | Необходимо определить, где находятся актуальные цены и остатки и куда маршрутизировать запросы |

Исправление очереди не сводится к добавлению `Очистить()`: сначала нужно защитить выбранную версию изменения от параллельной перезаписи. Иначе новое изменение, зарегистрированное после сборки карточки, может быть ошибочно поглощено отправкой старой карточки.

Дополнительно: в показанном актуальном запросе берётся обычное `Номенклатура.Наименование`, тогда как ПЗ требует наименование для ценника. Точный источник свойства нужно подтвердить. В коде вида акции используются поля регистра, а ПЗ описывает получение части полей из документа-основания; наличие этих полей проверяется на реальных метаданных. Формат даты жёстко добавляет `+07:00`: это корректно только если исходная дата действительно приведена к этому поясу.

### Регистрация изменений пока не доказана полностью

В файлах показана подписка на запись штрихкодов. Нет полного состава метаданных подписок на цены, акции, карточки, дополнительные свойства и остатки. Общая процедура `ЗарегистрироватьРегистры` сама по себе не доказывает, что все события подключены.

При замене движений документа нужно учесть объединение старого и нового состава номенклатуры. По одному новому набору невозможно обнаружить товар, движение которого удалили. Для акций и цен с будущим началом нужны события наступления срока: запись документа сегодня не гарантирует отправку актуальной карточки завтра в момент начала действия. Для акций нужны также снятие и окончание действия.

## 3. Целевые маршруты

Ниже логические имена, а не обещание конкретных объектов или настроек версии Шины.

### Опера

1. Изменение данных в Асторе → регистрация изменившихся товаров в той же транзакции.
2. Фоновый отправитель → сбор полной актуальной карточки → сохранённый исходящий пакет.
3. Канал 1С входа в Шину → маршрут Оперы → AMQP-доставка бэку.
4. Бэк сохраняет пакет и сведения об обработанном `batch_id` в своей транзакции.
5. Подтверждение обработки бэка → обратный маршрут Шины → Астор, если Астору необходимо знать о бизнес-обработке.

Начальная выгрузка должна иметь отдельную сохранённую сессию и фиксированный состав пакетов. Смешивать меняющуюся очередь дельты с нумерацией full опасно. Изменения во время full не теряются: нужна согласованная граница и воспроизведение изменений либо сравнение версий товаров. Последний по номеру пакет не доказывает получение всех предыдущих. Завершение определяется полным набором пакетов и их успешной обработкой; пустая полная выгрузка тоже должна иметь явное завершение.

### ПрайсЧекеры

1. Бэк публикует запрос: уникальный `request_id`, `store_id`, строковый `barcode`, срок актуальности запроса.
2. Вход AMQP → маршрут Шины по магазину/узлу → обработчик Астора.
3. Общий сборщик формирует карточку с ценой, акцией и остатком нужной СЕ.
4. Астор → Шина → AMQP-ответ бэку с исходным `request_id` и `store_id`.
5. Бэк связывает ответ с конкретным сканированием.

Нужно различать `ok`, `not_found`, `invalid_request`, `error`. Не найденный товар является результатом запроса, а не поводом бесконечно повторять сообщение. Временная недоступность Астора требует ограниченного повтора и понятного тайм-аута.

Для 500 магазинов нужна таблица соответствия `store_id` → узел/база Астора. Отдельная очередь на каждый магазин не является обязательным следствием количества магазинов. Число очередей и потребителей выбирается после определения топологии и нагрузки. Запросы ПрайсЧекеров должны обслуживаться независимо от тяжёлой полной выгрузки Оперы.

## 4. AMQP и подтверждения

Позднее пользователь предоставил документационный пример прямого подключения внешнего приложения к каналам 1С:Шины и подтвердил выбор этого варианта. Пример использует AMQP 1.0 и библиотеку `amqp10`. AMQP 0-9-1 и AMQP 1.0 не взаимозаменяемы. Отдельный RabbitMQ для данного варианта не требуется; существующие узлы каналов 1С сохраняются.

Бэк аутентифицируется как зарегистрированная информационная система, получает доступные ему `destination` через API каналов и подключается к ним по AMQP 1.0. Детали и фактические направления двух схем сохранены в `патч_штатной_очереди/Подключение_бэка_AMQP.md`. Параметры примера, включая порт 6698, ещё не проверены на рабочем сервере.

Различаются три события:

- Астор передал сообщение своему механизму интеграции.
- Транспорт принял/доставил сообщение.
- Бэк успешно сохранил данные.

Подтверждение публикации транспортом не доказывает сохранение в базе бэка. Подтверждение потребителя следует выполнять после успешной фиксации данных. Если Астору нужна собственная гарантия бизнес-обработки, бэк дополнительно отправляет прикладное подтверждение по `batch_id`. Само транспортное подтверждение не является автоматически входящим сообщением статуса для BSL-модуля.

В текущем коде удаление локальной очереди вызывается по строкам `Успешно` / `200`. В присланных файлах нет доказательства, что это статус именно сохранения бэком. Нужно проследить реальный источник вызова до удаления записи.

Если AMQP-адаптер Шины считает доставку завершённой уже при передаче внешнему брокеру, буквальное требование «хранить именно в очереди Шины до обработки бэком» потребует отдельного механизма. Нельзя обещать его исполнение одним включением ручного ACK на бэке.

## 5. Предлагаемый контракт сообщений

Это проект контракта, ещё не согласованный с бэком. Существующие поля `batch_id`, `store_id`, `kind`, `products`, `deleted_nomenclature_ids`, а для full — `session_id`, `sequence`, `total_batches`, `is_final` целесообразно сохранить. Добавления версионировать.

| Сообщение | Идентификаторы и содержание |
|---|---|
| Опера full/delta | `schema_version`, `message_type`, `message_id`, стабильный `batch_id`, `store_id`, `kind`, полные `products`, удаления; поля сессии для full |
| Подтверждение Оперы | Новый `message_id`, исходные `batch_id` и `store_id`, статус `processed` только после фиксации данных; при необходимости ID исходного сообщения |
| Запрос ПрайсЧекера | `schema_version`, `message_type`, `request_id`, `store_id`, `barcode`, время истечения |
| Ответ ПрайсЧекера | Исходные `request_id`, `store_id`, `barcode`, статус, `product` либо структурированная ошибка |

Единая карточка: `nomenclature_id`, `name`, `base_unit`, `country`, `manufacturer`, `category`, `composition`, `nutrition`, `barcodes`, `price`, `promos`, `stock`; версия состояния товара для защиты от устаревших сообщений.

Правила для согласования:

- Ключ состояния — магазин и стабильный ID товара; версия сравнивается внутри этого ключа. Версия должна отражать порядок состояния данных, а не просто порядок отправок. Время сборки не заменяет версию.
- `stock.quantity` — абсолютное количество на момент расчёта, не прибавка/убавка; единица количества должна быть определена.
- В текущих модулях десятичные значения форматируются строками. Типы денег и количества нужно сохранить либо изменить согласованно с бэком. Штрихкод всегда строка, включая ведущие нули.
- Полная карточка заменяет прежнее состояние товара. Для очищенных полей определить `null`/пустое значение, для снятой акции — `promos: []`, для удалённых штрихкодов — полный актуальный массив. Неоднозначное отсутствие поля не должно сохранять старое значение у бэка.
- Повтор одного пакета сохраняет исходные `batch_id` и тело. Транспортный ID может меняться по правилам адаптера. Новый актуальный снимок — новый пакет.
- Бэк обрабатывает дубликаты идемпотентно и игнорирует устаревшие версии. Повторный ACK безопасен; поздний ACK старого пакета не удаляет новые изменения.
- Удаление товара передаётся отдельно. В актуальном модуле функция формирования удаления есть, но путь её вызова и доставка в показанной очереди не завершены. Стабильный ID необходимо сохранить до физического удаления объекта.
- Для даты явно определить пояс источника и преобразование. Не приписывать фиксированное смещение неподготовленной дате.

## 6. Очередь Астора: что требуется до промышленного запуска

Логически следует различать регистрацию изменившихся товаров и сохранённые исходящие пакеты. После получения кода существующей `ОчередьШины` отдельный регистр для новых проектов не предлагается: сначала адаптируется действующий механизм. Требования ниже относятся к надёжности алгоритма и не означают обязательного создания новых регистров.

Регистрация изменений: проект, СЕ, номенклатура, версия/маркер изменения. Захват порции должен исключать двух одновременных отправителей; удалять можно только обработанную версию, сохраняя более новую регистрацию. Не выполнять сетевые операции внутри обработчика записи документа.

Исходящие пакеты: проект, СЕ, стабильный `batch_id`, сохранённое тело, состав/версии товаров, состояние, число попыток, время следующей попытки, последняя ошибка. Пакет сохраняется до попытки отправки. При неизвестном результате отправки его можно повторить без потери тела и идентичности. Конкретное место атомарной передачи штатному сервису интеграции нужно определить по возможностям платформы.

Обязательны обработка тайм-аутов, повтор временных ошибок с задержкой, отдельный учёт постоянных ошибок, сохранение недоставленных сообщений, наблюдение возраста очереди и защита от бесконечного повтора повреждённого сообщения. Сохранность данных проверяется настройками Шины и выбранного AMQP-транспорта, а не только кодом Астора.

## 7. Порядок реализации

1. Определить рабочую пару модулей и метаданные очереди; устранить несовместимости и синтаксические дефекты.
2. Согласовать общий контракт карточки, смысл остатка и идентификаторы; вернуть расчёт остатков в общий сборщик.
3. Сделать надёжную регистрацию и отправку Оперы, включая full, delta и восстановление после сбоя.
4. Настроить маршрут Оперы до AMQP-потребителя и обратное прикладное подтверждение при необходимости.
5. Перенести сценарий запроса по штрихкоду в ПрайсЧекеры, добавить корреляцию, маршрутизацию по СЕ и явные результаты ошибок.
6. Подключить все источники изменений, граничные моменты акций/цен и проверить совместную нагрузку двух проектов.

## 8. Приёмка

- Опера: начальная загрузка нескольких пакетов, получение не по порядку, пустой набор, перезапуск в середине и завершение только после всех пакетов.
- Изменение цены, карточки, дополнительных свойств, штрихкодов, акции и остатка приводит к получению полной актуальной карточки.
- Остаток становится нулём; отдельно проверяются отрицательное и дробное количество, несколько складов одной СЕ и отсутствие подмешивания другой СЕ.
- Смена состояния товара во время full и во время формирования delta не теряется; поздний full не откатывает более новую delta.
- Недоступность Шины/брокера/бэка, потеря подтверждения и перезапуск отправителя не теряют данные. Повторы не создают повторных бизнес-изменений.
- После фиксации пакета бэком и до ACK аварийно остановить потребителя: повторная доставка безопасна.
- ПрайсЧекеры: два одновременных одинаковых штрихкода из разных магазинов возвращают данные нужных СЕ и сохраняют исходные `request_id`.
- Неизвестный штрихкод, некорректный магазин, некорректный JSON и тайм-аут дают различимые результаты.
- Полная выгрузка Оперы не блокирует ответы ПрайсЧекерам; измеряются задержка сканирования и задержка изменений. Целевые показатели «реального времени» фиксируются отдельно, без произвольного обещания секунд.

## 9. Что требуется для точных правок BSL и настроек Шины

Версии платформы, Шины и релиз Астора; расположение данных магазинов; какой из модулей обмена установлен сейчас; метаданные регистра очереди и подписок; экспорты обеих интеграционных схем с обработчиками и настройками каналов без паролей; выбранная версия AMQP и место подключения бэка.

Версия платформы, топология и рабочий модуль отправки уже получены; повторно уточнять их не нужно. Точные настройки AMQP требуют подтверждения возможностей установленного продукта и экспорта схем; предложенный изменённый код требует проверки в Асторе. Для безопасного исправления очереди нужны её измерения, ресурсы, периодичность и режим записи, а также подключённые подписки и регламентные задания.

## 10. Дополнение: получен код существующей `ОчередьШины`

Пользователь прислал структуру регистра и 514 строк его обработки. Нормализованная копия: `Штатная_обработка_ОчередьШины.bsl`. Это именно требовавшийся код существующей конфигурации; наличие регистра в платформе 1С вообще из этого не следует.

Подтверждены следующие возможности:

- `ЗарегистрироватьОбъектВОчереди` принимает источник, узел, канал, явный идентификатор и внешнюю систему. Для строкового источника с непустой внешней системой сохраняет исходную строку в `СтроковыйОбъект`.
- `ОтправитьСообщенияВШину` выбирает очередь, вызывает преобразователь внешней системы и отправитель, затем фиксирует результат.
- `СписокСтатусовДляОтправки` выбирает `ОжидаетОтправки` и `Ошибка`: ошибочные сообщения повторно попадают в обработку. Задержка и предел попыток в этом фрагменте не показаны.
- `ЗафиксироватьИзмененияВОчередиШины` устанавливает `Отправлено` после успешного возврата отправителя.
- `ОбработатьКвитанцию` ищет запись по транспортному ID и устанавливает `ДоставкаПодтверждена` или `Ошибка`. Источник квитанции и момент её формирования по-прежнему требуют проверки: это не доказательство сохранения данных бэком.

Решение: переиспользовать этот регистр и механизм для Оперы и ПрайсЧекеров, не создавать `КХ_ОчередьPriceChekerШина`. Простая замена имени регистра в старом отправителе невозможна: у существующего регистра другой состав ключей и свой алгоритм обработки.

Точные ограничения и риски нового фрагмента:

1. В регистрации и фиксации результата замещение набора ограничено только `ИдентификаторОбъекта` и `УзелПолучатель`, хотя в регистре есть ещё канал, внешняя система и ID сообщения. Одинаковый ID объекта и узел могут привести к замещению записей другого проекта или отправки. Для сохранённых JSON-пакетов нужен отдельный стабильный ID каждого пакета и разделение проектов; использовать только GUID номенклатуры для всех отправок нельзя.
2. Между чтением очереди, отправкой и фиксацией результата в показанном коде нет проверки версии выбранного состояния. Если одна и та же регистрация обновилась параллельно, результат старой отправки может перевести новую регистрацию в `Отправлено`. Неизменяемые записи пакетов с уникальными ID устраняют подмену тела в этом сценарии, но отдельно остаётся восстановление после сбоя и защита от параллельных отправителей.
3. `ОбработатьКвитанцию` обрабатывает только первую найденную строку. Не следует строить схему, где несколько строк регистра ожидают квитанцию на один общий транспортный ID, без адаптации этого обработчика. Схема «одна запись на пакет» соответствует текущему поведению лучше.
4. `УдалениеСтарыхЗаписейОчереди` удаляет по возрасту без проверки статуса. `ОтменаЗависшихСообщенийВШине` переводит старые ошибки в `Отменено`. При включённых заданиях данные могут перестать доставляться без успешной обработки. Для новых проектов нужны согласованные правила хранения неподтверждённых сообщений, без необдуманного изменения поведения других интеграций.
5. `ОтправитьИсходящееСообщениеВШину` записывает тело через `КодировкаТекста.ANSI`, что не гарантирует UTF-8. Для JSON новых проектов требуется явный UTF-8 и соответствующее объявление кодировки; влияние общей правки на другие обмены нужно оценить отдельно.
6. `ОчередьДляВыгрузки` выбирает весь подходящий набор без ограничения порции; режим расписания и допустимая нагрузка при full ещё не известны.

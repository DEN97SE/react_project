# Штрихкоды с единицами измерения и основным кодом — 03.11.2026

Последнее требование пользователя: передавать и штучную, и коробочную упаковку, даже если в НСИ у них один ШК. Фильтрация коробок из редакции33 отменена. Изменяется модель связи и ключ получателя, а не исходное количество упаковок.

## Источники, подтверждённые снимками конфигуратора

- РегистрСведений.ОсновныеШтрихкоды: измерение Номенклатура; ресурс ШтрихКод; реквизиты Автор и ДатаИВремяЗаписи. Единицы измерения в регистре нет.
- РегистрСведений.ШтриховыеКоды: Номенклатура, ЕдиницаИзмерения, ШтрихКод — уже используется работающим сборщиком.
- Справочник.ЕдиницыИзмерения: конкретная упаковка товара, ЕдиницаПоКлассификатору и Коэффициент. Ссылка упаковки и ссылка классификатора имеют разный смысл.
- Справочник.КлассификаторЕдиницИзмерения: общая единица классификатора. Название не является идентификатором: на снимке много разных записей «0,5 л».

## Дополнительные поля существующей записи barcodes

| Поле | Значение |
| --- | --- |
| unit_id | UUID конкретной ссылки ШтриховыеКоды.ЕдиницаИзмерения из справочника ЕдиницыИзмерения |
| is_primary | Boolean: barcode совпадает с текущим ШтрихКод регистра ОсновныеШтрихкоды по этой Номенклатуре |
| is_base_unit | Boolean: ЕдиницаПоКлассификатору совпадает с Номенклатура.БазоваяЕдиницаИзмерения и коэффициент упаковки равен1 |

Сохраняются barcode, unit и quantity_in_package; коэффициент передаётся прежней decimal-строкой, включая дроби. Для заполненной ссылки упаковки unit_id формируется из УникальныйИдентификатор(). При пустой исходной ссылке UUID не выдумывается и поле unit_id отсутствует; такое наследуемое состояние требует отдельной обработки качества НСИ, без связывания по одному названию.

Признаки независимы. Основной код товара не означает, что все коды базовой упаковки основные. Если основной код назначен нескольким упаковкам, is_primary будет true у нескольких строк: регистр не содержит единицы и не позволяет выдумать единственную основную упаковку. is_base_unit также не является уникальным ключом записи. Отсутствие основного кода даёт false, а не выбор первой строки.

Для булочки по снимкам ожидается:

| barcode | unit_id | unit | quantity_in_package | is_primary | is_base_unit |
| --- | --- | --- | --- | --- | --- |
|2000452859001|UUID конкретной штучной единицы|шт|1|false|true|
|2210000274648|тот же UUID штучной единицы|шт|1|true|true|
|2000452859001|UUID конкретной коробочной единицы|кор|30|false|false|

Точные UUID получаются в базе, по изображению они не определяются. Основной код2210000274648 остаётся в выгрузке; коробка2000452859001 тоже остаётся. То же правило сохраняет кор/100 и кор/50 для двух тетрадей.

## Ключ и чтение на бэке

В пределах своего проекта связь хранится по **(store_id, nomenclature_id, unit_id, barcode)**. Если проекты используют общую таблицу, project также входит в область ключа. Количество и признаки — изменяемые значения, не часть ключа.

Уникальность одного barcode для всего товара или магазина несовместима с этим требованием. Разные упаковки не объединять и не отбрасывать при разном коэффициенте. Удалять только полностью одинаковые представления; не смешивать разные товары. При приходе полной карточки полностью заменить её связи, снимая старые признаки основного и старые упаковки; сохраняется прежняя защита по версии/эпохе/сессии.

Один скан barcode не сообщает, какую физическую упаковку держит покупатель. Если нужна конкретная упаковка, передаётся unit_id или используется контекст операции. Для согласованного режима проверки штучной цены PC выбирает базовую единицу с коэффициентом1, сохраняя на бэке и коробочные варианты. Основной код используется для представления товара, не для удаления остальных строк. Это правило чтения не меняет цену базовой единицы в исходном JSON.

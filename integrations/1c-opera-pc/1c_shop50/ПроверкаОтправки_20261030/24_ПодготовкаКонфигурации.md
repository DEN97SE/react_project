## Три настройки конфигурации перед включением

1. В функции КХ_ОбменШиныОпера.ПараметрыОбмена изменить только значение ДнейХраненияПодтвержденных с0 на1 для тестовых баз. Это позволяет менеджерам наблюдать подтверждённые пакеты до очистки. Имена каналов, остальные параметры и весь модуль старой локальной копией не заменять.
2. В подписке КХ_ОпераСвойстваНоменклатурыПередЗаписью проверить событие ПередЗаписью и обработчик КХ_ОбменШиныОпера.НаборЗаписейПередЗаписью. Добавить в составной источник РегистрСведенийНаборЗаписей.АссортиментныеМикроматрицы, сохранив нынешние источники. Если отдельная эквивалентная связь уже существует, её не дублировать. В полном результате50 на этом регистре видны только штатные/ShelfSpace-подписки, наших названий нет; по410 строка скриншота обрезана справа, окончательный вывод о всей строке не делается.
3. Для РегистрСведенийНаборЗаписей.НазначениеМикроматрицВСтруктурныхЕдиницах проверить отдельную связь ПередЗаписью -> КХ_ОбменШиныОпера.НазначенияМатрицПередЗаписью. Если отсутствует, добавить подписку КХ_ОпераНазначенияМатрицПередЗаписью. Не назначать этому источнику обычный обработчик НаборЗаписейПередЗаписью: здесь нужен выбор товаров по старым и новым назначениям.

Сохранить изменения, выполнить проверку и обновление конфигурации базы F7, обновить сеанс. Изменения метаданных не выполняются обычным console-алгоритмом; последующая настройка служб и задания выполняется одним блоком24.

## Один алгоритм24 для обеих баз — актуальная версия

- Валидирует свою СЕ/UUID/сохранённые маршруты/каналы, хранение подтверждений, заполненность и активность обоих сервисов, существующее единственное товарное задание и пользователя. Никакой смены личности базы/очистки/повторной регистрации магазина нет.
- По свежим результатам службами управлять уже не требуется: алгоритм не вызывает УстановитьНастройки/УстановитьАктивность, не копирует ключи между службами. Значения ключей только читаются для проверки заполненности и скрытия их возможного появления в ошибках.
- Существующий пользователь задания сохраняется; пустое имя заполняется текущим пользователемИБ, проверяется его существование. Его права и контекст СЕ подтверждаются реальным автоматическим запуском. В50 сохраняется уже настроенный пользователь.
- Каноническое расписание тестов: ежедневно с интервалом10секунд. Используются проверенные имена API ПериодПовтораДней / ПериодПовтораВТечениеДня. Сравниваются все стандартные поля расписания и отсутствие детальных исключений. После проверок включается только выбранный общий товарный job. Дубли не создаются и не удаляются; отдельный старый PC-job, если он активен, блокирует включение общего цикла.
- Если изменение параметров пришлось на ещё активный товарный цикл, выключаются будущие старты только этого задания, текущий запуск не отменяется, предлагается повтор после завершения. Повтор при уже верных настройках читает историю/очереди, не переписывает расписание.
- Прямой вызов товарного метода/ручная отправка не выполняются. Планировщик сам начнёт первичную загрузку обоим бэкам при catalog_bootstrap_started=false.
- Повтор через30–60секунд показывает историю реального задания, прогресс full/очередей и до5ошибок пакетов. При отсутствии истории проверяется блокировка заданий конкретной базы на сервере; алгоритм не разблокирует весь кластер и не включает чужие задания.
- Прежний более широкий черновик настройки служб сохранён как24_ЧерновикНастройкиСервисов_НеВыдавался.bsl для истории. Он пользователю не выдавался и не является текущим алгоритмом.

После фактических результатов проверяется обычное изменение номенклатуры/остатка без ручных вызовов. Доставка и готовность к передаче ещё не объявляются по одному факту включения расписания.

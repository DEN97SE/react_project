# Ответ бэка на товарные карточки Opera и PC

Сверено02.11.2026 с КХ_ОбменШиныОпера.ОбработатьВходящееСообщение/ОбработатьПодтверждение и КХ_ОбменШиныПрайсЧекеры.ОбработатьВходящееСообщение. Это контракт ACK сообщения products; он не является форматом запроса восстановления или ACK справочникаСЕ.

## Opera: транспорт

Бэк публикует ответ в процессе **Opera**, входной узел **FromBackend**. В сообщении задаётся явный RecipientCode; Шина проводит его через обратную ветку к ToBackend нужного магазина.

Для магазина410:

```yaml
SenderCode: BackendOpera
RecipientCode: S4093310384ba4d00ab50ce9efa15eda8
Content-Type: application/json; charset=utf-8
```

Это транспортные заголовки/конверт Шины. JSON-поля с такими названиями сами не задают маршрут.

Общее правило: SenderCode=BackendOpera, RecipientCode=source_node исходного products. Для50 получатель S3370588b074211e0b9c1001a64c3f566. Адрес не подставляется по последнему активному магазину и не фиксируется навсегда на410. Подключение бэка должно соответствовать участникуBackendOpera процессаOpera.

Обратный вход в1С: ExchOperaPC / Основной_ExchangeOpera_ToBackend. Его обработчик передаёт сообщение в КХ_ОбменШиныОпера.ОбработатьВходящееСообщение.

## JSON успешного товарного ACK

Заменить строку-плейсхолдер batch_id значением из принятого products. Это не готовый ACK конкретной порции.

```json
{
  "message_type": "ack",
  "store_id": "40933103-84ba-4d00-ab50-ce9efa15eda8",
  "batch_id": "<batch_id из принятого products>",
  "status": "processed"
}
```

Текущий обработчик требует именно эти четыре поля. Store_id и batch_id копируются из той же принятой порции. Batch_id — поле JSON, а не транспортныйID сообщения Шины. Store_id — UUID с дефисами, source_node/RecipientCode — адрес S... без дефисов. Поле project для ACK товаров в текущем обработчике не обязательно. Dataset=structural_units к ACK товара не добавляется: оно переключает обработчик на другой контракт.

Processed возвращается после надёжного сохранения всей порции или полного надёжного стадирования. На каждую порцию full возвращается самостоятельный ACK. Дубликат уже обработанного batch_id подтверждается снова, без повторного применения устаревших данных. После очистки старой строки1С неизвестный старый batch не создаёт новую строку.

## JSON ошибки

Тот же транспортный получатель и те же store_id/batch_id. Причина должна отражать фактическую ошибку обработки.

```json
{
  "message_type": "ack",
  "store_id": "40933103-84ba-4d00-ab50-ce9efa15eda8",
  "batch_id": "<batch_id из принятого products>",
  "status": "error",
  "error": "Описание фактической ошибки сохранения"
}
```

Допустимые статусы в текущем обработчике только processed/error, в указанном регистре символов. Служебное полеerror необходимо для объяснения сбоя; неизвестный статус отклоняется.

## Отличие PC

Рабочая PC-схема сохраняется. PC-бэк отвечает в **PC / FromBackend**, Opera-бэк в **Opera / FromBackend**. Эти одноимённые узлы относятся к разным процессам.

| Для ответа магазину410 | SenderCode | RecipientCode |
| --- | --- | --- |
| Opera | BackendOpera | S4093310384ba4d00ab50ce9efa15eda8 |
| PC, текущая согласованная схема | S4093310384ba4d00ab50ce9efa15eda8 | S4093310384ba4d00ab50ce9efa15eda8 |

JSON товарного ACK содержит те же четыре поля, но значения берутся из своего проекта: Opera подтверждает batch_id исходного products проектаopera, PC — своего products проектаpricechecker. У двух проектных пакетов разные batch_id. ОтветPC в1С принимается ExchPriceChecker / Основной_PC_ToBackend. Текущая публикация СЕ остаётся только ЦО→Opera, СЕ вPC не добавляются.

## Наблюдаемая проблема Opera

Последний снимок: от410 доставлено12, ToOperaBackendOpera12, FromBackendBackendOpera12, ToBackendмагазинов0. В карточке недоставленного сообщения виденSenderCodeBackendOpera, RecipientCodeнепоказан; узелToBackend/Внутренняяошибка. Полного текста ошибки и JSON этого ответа не получено. Нельзя объявлять точную внутреннюю ошибку установленной по одной общей причине.

Ранее присланный транслятор АдресОтветаPCПреобразование вOpera при пустом списке получателей подставляет Отправитель.Код. Для общегоBackendOpera это не адрес магазина; непустой правильный RecipientCode этот код сохраняет. Простой возврат сообщения с пустым получателем не является безопасным исправлением: по документации пустой адрес на групповом назначении может открыть широкую доставку. Backend должен передавать правильный явный RecipientCode; фактическое исправление и успешный ACK Opera в новой отправке пока не показаны.

Комплект для 29.10.2026: два процесса, отдельная ИС магазина в обоих, два штатных сервиса.

Оценка пилота №50/№410: 6–10 часов совместной доработки и проверки. Регистрация/остатки после 500: 2–3 ч; настройки двух баз: 1–2 ч; доставка/ACK/full: 2–3 ч; отказы/повторы: 1–2 ч. При изменении бэкендов, неподдерживаемом API установленной версии или необходимости отдельного шлюза срок пересчитывается. Массовое подключение 500 баз сюда не входит.

Новые файлы предназначены для выдачи целиком в чате. Пользователь не скачивает архивы/файлы. Никаких обещаний фоновой работы до завтра: подготовка выполняется сейчас, тесты пользовательской среды — завтра.

Предпосылки: установлены канонические общие модули обмена из существующего рабочего выпуска; оба native-сервиса уже присутствуют в конфигурации; HTTP InfoBases использует Основной и содержит существующие НормализоватьКод, ОтветитьОшибкой, УстановитьЗаголовкиОтвета. Общую архитектуру/схемы не перестраиваем. Новый исследовательский SharedUserTest для этого пилота не нужен, его получатели должны быть выключены.

Перед изменениями отключить наши регламентные задания и источник публикации общего справочника на тестовых магазинных копиях; проверить фактическую остановку производителей. На обеих базах выполнить Контекст/Показать. Номера 50 и 410 и реальные store GUID должны различаться. После копирования базы GUID сам не становится GUID другого магазина; автоматическое исправление СЕ скриптом не предусмотрено.

База №50 с прежними пакетами/full продолжает старый обмен под прежней личностью. Переход блокируется, пока сохранены неподтверждённые пакеты, full/запросы/маркеры или роль источника справочника. Не удалять их ради прохождения. Общий справочник имеет отдельный источник ЦО и старый обратный маршрут до завершения. Это обоснованная блокировка, а не основание обходить guard.

В Шине добавить к существующему модулю блок InfoBases_Пилот3.xbsl. Новые шаблоны: GET /pilot-status -> СостояниеПилота; POST /pilot-enroll -> ЗарегистрироватьПилот. Все уровни admin-only. Нет второй карточки/справочника/процесса. Старые health/infosystem остаются. Новый GET возвращает version=opera-pc-pilot-3.

Пользователь приложения регистратора имеет административный доступ к Opera_PC. Обычные участники: код магазина GUID в группах MagazyniOpera и MagazinyPriceChecker; BackendOpera в группе BackendOpera процесса Opera; Backend_PC в группе BackendPriceChecker процесса PC. Коды получателей — реальные существующие BackendOpera/Backend_PC; группы и коды ИС не путать. Проверить реальные подключения бэкендов с их собственными ключами.

Новый общий модуль КХ_ПилотШины: Сервер/ВызовСервера/ВнешнееСоединение=Да, Глобальный/Привилегированный=Нет, без повторного использования. Исполнение через серверную консоль/толстый клиент с административными правами платформы на установку настроек. Администраторские параметры вводятся однократно для ручного пилота, в код модуля не включаются. Этот вызов не является механизмом рассылки административного ключа 500 магазинам: массовый исполнитель позже оставит регистрацию центральной и доставит базам только магазинные результаты.

Модули двух сервисов из комплекта проверяют КодОтправителя до чтения потока: BackendOpera / Backend_PC соответственно. Это реальные коды выбранных бэков, а не названия групп. Назначить процедуры событиям получения. Если рабочий бэк использует другой код, сначала установить доверенный фактический код и согласовать константу/маршрут; не выключать проверку ради приёма неизвестного отправителя. Существующие общие обработчики остаются. В выгрузке названия узлов расходятся с направлением: Opera.FromOpera -> ToOpera -> BackendOpera, FromBackend -> ToBackend -> магазины; PC.FromShops -> ToShops -> BackendPriceChecker, FromBackend -> ToBackend -> магазины. Не переименовывать их во время пилота; проверять реальные связи.

1. При выключенных фоновых производителях запустить Показать(), ТестМаршрутов(), ТестЧужогоACK(). Два последних ожидают PASS. Это локальные проверки, не доставка.
2. В обеих базах выполнить Диагностика(АдминID, АдминСекрет). GET не создаёт ключ. count>1 — дубли, прекратить; count=1 — не повторять регистрацию ради нового ключа. user_id относится к локальному пользователю приложения; user_by_code/user_by_name — глобальные ID, не считать их автоматически одинаковыми.
3. Для переходящей новой №410 выключить оба native-сервиса и подтвердить остановку соединений. Указать их реальные адреса из работающего подключения, локального пользователя выполнения, проверить каналы метаданных. Контроль отсутствия старых нативных сообщений на стороне платформы/Шины остаётся отдельной предпосылкой: регистр бизнес-очереди не доказывает пустоту внутренних очередей.
4. Если count=0, нет неизвестных пользователей и guard проходит: АдресРегистрации = Зарегистрировать(АдминID, АдминСекрет). При уже существующем глобальном пользователе поле ОжидаемыйUserID заполняется только после проверки владельца по доверенной ВЕДО/административной карточке. Совпадение имени само по себе недостаточно. Автоматически брать ID из диагностического ответа и повторять нельзя.
5. Ошибочный HTTP не повторяется. stage указывает операцию. user_created/key_issued отражают успешно завершившиеся вызовы, не доказывают отсутствие побочных эффектов при исключении. По GET и панели сверить глобальную учётку, ИС и членство. Локальный rollback не доказывает откат глобального IAM/брокера.
6. Для уже существующей проверенной GUID-ИС либо после утраты ответа: администратор штатно выдаёт обычный магазинный ключ её проверенному связанному пользователю; АдресРегистрации = ПринятьКлюч(МагазинClientID, МагазинСекрет). Существующие участники и группы должны быть проверены отдельно. Прежний API-ключ автоматически не считается отозванным. Не использовать админский ключ как магазинный. ИС с прежним негuid-кодом нельзя выдать за новую GUID-ИС этим методом.
7. Не закрывая сеанс, Каналы(АдресРегистрации). Минимум четыре уникальных имени без разных destination одного имени. Это предварительный контроль: сверить реальные внешние привязки импортированных native-каналов Opera/PC; локальные имена 1С и опубликованные алиасы API не объявляются автоматически одинаковыми. Список каналов не является сквозной приёмкой.
8. Применить(АдресРегистрации, РеальныйАдресOpera, РеальныйАдресPC, ЛокальныйПользователь). Программа предварительно готовит оба подключения, записывает последовательно и не включает активность. Если шаг упал, ответ остаётся в памяти для проверки/повтора; частичные изменения не объявляются откатившимися.
9. Через до20 секунд ПроверитьНастройку(АдресРегистрации) проверяет запись обоих ключей и маршрутов, удаляет временную копию. Завершение сеанса раньше этого шага теряет временный ответ, но не гарантирует удаления уже выданного серверного ключа.
10. Для готовой GUID-ИС ТестПовторногоPOST(АдминID, АдминСекрет): ожидается ровно 409, ИС/user_id/credential_id не меняются. Этот целевой тест отличается от слепого повторения POST после неизвестного исхода.
11. Включить оба native-сервиса, проверить фактические подключения. УстановитьАктивность не доказывает соединение. Отправка через существующий код вызывает ВыполнитьОбработку для всех активных сервисов области, а не только наших двух; учитывать остальные подключения.
12. В новой готовой базе ПодготовитьFull(), Показать(), Отправить(). Два вызова начала внутри ПодготовитьFull возвращают одну сессию; готовится не более двух порций за вызов. Повторять подготовку/отправку последовательно для продолжения всей сессии. Не сбрасывать full. Для №50 продолжать старую сессию/отправку под прежней личностью; переход и новая GUID-сессия после завершения старого обмена.
13. Реальные бэкенды должны сохранить товары, затем вернуть свой ACK с исходными store_id/batch_id. Для каждого проекта отдельно нужны JSON на бэкенде, факт сохранения и возвращённый ACK к правильному магазину. Показать() должен отразить ДоставкаПодтверждена; вручную вызываемая Отправить() не чистит подтверждённые строки, чтобы они были видимы. На время наблюдения общее задание с очисткой остаётся выключено. Если задание уже чистило, требуются журнал ACK и данные бэка; пустота очереди одна не доказывает успех.

Полезный ACK товаров: {"message_type":"ack","store_id":"<из products>","batch_id":"<из products>","status":"processed"}. Его отправляет реальный бэк после устойчивого сохранения. Скрипт не подставляет этот ACK в живую очередь и не симулирует прикладной успех. Транспортное подтверждение Шины не заменяет такой ACK.

В комплекте нет кода изменения неизвестного нам стека бэкендов. Проверки задержки ACK/идемпотентности выполняются их штатными средствами/тестовым режимом. Если их поддержки нет, потребуется доработка бэкендов; одинаковый JSON в очереди этого не исправит.

Масштабная регистрация требует контроль конкуренции по магазину, постоянный центральный журнал состояний/соответствий, восстановление после частичного успеха и проверенный канал доставки обычных ключей. Текущий последовательный пилот не объявлен выполнением этих требований для 500 баз.

Фактическая локальная проверка: ограниченный разбор BSL и контроль согласованности с текущими источниками. Компилятора/исполнителя XBSL и 1С здесь нет; program58 недоступен. Приёмочные тесты выше подготовлены, но не исполнены в пользовательской среде.

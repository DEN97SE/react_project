# Проверка карточек магазинов

**Результат пользователя:** сценарий 11 выполнен в тестовой базе магазина №50. id совпал с товарным store_id, code=123, store_number=50. Прочитаны 567 непомеченных магазинов (502 работают, 65 не работают), отдельно 16 помеченных. Карточка и пустой отбор сформированы без записи/отправки. Источник результата — РезультатПроверки11.json.

«База ЦО: Да» объяснено пользователем: он намеренно изменяет настройки в тестовой базе магазина. Это не доказательство, что база — авторитетный источник справочника. Будущий регистратор должен иметь отдельный явный выключатель публикации с исходным значением Ложь; одного ЭтоБазаЦентральногоОфиса() недостаточно.

В присланной карточке работающего магазина была старая closing_date=2001-01-01. Код штатной формы скрывает ДатаЗакрытия при Работает и очищает её при открытии. Подготовлена поправка: при is_working=true closing_date=null, при false — фактическая заполненная дата либо null. Произвольный 2001 год не считается пустым для всех магазинов; исходная дата в Асторе не меняется. Статический анализ исправленного модуля — 0 Error, отчёт СЕДатаЗакрытия_20261023.json. Для проверки этой поправки достаточно обновить только новый модуль и выполнить сценарий 12 на одной текущей СЕ; весь справочник повторно проверять не требуется. Изменение ещё не проверено на платформе.

Корневые метаданные получены. Дополнительных файлов для этой проверки не требуется. Подготовлен новый читающий модуль; существующие модули четырёх товарных интеграций, подписки, задания и штатный модуль объекта СЕ на этом этапе не заменяются.

Статическая проверка BSL Language Server 1.0.7: у сборщика и сценария 11 **0 Error**. Запрашиваемые 16 полей проверены по XML/ранее подтверждённым стандартным и общим реквизитам. SHA-256 прежних четырёх товарных модулей совпадают с сохранённым манифестом; в этой правке они не менялись. Отчёт: Проверка/СтатическийАнализ/СборщикСтруктурныхЕдиниц_20261023.json, манифест — ПроверенныеИсходники.json в текущей папке. Платформы 1С в окружении анализа нет: компиляция и исполнение требуют проверки ниже.

1. В **тестовой базе магазина №50** создать общий модуль `КХ_ДанныеСтруктурныхЕдиниц`: Сервер — включён, Глобальный — выключен, повторное использование возвращаемых значений — Не использовать. Вставить [КХ_ДанныеСтруктурныхЕдиниц.txt](../ДляКопирования/КХ_ДанныеСтруктурныхЕдиниц.txt).
2. Проверить синтаксис конфигуратором, обновить конфигурацию базы F7 и открыть новый сеанс.
3. В консоли кода через **«На сервере»** выполнить [11_ПроверитьКарточкиМагазиновБезОтправки.txt](../АвтоматическаяРегистрация/11_ПроверитьКарточкиМагазиновБезОтправки.txt).
4. Сверить карточку: id должен совпасть с прежним store_id **3370588b-0742-11e0-b9c1-001a64c3f566**, code с текущим кодом СЕ **123**. store_number сверить с реквизитом НомерМагазина, не назначать ему 123 по коду. Проверить имя, адрес, Работает и даты по карточке источника. Отдельно выводятся числа работающих/неработающих и помеченных магазинов, пустой массив проверяется как пустой отбор.

Сценарий читает справочник и выводит JSON только текущей СЕ, а также агрегированные количества всего списка. Он не создаёт пакетов, не регистрирует изменения и не вызывает СервисыИнтеграции.ВыполнитьОбработку. Его результат в магазине подтверждает чтение реплики справочника, а не авторитетную публикацию из ЦО. На ЦО текущая СЕ может быть офисом: её нет среди карточек магазинов, это ожидаемо.

Диагностика 10 была подготовлена до получения корневого XML и остаётся дополнительной проверкой роли/метаданных. Для проверки готового сборщика достаточно сценария 11; выполнять обе диагностики подряд без причины не требуется.

Дальнейшее подключение: отдельный регистратор ЦО, первоначальный список и события СЕ, отдельные версии/подтверждения и диспетчер запросов бэка. Это ещё не реализованные обработчики. Не создавать подписки с выдуманными именами методов и не направлять новые типы сообщений в прежние ACK-обработчики.

Если позже будет включена выгрузка имён связанных форматов/территорий/регионов, изменение имени в таком справочнике должно перерегистрировать связанные магазины либо сопровождаться новым full справочника. Изменение этих объектов не вызывает ПриЗаписи самой СЕ. Аналогично перенос склада между владельцами влияет на каталог товаров и требует отдельной обработки зависимостей; текущий читающий модуль такого события не регистрирует.

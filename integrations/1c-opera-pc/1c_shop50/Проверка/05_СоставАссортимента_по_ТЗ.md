# Состав выгрузки: ТЗ, текущий код и предлагаемый отбор

23.10.2026 пользователь выполнил диагностику 06: 357 621 кандидат полной выгрузки, 200 ссылок передано сборщику, 200 карточек сформировано, удалений 0. Это подтверждает сборку первой порции. Данные в Шину этим тестом не отправлялись.

## Что требует ТЗ

В исходном ТЗ «ПЗ Шина», раздел 3, первичная загрузка описана как «полный срез всех актуальных данных». Раздел 5 требует «первичной полной выгрузки всех товаров магазина». Ключ карточки в разделе 2 — «Штрихкод или GUID». Условий «только положительный остаток», «только положительная цена» и обязательного наличия штрихкода для каждой карточки нет. Термин «актуальный товар магазина» не расшифрован через конкретный регистр/статус, поэтому конкретный отбор ниже — рекомендация для уточнения бизнес-правила, а не дословное требование ТЗ.

Текущие договорённости пользователя уточняют исходный документ: остатки нужны уже сейчас для Opera, ПрайсЧекеры получают карточку по запросу через Шину. Поэтому старое исключение остатков из MVP не используется как повод менять уже согласованный обмен.

## Почему текущий список большой

В `КХ_ДанныеОпера.ПолучитьНоменклатуруДляПолнойВыгрузки` отбираются все элементы справочника без пометки удаления. Структурная единица проверяется на заполненность, но не используется для ограничения списка. Поэтому 357 621 — число кандидатов общего справочника этой базы, а не доказанное число товаров, продаваемых магазином №50.

Помеченные на удаление и группы уже исключены из начального списка. В дельте помеченный ранее отправленный товар должен прийти как ID в deleted_nomenclature_ids. Полное игнорирование его записи оставит карточку у бэка. Физическое удаление — отдельный сценарий: текущий сборщик не выдумывает удаление для отсутствующей ссылки и выдаёт ошибку.

## Рекомендация по признакам

| Признак | Предлагаемое поведение |
| --- | --- |
| Группа или пометка удаления | Не включать в начальную полную выгрузку |
| Товар входит в согласованный ассортимент магазина | Включать, даже если временно нет остатка |
| Остаток стал нулевым | Передать stock.quantity=0, не прекращать обновления только из-за нуля |
| Нет записи цены | Не подставлять цену 0 и не сохранять у бэка старую цену. Нужен явный результат актуальной полной карточки/снятие возможности продажи по согласованному контракту |
| Есть запись цены со значением 0 | Различать с отсутствием записи. Допустимость нулевой цены — бизнес-правило |
| Нет штрихкода | Для поиска ПрайсЧекера товар недоступен по штрихкоду; это само по себе не доказывает ненужность GUID-карточки для Opera |
| Товар вне матрицы, но остаток ненулевой | Проверить как исключение: это может быть распродажа, остатки выведенного товара или ошибка учёта |
| Отрицательный остаток | Не терять молча при условии Остаток>0; согласовать отображение отдельно от отбора карточки |
| Нет принадлежности магазину, цены и остатка | Основной кандидат на исключение из каталога магазина |

Предпочтительная основа — ассортимент магазина с учётом допустимых статусов, плюс согласованные исключения по фактическим остаткам. Наличие исторической цены и глобального штрихкода само по себе не определяет текущую принадлежность магазину. Без изучения статусов нельзя автоматически объявлять любой непустой статус «активным».

## Источник ассортимента уже найден в присланном коде

Существующий обмен онлайн-площадок использует:

1. `НазначениеМикроматрицВСтруктурныхЕдиницах`: отбор по текущей СЕ и Назначено=Истина.
2. `АссортиментныеМикроматрицы`: связь по микроматрице и категории/родителю товара.
3. Непустой `Статус` из `СтатусыНоменклатуры`.

Источник найден в реально используемом тексте функции `НовыйТекстЗапросаДанныеОЦенахИОстаткахДляОнлайнПродаж`, начиная со строки 996 сохранённого исходника аудита. Это основание проверить матрицы, а не автоматически переносить весь отбор онлайн-продаж в Opera. Например, финальное исключение нулевых цен из онлайн-обмена и его фиктивные остатки для нашей карточки автоматически не заимствуются.

Подготовлен сценарий `АвтоматическаяРегистрация/07_ОценитьАссортиментБезОтправки.txt`. Он считает наличие цены, штрихкода, знак остатка, принадлежность назначенным матрицам и размеры вариантов отбора. Также выводит названия статусов матриц. Статистика по матрицам воспроизводит найденное условие непустого статуса, но не утверждает, что оно подходит для нашего проекта. Один товар может иметь несколько статусов в разных матрицах: суммы по статусам не обязательно равны общему числу уникальных товаров матриц.

Сценарий предназначен для однократного запуска «На сервере» на тестовой базе. Он не меняет состав рабочего обмена, не регистрирует пакеты и не создаёт full-сессию. Запрос охватывает весь справочник и источники магазина, поэтому может выполняться заметно дольше проверки 200 карточек. Цена берётся из того же среза/категории/базовой единицы, что в текущем сборщике. Для подсчёта наличия используется максимум цены на товар; это не замена проверки неоднозначных цен в рабочем сборщике. Непустой штрихкод здесь ещё не означает проверку его контрольной цифры или уникальности.

## Что потребуется при реализации отбора

Единое правило включения должно использоваться в начальной выгрузке Opera и в обработке её дельты. Если товар вышел из состава выгрузки, нельзя просто пропустить его: бэку нужно явное удаление из каталога магазина или согласованное состояние недоступности. При удалении последнего штрихкода нужно снять старые штрихкоды, при удалении цены — старую цену, при обнулении остатка — старое количество.

Изменения назначения матриц и статусов также должны регистрировать затронутые товары. Одних существующих подписок на цены/свойства недостаточно для обновления членства в ассортименте. Общий сборщик используется также запросами ПрайсЧекера: изменение его фильтра без учёта обоих путей может дать неожиданный not_found. Правило отбора Opera следует отделить от технического чтения карточки.

На текущем объёме по 200 товаров получится примерно 1 789 full-пакетов. Кроме сокращения состава, перед реальным запуском нужно учесть реализацию состояния: сейчас список GUID полной сессии целиком хранится в OperaState и сериализуется вместе с изменениями revision. Для 357 621 GUID один массив JSON занимает около 14 МБ. После постановки всех full-пакетов список также остаётся в поле full. При такой численности это нагрузка на регистрацию изменений внутри транзакций; уменьшение отбора не заменяет проверку/оптимизацию этого хранения.

Рабочие модули не менялись: сначала нужны результаты статистики и смысл используемых статусов, затем можно подготовить согласованное правило и точечную правку full/delta.

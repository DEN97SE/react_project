Автоматическое подключение базы через HTTP-сервис регистрации. 28.10.2026.
Это контракт и план реализации, не готовый штатный URL Шины и не установленный серверный код.

Идея пользователя подходит: база 1С обращается к отдельному HTTP-сервису, получает параметры своего участника и записывает их через ПолучитьНастройки/УстановитьНастройки, затем задаёт активность.
Две части имеют разную готовность: методы записи настроек 1С подтверждены справкой платформы пользователя; поддерживаемая программная выдача ключей и изменение членства участников Шины пока не подтверждены.

Начальная идентификация

Код информационной системы и store_id являются идентификаторами, а не доказательством права на её секрет. По одному коду сервер не выдаёт ключ.
Для первого обращения центр выдаёт индивидуальный одноразовый регистрационный билет, привязанный к магазину, назначенному участнику и конкретному развёртыванию базы. Билет может автоматически доставляться вместе с индивидуальным пакетом развёртывания, поэтому ручной ввод ключей в 500 формах не требуется.
После восстановления копии базы нельзя молча подключать её как исходную рабочую базу: статус развёртывания/назначение проверяются центром. installation_id из произвольного тела запроса сам по себе также не является доказательством личности.
Административный ключ Шины или учётная запись с правом выдачи ключей не размещаются в общих модулях магазинных баз. Такие полномочия использует только сервер регистрации для разрешённых операций.

Предлагаемый контракт

POST /api/esb/enrollment/claim
Authorization: Bearer <индивидуальный регистрационный билет>

Пример тела без секретов:
{
  "request_id": "<UUID операции>",
  "store_id": "3370588b-0742-11e0-b9c1-001a64c3f566",
  "information_system_code": "ASTOR_0050",
  "installation_id": "<идентификатор развёртывания>"
}

URL предложен для нашего HTTP-сервиса. Нельзя использовать его как уже существующий API 1С:Шины.
Сервер проверяет привязку билета и права на этот код, создаёт/находит назначенного участника, обеспечивает его членство в двух нужных процессах и подготавливает ключ. Генерировать новый ключ при каждом повторе запроса нельзя.

Ответ включает store_id, назначенный код участника, версию параметров и массив connections. Для каждого элемента: service, address, client_id, client_secret и при необходимости active. При общем участнике два сервиса могут получить одну пару ключей.
Клиент проверяет магазин и допустимые имена сервисов, преобразует ответ в План для КХ_НастройкаПодключенийШины и сохраняет параметры штатными методами платформы. Секреты не выводятся в сообщения и общий журнал.
После применения учитывается кэш до 20 секунд, проверяется соединение и прикладной тест доставки/ACK. Сам факт возврата из УстановитьНастройки подтверждает запись параметров, но не готовность обмена.

Повторы и ротация

На стороне сервера нужен устойчивый журнал request_id и состояний выдачи. При потере HTTP-ответа повтор не должен создавать ещё одного участника или менять действующий ключ.
Поскольку прежний client_secret может быть недоступен для чтения после однократной выдачи, нельзя обещать его получение из Шины по коду инфосистемы. Нужно либо безопасно сохранять результат первичной выдачи до завершения регистрации и повторно доставлять назначенной базе, либо иметь явно описанную процедуру восстановления/ротации.
Постоянное хранение секретов в центре, если оно требуется, реализуется в защищённом хранилище. Ротация отделяется от обычного повторного запроса регистрации.
Создание пользователя сервиса не предоставляет автоматически полномочия на выдачу токенов: операции и доступ нужно проверить в проекте установленной версии Шины.

Если API выдачи ключей Шины недоступен

Первый этап всё равно возможен: администратор заранее создаёт участников и ключи штатно; защищённый реестр центра хранит соответствия. HTTP-сервис доставляет уже подготовленные настройки назначенной базе, а она применяет их программно.
Это автоматизирует настройку магазинной 1С, но не выдачу ключа самой Шиной. Полную регистрацию добавляют после проверки поддерживаемых механизмов создания участника, групп и токенов.

Граница текущего пилота

Текущие ExchOperaPC и ExchPriceChecker используют разные коды отправителей и уже имеют сохранённые пакеты. Получение общего ключа нового участника не даёт права изменить frozen source_node в старых телах.
Настройка новых баз и миграция существующих - отдельные режимы. Для существующей базы проверяются активная full, запросы и неподтверждённые пакеты; согласованный переход не подменяется автоматическим включением новых учётных данных.
Создание карточки СтруктурныеЕдиницы сохраняет заявку регистрации. Сетевой HTTP-запрос выдачи ключей не выполняется синхронно внутри транзакции записи магазина.

Что уже подготовлено

В наборе есть общий исполнитель КХ_НастройкаПодключенийШины и пример плана. Код построен по подтверждённым методам и четырём свойствам платформы, но ещё не проверен в установленной 1С.
HTTP-клиент, сервер выдачи и централизованный диспетчер 500 баз этим набором пока не реализованы. Для серверной части сначала нужны подтверждённые методы Шины выдачи ключа и включения в группы либо доступный защищённый реестр заранее выданных параметров.

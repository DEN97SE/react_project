Сохранить рабочую выгрузку, открыть кандидат в среде разработки как проверочную копию. Выполнить проверку проекта до публикации.
Если есть ошибка компиляции, сохранить полный текст первой ошибки с именем модуля и строкой. Не публиковать проект с ошибками.
В новой версии проверить:

- HTTP-методы доступны только администраторам;

После успешной проверки обновить сначала тестовое приложение штатным способом. Автоматической публикации из этого комплекта нет.
Получить фактический полный URL POST для infobases/infosystem из опубликованного приложения. Префикс приложения/HTTP-служб не выдумывать: взять адрес из вашей среды.
Для административного запуска нужен API-клиент пользователя с правом вызова этого закрытого сервиса и создания пользователей/участников. Магазинные ключи не имеют административных прав.
В вашем присланном проекте создание пользователей и данные доступа уже используются: кандидат переносит эти вызовы, но компиляция и фактические права в Opera_PC проверяются заново.

2. Проверить HTTP без изменения 1С

Скрипты PowerShell запускаются на центральном Windows-компьютере, не в консоли кода 1С.
Полный URL POST задаётся один раз:

$RegistrationUrl = Read-Host 'Полный URL POST infobases/infosystem'
.\Test-EnrollmentApi.ps1 -RegistrationUri $RegistrationUrl

Скрипт запросит идентификатор и секрет административного API-клиента. Секрет вводится скрыто. В чат его присылать не нужно.
Ожидается PASS проверки health с версией opera-pc-enrollment-2.

Для одного магазина, которого ЕЩЁ НЕТ в Exch под этим GUID:

.\Test-EnrollmentApi.ps1 -RegistrationUri $RegistrationUrl -StoreId '3370588b-0742-11e0-b9c1-001a64c3f566' -StoreName 'К0050' -Register

Приведён GUID вашей тестовой №50. Перед запуском убедиться, что именно этот GUID планируется использовать; вместо него можно указать другой реальный пилотный магазин.
Ожидается PASS регистрации, сохранения защищённого локального результата, отклонения повторного POST с HTTP 409 без перевыпуска ключей и авторизации выданного ключа. В интерфейсе Шины проверить, что один участник с кодом GUID входит сразу в оба процесса и нужные группы.
Проверка создаёт участника, но не меняет настройки базы 1С. Поэтому HTTP можно проверить до миграции её старой очереди.
Любой существующий участник получает HTTP 409 existing_participant_use_central_cache_or_recover. Повторный запуск центрального исполнителя использует DPAPI-кэш и не вызывает POST повторно. Чужие/действующие ключи сервис не ротирует молча. Такой случай требует отдельного согласованного присоединения, а не удаления участника или повторного создания пользователя.

Клиентские контексты не требуются. Сохранить, проверить синтаксис, F7, обновить сеанс. Уже установленные семь модулей обмена и два сервисных модуля не заменять этим комплектом.
Пользователь настройки должен иметь Администрирование данных. Программная запись выполняется штатными методами без обхода прав.
В консоли кода через «На сервере» выполнить 03_database_preflight.txt. Он только читает состояние.

Если can_apply=false из-за pending_packets/full_active/pending_requests, это ожидаемая защита текущего пилота. У вас ранее были активная полная сессия и неподтверждённые пакеты Opera/StructuralUnits. Сначала завершить/разобрать их в существующем обмене, не удаляя очередь и не ставя фиктивный ACK.
directory_identity_conflict=true означает, что эта база уже является источником общего справочника под другим source_node. Настройку такого ЦО нельзя заменить магазинной регистрацией: она требует отдельного согласованного перехода источника справочника. В тестовой №50, которой временно назначали роль ЦО, этот ограничитель также может сработать. Рабочий ЦО не включать в CSV обычных магазинных баз.
Новый ключ GUID нельзя подставлять поверх старых source_node MagazyniOpera/Magazyni_PC. Пока блокировка сохраняется, HTTP-регистрацию можно проверить отдельно, но массовая смена личности базы не выполняется.

4. Реестр баз и режим просмотра

pilot.csv содержит только несекретные столбцы StoreId,Name,Server,Ref. Server и Ref заменить на реальные данные одной тестовой базы.
Для 500 баз такой CSV выгрузить из существующего реестра отправлятора; вручную 500 форм сервиса не заполняются.
На центральном компьютере нужна установленная 1С с V83.COMConnector нужной разрядности и сетевой доступ к базам. Пользователь подключений 1С вводится один раз для однородной партии. Для баз с разными учётными данными разделить партии или подключить имеющееся защищённое хранилище отправлятора.

.\Run-StoreEnrollment.ps1 -RegistryCsv .\pilot.csv -RegistrationUri $RegistrationUrl

Это только чтение: без HTTP-регистрации и записи настроек баз. Отправлятор сверит GUID каждой базы с CSV.
READY_PREVIEW означает, что подготовка разрешена. BLOCKED_EXISTING_QUEUE_OR_SOURCE означает, что нужен разбор старого обмена либо отдельная настройка источника справочника. ERROR означает сбой на указанном этапе; сообщение не содержит секретов и сырого текста исключения.
Если адреса сервисов в новой базе ещё не заполнены, передать фактические адреса из штатной формы параметрами -OperaServiceAddress и -PcServiceAddress. Это адрес подключения сервиса интеграции, а не URL InfoBases, документации или отладочной сессии. При пустых параметрах адреса уже настроенных сервисов сохраняются.
Поле ИмяПользователя в объектах настроек остаётся прежним. Если оно пустое в совершенно новой базе и требуется фоновому выполнению, определить и проверить его назначение до массового запуска; программа не подставляет туда административный пароль.

5. Применить к одному магазину

Приостановить только наши товарное задание и задание справочника, дождаться завершения их текущих запусков. Не отключать штатные задания других обменов.
Далее при READY_PREVIEW:

.\Run-StoreEnrollment.ps1 -RegistryCsv .\pilot.csv -RegistrationUri $RegistrationUrl -Apply

Скрипт:
- проверяет базу до HTTP-запроса;
- вызывает административный сервис с центрального компьютера;
- сохраняет результат в DPAPI-кэше текущего Windows-пользователя;
- проверяет выданные ключи через /auth/oidc/token;
- передаёт магазину только его результат регистрации, без административного ключа;
- задаёт GUID отправителя обоим проектам и сохраняет индивидуальные параметры двух сервисов;
- включает активность, выдерживает 21 секунду один раз после партии и проверяет записанные параметры.

SETTINGS_VERIFIED_DELIVERY_NOT_TESTED означает: запись адресов/ключа/активности и коды источников проверены, но сквозная доставка ещё не доказана.
Скрипт не включает регламентные задания, не отправляет товары и не очищает очередь. После настройки возобновить наши задания штатно и проверить один реальный пакет -> бэк -> прикладной processed -> очистка.
Указанные значения получателей по умолчанию - BackendOpera и Backend_PC, то есть согласованная центральная архитектура. Не включать несколько магазинных потребителей под ключом Backend_PC, каждый из которых умеет принимать только свой store_id.

6. Массовый запуск

После успешного пилота на одном и затем двух магазинах выполнить тот же Run-StoreEnrollment.ps1 с CSV партии и -Apply. Один исполнитель, последовательно. Не запускать две партии с одним GUID одновременно.
Кэш находится в LocalApplicationData\AstorEsbEnrollment. Он зашифрован Windows DPAPI и читается тем же Windows-пользователем на том же компьютере. При потере кэша либо смене компьютера сервер не сможет вернуть прежний секрет: требуется отдельное восстановление доступа. Потеря первого HTTP-ответа после фиксации ИС, но до сохранения DPAPI-кэша, также требует восстановления. Не удалять ИС для обхода 409.
Серверного реестра ключей нет: тип проекта допускает только один каталог. Секрет выдаётся в первом ответе и сохраняется центральным исполнителем. DPAPI-кэш необходимо сохранить под исходной учётной записью Windows. В Exch, исходники и CSV секрет не записывается.
Повтор запуска использует кэш; для уже применённого подключения возможен ALREADY_CONFIGURED. Это не тест сетевой доступности из магазина. Ротация отдельным endpoint не реализована и автоматически не выполняется.
Результат партии - CSV с GUID, именем, этапом и признаками проверок. Ключей и паролей в отчёте нет.

Границы и проверка

Кандидат рассчитан на одного последовательного исполнителя регистрации. Конкурентная регистрация одного GUID разными исполнителями требует отдельной проверки/блокировок установленной платформы и не объявляется поддержанной этим выпуском.
Создание пользователей/данных токена может иметь побочные эффекты вне транзакции каталога. Если первый запуск оборвался между созданием пользователя и записью ИС, требуется локальная административная диагностика; повтор не должен сопровождаться безусловным удалением пользователя.
Повторная регистрация возвращает 409 и членство групп не исправляет. Административное изменение членства после регистрации проверяется отдельно в Шине.
Применение двух сервисов и настройка маршрутов не объявляются одной атомарной операцией. Если часть выполнена, скрипт сохраняет этап/кэш, оставшиеся действия разбираются до возобновления заданий.
Приложения не публиковались, код в пользовательской 1С не исполнялся, сквозная доставка этими локальными проверками не подтверждена.

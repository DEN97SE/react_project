Это дополнительные обработчики, а не замена уже установленных. КХ_ОбменШиныОпера.НоменклатураПриЗаписи продолжает регистрировать обычные карточки. Подписки публикации СЕ КХ_ОбменСтруктурныхЕдиниц.* остаются отдельно: новый обработчик категории цен не публикует справочник магазинов, а запрашивает пересборку товарного каталога своей базы. Две разные подписки на одно событие с разными необходимыми обработчиками допустимы; дублирование одной связи источник/событие/обработчик не требуется.

Работа новых событий:

- Физическое удаление товара: в транзакции удаления сохраняются внутренний GUID и настоящий внешний СтроковыйИдентификатор, затем обычная delta передаёт только внешний ID удаления. Техническая запись OperaState/КХ_OperaDeleted сохраняется после первого пакета: она нужна и для старой полной сессии, чей список ещё содержит исчезнувшую ссылку.
- Если товар физически удалили до установки этой подписки и ID не сохранился, новый код не может восстановить его достоверно. Такая ссылка по-прежнему вызывает явную ошибку, вместо выдуманного удаления. Нужен реальный внешний ID из прежних данных/пакетов и отдельное восстановление.
- Переименование группы, страны, единицы, смена категории цен или кода текущей СЕ, владельца/пометки собственного склада и его физическое удаление создают один долговечный запрос новой full-сессии. Сотни тысяч маркеров внутри записи объекта не создаются. Общее задание выполнит запрос после активной сессии и запросов бэка; промежуточные массовые записи могут объединяться.
- Склад учитывает прежнего и нового владельца через пару ПередЗаписью/ПриЗаписи; подключить оба обработчика. Для СЕ также требуется пара before/after. Обычное переименование склада не меняет товарную карточку и full не запрашивает.
- Запрос массовой пересборки и ID удаления откатываются вместе с исходной записью/удалением. ОбменДанными.Загрузка используется только на точном собственном техническом наборе ОчередьШины, не на сеансе или удаляемом объекте.

Проверка:

1. При выключенных наших заданиях выполнить 02_УдаленияИМассовыеЗависимостиСПОткатом.txt. Этот тест проверяет алгоритм на фикстуре и всегда откатывает технические записи; реальный товар не удаляется.
2. Проверить реальную подписку записи группы переименованием временной группы тестовой базы в контролируемой операции: catalog_full_requested=true, revision выросла, новых сотен тысяч OperaChange нет. После завершения приёмки вернуть тестовые данные штатно.
3. Для проверки реального ПередУдалением использовать только отдельный временный товар тестовой базы с известным внешним ID и без ссылок/движений. Ни действующий товар, ни Бананы №50 физически не удалять. До включения отправителей проверить КХ_OperaDeleted и пакет delta; отмена удаления должна отменить и событие.
4. Смена категории цен своей СЕ и перенос/пометка склада проверяются в тестовой копии. Контрольные объекты/состояния возвращаются штатно либо транзакционным откатом; ошибки native Астора не обходить.

Граница покрытия: код использует подтверждённые поля текущих сборщиков. Он не обещает универсальную обработку любого нового произвольного свойства/связанного справочника после будущих изменений конфигурации. Для новой зависимости добавляется конкретный источник и проверка.

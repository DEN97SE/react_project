## Источники и адресаты

| Данные / запрос | Источник ответа | Получатели |
| --- | --- | --- |
| Справочник СЕ: первичная загрузка, создание, изменение, пометка удаления | ЦО | Opera: весь согласованный перечень; PC: сведения только о своей СЕ |
| Полный каталог одной СЕ: карточки, штрихкоды, цены, акции, остатки | Магазинная база этой СЕ | Запросивший проект: Opera или PC своего магазина |
| Текущие изменения каталога | Магазинная база этой СЕ | Оба проекта, независимо друг от друга |

Приход штатного обмена со справочником в магазин не создаёт новую авторитетную рассылку справочника. Её формирует ЦО. Новая СЕ может ещё не иметь работающего магазинного Астора: запись в справочнике сама по себе не означает готовность каталога.

«Все данные магазина» означает полный **публикуемый каталог по текущему правилу отбора**, включая все поля карточки, а не документы и все регистры Астора. Для сведений о СЕ предусмотрен отдельный запрос в ЦО.

ID СЕ в справочнике должен в точности совпадать со store_id товарных пакетов: используется существующий внешний идентификатор, новый ID для бэка не генерируется. Код и наименование могут изменяться и не служат постоянным ключом. Адреса участников Шины сопоставляются со стабильным store_id; после изменения кода СЕ маршруты необходимо обновлять согласованно.

## Справочник структурных единиц

Предлагаемый тип сообщения — `structural_units`. Поля конверта: schema_version, message_type, project, batch_id, source_id (источник ЦО), directory_epoch, directory_revision, created_at, kind=full|delta, scope_store_id, structural_units, deleted_structural_unit_ids. У full также session_id, sequence, total_batches, is_final. Версия справочника независима от source_epoch/source_revision магазинного каталога; их не сравнивают между собой.

Для Opera scope_store_id=null: full заменяет только справочник СЕ в согласованном охвате. Для PC scope_store_id равен своему store_id: full затрагивает только сведения об этом магазине. Минимальная запись: id, code, name. Адрес, тип СЕ, контакты и признаки деятельности добавляются после проверки реальных метаданных; названия таких реквизитов пока не установлены. Состав СЕ, которые представляют магазины, нужно определить по фактическим реквизитам справочника: не каждый элемент автоматически считается магазином.

Пометка удаления передаётся явно в deleted_structural_unit_ids. Снятие пометки — обычная запись structural_units с более новой версией. На бэке сохраняется версия удаления, чтобы старый повтор не восстановил магазин. Удаление СЕ делает её недоступной для использования, но не запускает безусловное физическое удаление всей истории товаров. Поздние товарные пакеты не снимают признак удаления справочника. Политика физической очистки — отдельная операция.

Если необходимо физическое удаление СЕ в 1С, её внешний ID и событие должны быть надёжно сохранены **до** удаления, в той же транзакции. Нельзя читать ID только после исчезновения ссылки. Действующие штатные подписки обмена СЕ сохраняются.

Каждый исходящий пакет имеет свой batch_id, сохраняется до прикладного ACK, повторяется с неизменным телом. Для справочника ACK содержит message_type=ack, dataset=structural_units, project, source_id, batch_id, status=processed|error. Он требует отдельной диспетчеризации: существующий товарный ACK проверяет store_id и не подходит для справочника ЦО без доработки. Подтверждение одного получателя не подтверждает остальных.

Первично справочник доставляется до публикации соответствующего каталога. Если товарные пакеты пришли раньше, бэк надёжно сохраняет их во временное хранилище и запрашивает сведения о СЕ; неизвестный store_id нельзя подменять текущим магазином или создавать с выдуманными реквизитами.

## Полный каталог по запросу бэка

Предлагаемое сообщение для маршрута **бэк → Шина → Астор нужного магазина**:

```json
{
  "schema_version": 1,
  "message_type": "catalog_full_request",
  "project": "pricechecker",
  "request_id": "edc09838-c86b-4b45-bd24-bf12072f820a",
  "store_id": "3370588b-0742-11e0-b9c1-001a64c3f566"
}
```

Для Opera project=opera. Один запрос относится к одному магазину и одному проекту; второй проект из-за этого запроса не перезагружается. Обычная автоматическая delta продолжает поступать обоим. Массовое восстановление Opera — серия отдельных запросов с ограничением одновременных выгрузок, а не широковещательный запрос ко всем базам.

store_id обязателен; request_id — UUID. JSON не является основанием авторизации. Доступ участника к проекту/магазину проверяется маршрутом и учётными данными Шины, затем в Асторе дополнительно сверяется store_id с текущей СЕ. Отправитель PC может запрашивать только свой магазин. Клиент не задаёт произвольный адрес получателя ответа в JSON.

Приём запроса выполняет короткую транзакцию: проверяет входные поля и повтор, сохраняет запрос и регистрирует ответ о принятии. Сборку всех карточек внутри входящего обработчика не выполняют. Фоновое задание запускает/продолжает full после фиксации запроса, даже если сеанс приёма завершился или сервер перезапустился.

Предлагаемый ответ — catalog_full_request_result, содержащий project, store_id, request_id, свой batch_id, status и session_id при accepted. Возможные статусы: accepted, busy, wrong_store, invalid_request, error. Ответ также надёжно доставляется и подтверждается прикладным ACK по его batch_id. accepted означает принятие к обработке, не завершение загрузки бэка.

Для ключа project + store_id + request_id сохраняется журнал результата. Повтор идентичного запроса возвращает прежний результат/session_id и не запускает вторую выгрузку, в том числе после завершения первой. Повтор request_id с изменённым содержимым отклоняется. Если выполняется другая полная сессия, возвращается busy без принятия второй; повтор того же busy-запроса остаётся busy. Для новой попытки после освобождения нужен новый request_id. До определения срока хранения журнала автоматическое удаление записей дедупликации не включается.

Ответный каталог использует прежние products, kind=full, session_id, sequence, total_batches, is_final, source_epoch/source_revision и дополнительно исходный request_id во всех порциях. Каждая порция имеет собственный batch_id и ACK. Не следует привязывать запрос только к транспортному ID Шины: при повторной отправке он может измениться.

Бэк собирает сессию отдельно от действующего каталога. Получение is_final не гарантирует получения остальных номеров. Переключение выполняется после получения всех порций и учёта delta с более новыми версиями; исчезнувшие из полного состава товары снимаются только для указанного store_id. Пустой успешный full — один финальный пакет с products=[]; это полноценный пустой каталог. Ошибка связи или ошибка сборки не превращаются в пустой успешный full.

При недоступности магазинной базы Шина сохраняет запрос согласно политике доставки; бэк показывает ожидание/таймаут, продолжает обслуживать последнее сохранённое состояние. Запрос только справочника СЕ не может восстановить цены и остатки этого магазина.

## Запрос справочника в ЦО

Предлагаемый тип — structural_units_request, поля schema_version, project, request_id и scope_store_id. Opera может запросить весь справочник (scope_store_id=null) либо одну СЕ. PC запрашивает только собственную СЕ. Ответ — structural_units с request_id, нужным scope_store_id и теми же правилами полной сессии, версий, дедупликации и подтверждений. Это другой маршрут в ЦО, а не каталоговый запрос в магазинную базу.

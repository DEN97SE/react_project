Разбор предложения «Прайс-чекеры и 1С:Шина: адресная доставка по магазинам».
27.10.2026. Это анализ и план перехода, не установленное изменение маршрутов.
Источник: предоставленный пользователем PDF, 6 страниц; сопоставлен с текущими общими модулями.

Рекомендация

Для описанной в PDF схемы, в которой магазинные бэки сами подключаются к Шине, подходит отдельная информационная система и отдельные учётные данные каждого бэка. Товарные пакеты следует адресовать только нужному магазину.
Выбираем вариант А: КодПолучателя задаёт 1С. Это свойство уже заполняет наш отправитель, новый транслятор только для адресации не нужен.
Однако обратную адресацию и публикацию общего справочника из предложения нужно дополнить. Существующие неподтверждённые пакеты нельзя просто перевести на другого получателя.

Что установлено, а что пока является утверждением предложения

В нашем коде товарный получатель PC сейчас Backend_PC, отправитель текущего тестового магазина Magazyni_PC. Отправка уже использует Сообщение.КодПолучателя из сохранённой строки очереди.
Общий справочник StructuralUnits для PC отдельно адресован центральному Backend_PC. Это явно выбранный режим публикации всех магазинов, а не случайная адресация товара.
В PDF утверждается, что разные магазинные бэки используют один ключ и читают одну очередь Backend_PC. Их подключения ассистент не проверял. Если это так, несколько потребителей одной очереди могут конкурировать за сообщения разных магазинов.
Оценка (N-1)/N относится к вероятности попадания не тому потребителю при условии равномерного распределения. Она не доказывает такую долю необратимых потерь: результат зависит от settlement/reject, повторной доставки, очереди недоставленных и прикладных ACK.
Наш исходящий пакет без processed остаётся в 1С и повторяется. Поэтому счётчик доставки Шины, фактическое сохранение в магазине и удаление строки 1С нужно различать.

Целевая схема товаров

Для магазина №50:
store_id = 3370588b-0742-11e0-b9c1-001a64c3f566.
Бэкенд магазина: код информационной системы равен этому UUID; член группы BackendPriceChecker; собственные ключ и очередь.
Источник 1С: свой код, например astor_pc_3370588b-0742-11e0-b9c1-001a64c3f566; член группы MagazinyPriceChecker; собственные учётные данные подключения.
Префикс astor_pc_ приведён как предлагаемый стандарт именования, не как уже созданный участник.

Доставка:
база 1С магазина -> ExchPriceChecker -> FromShops -> ToShops -> бэкенд с кодом store_id.
КодПолучателя сообщения = store_id. В теле JSON store_id тот же.
source_node нового пакета = уникальный код источника этой базы 1С.

Ответ:
бэкенд store_id -> FromBackend -> ToBackend -> source_node исходного пакета.
ACK содержит исходные store_id, batch_id и status=processed после устойчивого сохранения всего пакета.
Повтор batch_id повторно подтверждается без повторного бизнес-эффекта. При применении данных учитываются epoch и числовая revision.

Для 500 отдельных баз 1С нельзя оставить один общий получатель Magazyni_PC для ACK всех магазинов: несколько подключений к одной очереди могут забрать ответы друг друга. Нужны отдельные участники 1С либо один реальный центральный приёмник с собственным распределением ответов по базам.
В пилоте с одной базой 1С можно временно сохранить Magazyni_PC. Это не схема масштабирования на все базы.
Аналогичный принцип потребуется для обратных сообщений Opera, если все магазинные базы напрямую подключаются под одним участником Opera.

Число объектов

Количество сервисов интеграции в каждой базе остаётся два: Opera и PC. По сервису на каждую удалённую очередь в одной базе создавать не требуется.
Для 500 независимых бэков нужны примерно 500 участников-получателей в группе BackendPriceChecker.
Если 500 баз 1С независимо принимают ACK, нужны также отдельные участники-источники в группе MagazinyPriceChecker.
Группы в процессе могут оставаться общими, число групп не обязано равняться числу магазинов.
UUID из 36 символов укладывается в наш ограничитель кодов до 50. Вместимость и допустимые символы именно поля кода информационной системы Шины нужно подтвердить созданием первого участника.

Что остаётся общим

Каталог магазинов публикует выбранный ЦО в центральные приёмники: Opera -> BackendOpera, PC -> Backend_PC либо другой явно выделенный участник центра.
Магазинные потребители не используют ключ центрального Backend_PC.
Не следует удалять Backend_PC из процесса автоматически после перевода товаров, как предлагается в PDF: сейчас на него адресован общий справочник магазинов. Сначала сохранить этот поток либо отдельно согласовать замену его центрального получателя.
Полный список всех магазинов нельзя перенаправить в товарную очередь одного магазина только потому, что у неё появился UUID.
Если центру нужно раздать карточки магазинов дальше локальным бэкам, это отдельная функция центра или отдельный режим адресной публикации. Наш текущий общий список не превращается автоматически в 500 независимых публикаций.

Что потребуется изменить в нашем коде и настройках

1. Для каждой базы настроить явный PC-маршрут: уникальный код источника 1С -> UUID бэка своего магазина. Сам механизм пары Opera/PC, сбор карточек и JSON товаров менять ради этого не требуется.
2. ExchPriceChecker каждой базы авторизовать как её участника-источника. Ключ бэка магазина используется бэком, а не магазинной 1С.
3. Перед записью нового товарного PC-пакета проверять, что целевой UUID соответствует его store_id в выбранном режиме адресной доставки. Не распространять это правило на общий StructuralUnits, у которого другая область и получатель.
4. При товарном ACK дополнительно сверять реального Сообщение.КодОтправителя с получателем сохранённого пакета. Сейчас товарный ACK проверяет store_id, batch_id и статус, но фактический отправитель в эту ветку не передаётся. У ACK справочника проверка отправителя уже есть.
5. catalog_full_request должен приходить от UUID бэка своего магазина. Текущий обработчик уже сравнивает отправителя с настроенным PC-получателем; после корректной перенастройки это будет UUID.
6. Бэк адресует ACK и запросы восстановления соответствующему источнику 1С. Для ACK источник можно взять из source_node принятого пакета; для самостоятельного запроса после перезапуска бэк должен иметь сохранённое сопоставление магазина и источника.
7. Зафиксировать договорённость об адресате ACK на стороне бэка. Нельзя заменить source_node в уже сохранённых телах на новый код при очередной отправке.

Миграция существующей очереди

Процедура НастроитьМаршрутПрайсЧекеров сейчас намеренно запрещает смену маршрута при активной full-сессии, неподтверждённых PC-пакетах и ожидающих запросах PC.
Поэтому нельзя сейчас без подготовки выполнить замену Backend_PC на UUID. Ограничения не следует отключать ради перехода.

Предпочтительный порядок:
1. Завершить текущую проверку разделения сервисов и получить подтверждённую доставку пилотного пакета по существующему маршруту.
2. Создать участников и ключи для одного тестового магазина, проверить членство в группах. Затем подготовить второй магазин для проверки разделения очередей.
3. Инвентаризировать действующую full-сессию, незавершённые запросы и неподтверждённые PC batch_id. Завершить подготовку старой сессии и обработку старых пакетов через прежний адрес.
4. На период завершения старой общей очереди оставить одного контролируемого получателя Backend_PC, который сохраняет/распределяет данные в правильный магазин и подтверждает исходные batch_id. Иначе несколько старых конкурирующих потребителей сохранят прежнюю проблему.
5. Когда ограничители позволят смену, приостановить наше товарное задание. Отметки изменений могут продолжать накапливаться. Сохранить старую конфигурацию и заполнить новый маршрут своего магазина и соответствующие настройки сервиса.
6. Возобновить задание. У новых пакетов адресат UUID и правильный source_node; Opera сохраняет свой маршрут. При необходимости начать один новый full по обычной процедуре после завершения старой сессии.
7. Провести пилот на двух магазинах, затем подключать остальные партиями.

Если старые пакеты невозможно завершить, нужен отдельный контролируемый план миграции с учётом каждого batch_id и фактического сохранения бэком. Простая правка получателя/JSON, удаление очереди, сброс эпохи или принудительное processed не заменяют такой план.

Приёмка на двух магазинах

- Пакет А получает только бэк А, пакет Б только бэк Б. Проверить на стороне реальных подключений, а не только счётчик Шины.
- Отключённый бэк А не мешает Б; пакет А сохраняется до подключения/повтора и подтверждается после обработки.
- ACK возвращается в свою базу 1С; чужой отправитель/магазин не подтверждает пакет.
- Запрос полного каталога от А создаёт ответ только А; request_id сохраняется во всех его порциях.
- Повторное сообщение не дублирует бизнес-эффект, но получает ACK.
- Пустой или неизвестный адресат вызывает явную ошибку/контроль недоставленных, а не неявную широкую рассылку.
- Справочник всех магазинов по-прежнему доходит в центральный приёмник независимо от товарных маршрутов.

Автоматическое создание участников

В PDF HTTP-сервис и операции выдачи ключа, членства в группе и отзыва описаны как проект решения; часть API там прямо отмечена как непроверенная.
Наличие объекта ИнформационныеСистемы и метода токенов пользователей ещё не доказывает, что их вызов полностью повторяет кнопку «Выдать ключ API» с нужными правами и членством.
Сначала в проекте и документации установленной версии Шины проверить поддерживаемые операции создания участника, выдачи ключа, включения в группу, ротации и отзыва. Работоспособность предложенных URL и методов по PDF не подтверждена.
Не использовать внутренний RPC интерфейса как доказанный стабильный API.

Первый пилот можно завести вручную. Для 500 магазинов затем нужен поддерживаемый массовый регламент или автоматизация, если API подтвердится.
Автоматизацию размещать в управляющем центре/проекте Шины. Создание обычной карточки СЕ должно сохранять запрос подключения в отдельную устойчивую очередь работ, а не синхронно создавать ключи по сети внутри транзакции записи магазина.
Карточка магазина и активный магазинный бэк - разные сущности: нужны явные состояния «создан», «участник готов», «ключ настроен», «проверено», «активен».

Контракт POST должен быть идемпотентным по store_id и различать создание и явную ротацию. Если ключ уже создан, а HTTP-ответ потерян, повтор не должен выдавать новый ключ молча. Нужно заранее определить восстановление результата/безопасную доставку секрета.
Не обещать возврат прежнего client_secret, если платформа показывает его только один раз. Секреты не записывать в сообщения справочника, исходящие товарные JSON и общедоступные журналы.
Удаление/пометка карточки СЕ не должны немедленно отзывать подключение с неподтверждёнными пакетами: сначала прекратить новую публикацию, завершить/разобрать доставку, затем деактивировать участника по согласованному процессу.
Заявленный в PDF DELETE до исследования API остаётся эскизом, не готовой реализацией.

Часы

Опережение created_at на 15 секунд само по себе не доказывает причину: сравнивать UTC и синхронизацию времени сервера 1С, Шины и бэка. Это отдельная эксплуатационная проверка. Для защиты порядка данных используются epoch и revision, не только created_at.

# Автоматическая регистрация цены и остатка для Оперы

Сценарий рассчитан на тестовую базу магазина «Командор №50». Доставка вручную созданного пакета в Шину уже подтверждена пользователем; теперь проверяется другое: запись источника сама создаёт отметку, а регламентное задание превращает её в пакет и отправляет.

В актуальном КХ_ОбменШиныОпера уже существуют обработчики НаборЗаписейПередЗаписью(Источник, Отказ, Замещение) и НоменклатураПриЗаписи(Источник, Отказ). Для первых двух подписок менять код модуля не требуется. Не подключать обработчик ко всем регистрам: выбрать только два указанных набора записей.

## 1. Подготовка

1. Временно выключить только наши задания подготовки/отправки дельт, чтобы они не успели удалить отметку OperaChange до проверки. Обработку транспорта Шины останавливать для этого не требуется. Проверить, что никакой другой запуск того же обработчика не работает параллельно.
2. Использовать один товар, например «Бананы 1кг», штрихкод 2804496. Все правки документов выполнять в тестовой копии.
3. До изменения выполнить 01_ПроверитьОтметкуТовара.txt через кнопку «На сервере». Сохранить текущие price.value, stock.quantity и JSON отметки, если она уже есть. Существующие пакеты и OperaState не удалять.

## 2. Две подписки в конфигураторе

Конфигурация → Общие → Подписки на события → Добавить. Если такая привязка источник/событие/обработчик уже существует, использовать её, а не создавать дубликат.

| Свойство | Подписка цены | Подписка остатка |
|---|---|---|
| Имя | КХ_ОпераЦеныПередЗаписью | КХ_ОпераОстаткиПередЗаписью |
| Источник | РегистрСведенийНаборЗаписей.ЦеныНоменклатуры | РегистрНакопленияНаборЗаписей.ПартииНоменклатуры |
| Событие | ПередЗаписью | ПередЗаписью |
| Обработчик | КХ_ОбменШиныОпера.НаборЗаписейПередЗаписью | КХ_ОбменШиныОпера.НаборЗаписейПередЗаписью |
| Комментарий | semidockij - 22.10.2026 - Автоматическая регистрация цены для Оперы | semidockij - 22.10.2026 - Автоматическая регистрация остатка для Оперы |

В источнике выбирается именно набор записей конкретного регистра, не документ, менеджер регистра и не РегистрСведений.ОчередьШины. Общий модуль серверный. Для обработчика выбрать уже существующую экспортную процедуру, сигнатура которой указана выше.

Выполнить проверку синтаксиса, обновление конфигурации базы (F7), перезапустить сеанс. Подписки входят в конфигурацию; настройки регламентного задания и его расписание проверяются отдельно.

## 3. Цена: подтверждение события, отдельно от таймера

1. При выключенном отправителе выполнить сценарий 01 и записать исходное значение.
2. Штатным документом Астора изменить цену только тестового товара. Записать/провести документ так, чтобы запись действительно попала в РегистрСведений.ЦеныНоменклатуры. Выбрать текущую СЕ, её КатегорияЦенРозницы и базовую единицу товара. Период новой цены должен уже наступить; будущие цены проверяются отдельно.
3. Снова выполнить сценарий 01. Карточка должна содержать новую price.value. Отметка OperaChange должна появиться или иметь новый revision, если отметка уже была. Простое наличие старой отметки без изменения её содержимого не подтверждает срабатывание подписки.
4. В строке отметки идентификатор объекта — GUID тестовой номенклатуры, узел — КХ_OperaChange, канал пустой. СтроковыйОбъект содержит nomenclature_guid и revision. Это отметка для сборщика, а не готовый JSON карточки.
5. Выполнить 02_ПодготовитьДельту.txt один раз. Открыть новый пакет Opera в ОчередьШины: kind=delta, новый batch_id, увеличившийся source_revision, актуальная карточка с новой ценой. При очереди больше 200 отметок товар может попасть в один из следующих проходов; его отметка остаётся до обработки.

В этом тесте нельзя заменять реальное изменение ручным вызовом ЗарегистрироватьНоменклатуру. Регламентный метод с таймером также не использовать вместо проверки отметки: таймер способен зарегистрировать наступившую цену и тем самым скрыть отсутствие подписки.

Если новая цена есть в регистре, но в карточке прежнее значение — проверить СЕ, категорию, единицу, период и фактическую последнюю запись. Если документ не записывается из-за обработчика — прислать полный стек ошибки; проверку транзакции в модуле не отключать. Если источник изменён, а отметка не появилась/не обновилась — проверить привязку подписки и точку останова в НаборЗаписейПередЗаписью.

## 4. Остаток: подтверждение движения и отмены

1. При выключенном отправителе снова выполнить 01 и записать stock.quantity.
2. Создать/провести тестовый приход или списание выбранного товара по складу текущей СЕ. Проверить движения документа именно по ПартииНоменклатуры и изменение суммарного остатка по складам СЕ. Перемещение между двумя складами одной СЕ может сохранить суммарный остаток и не подходит для первой проверки изменения количества.
3. Сценарием 01 проверить обновление OperaChange и новое stock.quantity. Другие движения в базе могут менять итог одновременно; сравнивать с учётом Астора за тот же момент.
4. Сценарием 02 собрать дельту, проверить stock.quantity в карточке. Остаток передаётся абсолютным значением, а не величиной движения документа.
5. Отменить проведение только созданного тестового документа. Если из набора убираются все строки, отметка всё равно должна обновиться: обработчик читает старые строки при замещении. Проверить возврат stock.quantity и новую дельту. Это отдельная важная проверка: подписка только по новым строкам пропустила бы отмену движения.

## 5. Автоматическая подготовка и отправка

После успешной проверки двух подписок включить задание Оперы:

| Свойство | Значение |
|---|---|
| Имя | КХ_ОбработкаОчередиОпера |
| Имя метода | КХ_ОбменШиныОпера.РегламентнаяОбработкаОчередиОпера |
| Предопределённое | Да, если создаём новое автоматически создаваемое задание |
| Использование | Да |
| Расписание | Повтор каждые 10 секунд для начала теста |
| Комментарий | semidockij - 22.10.2026 - Подготовка и отправка изменений Оперы |

Если уже есть отдельное задание с этим методом, настроить его. Задание ПрайсЧекеров оставляется отдельным: его метод не является обработчиком очереди Оперы. Изменения метаданных сохранить, проверить синтаксис и применить F7; убедиться, что экземпляр задания создан и включён в базе.

На тестовой копии может действовать общая блокировка регламентных заданий на уровне кластера. Если задание не стартует, проверить статус, время последнего/следующего запуска и блокировку; одна галочка Использование не обходит общую блокировку. Включение всех заданий копии может затронуть другие обмены; рабочую настройку согласовывать для изолированной тестовой базы, не разблокировать весь набор автоматически.

Процедура уже готова: регистрирует наступление периодов цен/акций/будущих движений, собирает дельту и отправляет пакеты. В актуальном исправленном методе немедленного ОстановитьОбработку нет. Период задания 10 секунд не является гарантией доставки за 10 секунд; проверять фактическую задержку и длительность выполнения.

Повторить изменение цены и затем остатка по одному товару. Теперь не вызывать вручную ни регистрацию, ни ПодготовитьДельту, ни регламентный метод. После успешного прохода задания должен появиться новый пакет с нужным товаром, а счётчик входящих Шины — увеличиться. Для проверки данных смотреть СтроковыйОбъект в ОчередьШины Астора, а внутри Шины — перехват новой отправки в отладке схемы, как подтвердил пользователь. Веб-таблица каналов показывает счётчики; просмотр JSON через неё не обещается.

Отсутствие OperaChange при работающем задании не означает пропуск: сборщик мог уже перенести изменение в пакет. Искать пакет по номенклатуре, версии и времени регистрации. Рост счётчика Шины сам по себе не доказывает получение именно изменения: возможны повторы старых batch_id без ACK.

Пока бэк не подтверждает обработку, Sent допускает повторную отправку через 300 секунд с тем же batch_id и JSON. Поэтому конечная приёмка — новая карточка с новой версией и новым batch_id, а не только увеличение числа сообщений. Нагрузка от повторов и размер очереди требуют наблюдения до подключения бэка.

## 6. Критерии прохождения и следующие источники

1. Реальное изменение текущей цены создало/обновило отметку без вызова регистрации из консоли.
2. Реальное движение остатка создало/обновило отметку.
3. Отмена тестового движения также создала/обновила отметку и вернула актуальный остаток.
4. При включённом задании новая карточка сама появилась в пакете и поступила в Шину, с измеренной задержкой.
5. При откате транзакции документа отметка не фиксируется отдельно. Этот сценарий проверяется отдельно управляемым отказом записи в тестовой базе, не принудительным завершением сеанса в рабочей.

После этих тестов подключить оставшиеся источники карточки: Номенклатура/ПриЗаписи → НоменклатураПриЗаписи; ШтриховыеКоды, РекламныеАкцииЦены, ЗначенияСвойствОбъектов, ЗначенияСвойствТоваров / ПередЗаписью набора → НаборЗаписейПередЗаписью. Эти подписки имеют отдельные сценарии проверки. Будущая цена и цена с периодом сегодня в прошлом проверяются раздельно: первая должна попасть в актуальную карточку при наступлении времени, вторая — сразу после записи.

Документ подготовлен по присланным исходникам. Сами подписки, расписание и сценарии в удалённой базе ассистент не выполнял; результат нужно подтвердить на тестовой базе пользователя. Код рабочих модулей для этой настройки не изменялся.

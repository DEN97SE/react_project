# Покрытие изменений карточки по ТЗ

Основание: пункты 2, 3 и 5 исходного «ПЗ Шина» от 14.08.2026. Пользователь позднее уточнил актуальную архитектуру: остатки уже нужны; Опера получает full и delta, ПрайсЧекеры запрашивают свежую карточку своего магазина. Эти указания имеют приоритет над старым MVP-документом. Описанные подписки обслуживают дельты Оперы, а не фоновую рассылку каталога ПрайсЧекерам.

Прямое требование пункта 3: «При любом изменении данных (смена цены, добавление/снятие акции, редактирование карточки товара, изменение штрихкода) ... отправлять ... полный обновленный пакет ... Backend должен получить все поля карточки целиком». В критериях приёмки отдельно указаны изменения «цены, акции или свойств номенклатуры».

## Что требуется подключить

Вариант текущего механизма: любая запись карточки товара регистрирует эту номенклатуру; любая запись значений её свойств в двух перечисленных регистрах также регистрирует товар. Произвольные свойства не добавляются автоматически в JSON: сборщик формирует согласованные поля полной карточки. При записи свойств другого типа объекта обработчик пропускает их по типу ссылки.

| Источник | Событие | Обработчик | Роль/статус |
|---|---|---|---|
| СправочникОбъект.Номенклатура | ПриЗаписи | КХ_ОбменШиныОпера.НоменклатураПриЗаписи | Изменения реквизитов товара: наименование, страна, состав, базовая единица, родитель, пометка удаления |
| РегистрСведенийНаборЗаписей.ШтриховыеКоды | ПередЗаписью | КХ_ОбменШиныОпера.НаборЗаписейПередЗаписью | Добавление, изменение и удаление штрихкодов/упаковок |
| РегистрСведенийНаборЗаписей.ЦеныНоменклатуры | ПередЗаписью | Тот же | Уже проверено пользователем на одном товаре |
| РегистрСведенийНаборЗаписей.РекламныеАкцииЦены | ПередЗаписью | Тот же | Запись/замена/снятие акции; наступление границ периода обрабатывает также таймер |
| РегистрСведенийНаборЗаписей.ЗначенияСвойствОбъектов | ПередЗаписью | Тот же | В текущем сборщике здесь читается производитель; здесь же могут храниться другие свойства карточки |
| РегистрСведенийНаборЗаписей.ЗначенияСвойствТоваров | ПередЗаписью | Тот же | В текущем сборщике здесь читаются значения КБЖУ |
| РегистрНакопленияНаборЗаписей.ПартииНоменклатуры | ПередЗаписью | Тот же | Уже проверено пользователем на одном движении остатка |

Для двух регистров свойств подписка на саму Номенклатуру недостаточна: форма или обмен могут записать набор значений свойств отдельно от объекта справочника. Общий обработчик уже поддерживает колонку Объект: берёт ссылки именно типа СправочникСсылка.Номенклатура. При замещении набора собирает товары из старых и новых строк. Это необходимо также для удаления значения свойства или переноса записи на другой товар. Внутри записи источника сохраняется отметка, а полная карточка собирается фоновым заданием.

## Незавершённые требования и зависимости

1. Наименование для ценника/этикетки. Источник подтверждён новым выводом пользователя: предопределённое свойство СвойстваОбъектов.НаименованиеДляЦенника, значение в РС ЗначенияСвойствОбъектов. Правка сборщика реализована 22.10.2026: заполненное ценниковое имя используется в name; при отсутствии записи, пустом или пробельном значении — обычное Наименование. Нужна проверка в базе на различающихся именах и fallback. Порядок — Исправления_20261022/НаименованиеДляЦенника/Установка_и_проверка.md.
2. Свойство «Категория товара» = «Собственное производство» в ТЗ предназначено для условий следующих этапов и не передаётся в MVP. Текущий category содержит наименование родительской группы номенклатуры; это другое значение. Не подменять им признак собственного производства.
3. Изменения общих справочников могут менять карточки без записи самих товаров: переименование родительской группы, единицы, страны; изменение значения-ссылки, используемого как производитель. Семь указанных подписок не обеспечивают каскадную регистрацию всех зависимых товаров для этих событий. Например, запись группы Номенклатура сейчас отмечает саму группу, а сборщик группы пропускает, поэтому переименование группы не переотправит её товары. Нужны отдельные обработчики выбора зависимых товаров или согласованная полная перевыгрузка. В этом обзоре такой механизм не реализован.
4. Изменение категории розничных цен самой СЕ, состава/принадлежности складов может затронуть множество карточек. Это тоже отдельная массовая зависимость; подписок на строки цены/движения недостаточно.

Следовательно, нельзя заявлять, что любые изменения всех зависимых справочников уже покрыты. Две проверенные подписки подтверждают только цену и остаток; остальные пять и источники обязательных полей надо настроить и проверить отдельно.

## Проверки новых подписок

Использовать тот же подход, что уже прошёл для цены и остатка: временно выключенный сборщик, сценарий 01 до/после реальной записи, появление или обновление revision, затем сборка новой полной карточки. При включённом задании проверять новый пакет, поскольку отметка может быстро исчезнуть после обработки. Не вызывать ЗарегистрироватьНоменклатуру вручную для подтверждения подписки.

- Записать новый состав у тестового товара: отметка обновляется, composition содержит новое значение. Отдельно очистить состав и проверить актуальную полную карточку.
- Изменить одно КБЖУ, например белки с 1.50 на 1.60: отметка обновляется через ЗначенияСвойствТоваров, nutrition.proteins в новой карточке меняется.
- Изменить нужное свойство из ЗначенияСвойствОбъектов: отметка обновляется даже при отдельной записи этого регистра. Для производителя проверить manufacturer; для свойства вне JSON проверить регистрацию, не ожидая нового произвольного поля в контракте.
- Добавить/удалить один тестовый штрихкод: отметка и полный массив barcodes актуальны после каждой операции.
- Записать/изменить/снять тестовую акцию: отметка и promos соответствуют текущему состоянию. Наступление будущего начала/окончания проверять отдельно.
- После установления источника наименования для ценника исправить сборщик с пометкой semidockij, затем проверить изменение именно этого поля; изменение обычного Наименования не является доказательством выполнения требования к ценнику.

Код рабочих модулей в рамках этого обзора не изменялся. Сценарий поиска источников на платформе 1С ещё не выполнялся. Новые подписки и перечисленные сценарии требуют проверки пользователем в тестовой базе.

## Уточнение по скриншоту формы

Пользователь нашёл элемент ПВХ «Наименование для ценника». Для получения его GUID и значения по товару использовать более узкий сценарий `04_НаименованиеДляЦенника.txt`. Существование характеристики подтверждено; источник и значение по конкретному товару требуется получить. Общая диагностика 03 также исправлена: два отдельных запроса без представлений, объединения и сортировки.

## Уточнение: предопределённое свойство и резервное наименование

Пользователь подтвердил, что «Наименование для ценника» является предопределённым элементом ПВХ СвойстваОбъектов. GUID для обращения к нему не требуется: использовать точное имя предопределённых данных, как уже используется Производитель в сборщике. В присланных BSL-исходниках точное внутреннее имя этого элемента не найдено; отображаемое наименование не доказывает написание внутреннего имени. Сценарий 04 теперь выводит ИмяПредопределенныхДанных вместе с местом хранения значения.

Пользователь согласовал fallback: если свойство/его значение отсутствует или значение пустое/состоит из пробелов, name берётся из обычного Номенклатура.Наименование. При непустом значении используется наименование для ценника. Сборщик пока не изменён: требуется подтвердить внутреннее имя и регистр значения.

# Контракт каталога: общий бэк Opera и магазинные бэки ПрайсЧекеров

Актуальное требование от 23.10.2026: 500 источников Астора, одна общая база Opera, 500 баз PC. Обе системы получают первичный full и последующие delta. 26.10.2026 пользователь подтвердил приём и разбор одной карточки бэком PC после прямого теста 16. Штатная очередь и реальные ACK ещё не проверены. Новая подготовленная редакция от 26.10.2026 добавляет отдельную сохраняемую адресацию PC; её установка в базу ещё не подтверждена.

Подготовлен отдельный исходящий справочник structural_units с собственными версиями и ACK. Его фактический контракт: [ПубликацияСЕ/Контракт.md](Исправления_20261023/ПубликацияСЕ/Контракт.md). Товарный ACK ниже сохраняет прежний формат; справочник требует dataset=structural_units и возвращается на source_node ЦО. Новый тип ещё не проверен с бэком/Шиной. Обработка запросов full от бэка пока не реализована.

Справочник СЕ из ЦО и восстановление каталога конкретного магазина по запросу бэка описаны в [Контракт_справочника_и_запросов.md](Контракт_справочника_и_запросов.md). Эти новые входящие запросы ещё не поддержаны кодом; обычный full ниже запускается в 1С, а не новым сообщением из бэка.

## Два потока

| Получатель | project в JSON | ТипСообщения в заголовке | Внешняя система очереди |
| --- | --- | --- | --- |
| Общий бэк Opera | opera | OperaProducts | Opera |
| PC-бэк своего магазина | pricechecker | PriceCheckerProducts | PriceCheker |

Оба потока имеют message_type=products и одинаковые карточки/удаления одной сборки. batch_id разные; попытки и ACK независимы. Оба пакета одной порции регистрируются в общей транзакции. session_id/sequence и source_revision для соответствующих full-порций одинаковые. Дедупликация и полные сессии разделяются по project и store_id.

Сканирование PC читает локальную базу своего бэка. Новый full/delta не использует request_id. Старый lookup/lookup_result оставлен совместимым техническим интерфейсом с ТипСообщения=PriceCheckerResponse для ответа; он не является требуемым путём сканирования.

## Пакет

Обязательные поля: schema_version=1, message_type=products, project, batch_id, store_id, store_code, source_epoch, source_revision, created_at, kind=full|delta, products, deleted_nomenclature_ids. В новые PC-пакеты редакции 26.10.2026 также добавляется source_node — зафиксированный код отправителя PC для обратного ACK. Дополнительное поле необходимо принять в модели бэка, если она ограничивает состав JSON. У товарного Opera это поле не добавляется этой правкой.

Full также содержит session_id, sequence (от 1), total_batches, is_final. Пустой состав даёт один финальный full с products=[]; это осознанное пустое состояние магазина. is_final не доказывает получения остальных номеров. На диагностике магазина №50 20 304 позиции: при размере200 получится 102 порции на получателя.

Пример delta (карточка сокращена только в этом примере):

```json
{
  "schema_version": 1,
  "message_type": "products",
  "project": "pricechecker",
  "batch_id": "UUID_ЭТОГО_ПАКЕТА_PC",
  "store_id": "3370588b-0742-11e0-b9c1-001a64c3f566",
  "store_code": "123",
  "source_epoch": "ЭПОХА_ЭТОЙ_БАЗЫ",
  "source_revision": "14",
  "created_at": "2026-10-23T05:00:00Z",
  "kind": "delta",
  "products": [],
  "deleted_nomenclature_ids": ["ID_ТОВАРА_СНЯТОГО_ИЗ_КАТАЛОГА"]
}
```

Формат карточки сохраняется: nomenclature_id, name, base_unit, country/manufacturer/category/composition при наличии, nutrition, price при наличии, barcodes, promos, stock. name выбирается из НаименованиеДляЦенника, иначе из обычного имени; приоритет и fallback подтверждены пользователем. Сумма/количество — десятичные строки, даты UTC. Цена базовой единицы не пересчитывается по упаковке. Штрихкод — строка, включая ведущие нули.

Полная карточка заменяет прежнюю. Отсутствующее price снимает старую цену и не превращается в 0; UI решает, как показать недоступную цену. barcodes=[] снимает старые штрихкоды; promos=[] снимает акции; stock.quantity=0 обнуляет остаток, количества не складывают. Отрицательное количество не разрешает продажу. Нет возможности сканирования карточки без штрихкода не означает удаление GUID-карточки из каталога.

## Правило состава и снятия

Включаются непомеченные элементы без групп: Активный в назначенных текущему магазину матрицах ИЛИ ненулевой остаток по складам магазина. Закрытый в назначенных матрицах исключается даже при остатке, в том числе при конфликте статусов. Пассивные с остатком пользователь подтвердил как продаваемые. Пробный/Сезонный/Утвержденный не приравниваются к Активный; возможность продажи отдельно не установлена, хотя общая ветка остатка может включить их в диагностический состав.

deleted_nomenclature_ids означает снять карточку из каталога конкретного магазина. Причина может быть пометкой удаления, закрытием или выходом из отбора. Удаление неизвестного/уже удалённого ID идемпотентно. При восстановлении статуса/остатка приходит обычная полная карточка с более новой версией.

## Ключи и версии

В общем бэке Opera ключ карточки/цены/остатка — store_id + nomenclature_id. Один GUID номенклатуры может встречаться в нескольких магазинах с разными ценами и остатками. Полная сессия магазина изменяет только этот store_id. PC-бэк проверяет свой store_id и не сохраняет карточки другого магазина.

source_revision — целое число, переданное строкой; сравнивать численно, не лексикографически. Версию хранить для каждого товара и его удаления в рамках store_id и source_epoch. Последнее пришедшее сообщение не обязательно самое новое. Удаления тоже сохраняют версию, иначе старый повтор воскресит товар. Повторную доставку уже обработанного batch_id завершать повторным ACK без повторного бизнес-действия.

source_epoch сохраняется в основной OperaState. Не сбрасывать её/счётчик при чистке очереди. После восстановления или замены источника смена эпохи требует согласованного полного восстановления. Тестовая копия работает с тестовыми участниками/данными.

Full собирается по порциям, не является единой транзакционной фотографией всей базы. Перед переключением полной сессии получить все sequence, учесть delta с более новыми версиями и удаления. Не очищать всю общую таблицу Opera по приходу одного full-пакета. is_final может прийти раньше других. ACK порции означает, что она надёжно сохранена/обработана получателем; полный каталог публикуется после корректного завершения всей сессии.

## Очистка после подтверждения

Подготовленная редакция ACKИОчистка от 26.10.2026 вызывает собственную очистку в конце общего товарного задания с параметром хранения 0 дней. После настоящего processed строка получает Доставка подтверждена и удаляется следующим циклом (обычно до 10 секунд, до 1000 за цикл). Только подтверждённые Opera/PriceCheker/StructuralUnits; состояние эпохи/счётчика/маршрута и отметки не очищаются. При выключенном задании для первого теста можно сначала увидеть статус, затем вызвать отдельную проверку 22. Четыре старых Opera-пакета Отправлено остаются до своих ACK. Очистка ещё не проверена в платформе пользователем. Удаление строк регистра не является очисткой транспортных очередей Шины.

## Два независимых ACK

После надёжной фиксации обработки каждый бэк отправляет JSON со своим batch_id:

```json
{
  "message_type": "ack",
  "store_id": "3370588b-0742-11e0-b9c1-001a64c3f566",
  "batch_id": "UUID_ПОЛУЧЕННОГО_ИМЕННО_ЭТИМ_БЭКОМ_ПАКЕТА",
  "status": "processed"
}
```

Opera отвечает через свой обратный маршрут в КХ_ОбменШиныОпера.ОбработатьВходящееСообщение. PC отвечает через свой обратный маршрут в КХ_ОбменШиныПрайсЧекеры.ОбработатьВходящееСообщение. Адресат PC ACK — source_node из полученного PC-пакета, в проверенном тестовом маршруте Magazyni_PC. Отправитель ACK здесь Backend_PC. Для Opera сохраняется прежний код отправителя и свой обратный маршрут.

status=error с error сохраняет пакет для повтора. Успешный ACK необратим: поздняя ошибка не снимает подтверждение. Неизвестный или уже очищенный batch_id не меняет другие строки. ACK Opera не подтверждает PC и наоборот. Неподтверждённые записи не удаляются по обычному возрасту.

AMQP settlement и прикладной ACK — разные события. Прикладной batch_id не передаётся в штатную ОбработатьКвитанцию вместо транспортного ID. Возврат native ОтправитьСообщение не доказывает обработки получателем.

## Адресация

Сервис в Асторе ExchOperaPC. Сохранены исходящие каналы Основной_ExchangeOpera_FromOpera и Основной_PriceChekerExc_FromShops. Названия фактических destination/источников/назначений берутся из опубликованной схемы; исторические имена в старых документах не заменяют её настройки.

Для PC у сообщения непустой КодПолучателя. Редакция 26.10.2026 сохраняет отдельный маршрут методом КХ_ОбменШиныОпера.НастроитьМаршрутПрайсЧекеров(КодОтправителя, КодПолучателя) в OperaState: pc_store_id/pc_node_code/pc_backend_node. Подтверждённый прямым тестом маршрут магазина №50 — Magazyni_PC -> Backend_PC; группа получателя BackendPriceChecker. Без явной настройки сохранён прежний резервный параметр/шаблон pricechecker + код СЕ. Смена маршрута блокируется при неподтверждённых PC-пакетах или активной подготовке full, повтор идентичной настройки допустим. Код node_code Opera не меняется. Новые PC-пакеты сохраняют source_node в неизменяемом JSON, повторы используют его. Старые пакеты не перенаправляются автоматически. Для каждого из 500 магазинов задаётся его фактический маршрут. Runtime destinations бэк получает под собственными учётными данными. Секреты не передают в JSON товара.

Для Opera сохранён существующий маршрут общего получателя. Проверка двух магазинов должна подтвердить: центральная Opera принимает оба store_id раздельно, каждый локальный PC получает только свой. Работу маршрутизации для 500 бэков подготовка BSL не доказывает.

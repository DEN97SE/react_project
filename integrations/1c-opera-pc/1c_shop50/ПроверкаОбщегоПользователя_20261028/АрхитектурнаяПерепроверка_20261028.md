Архитектурная перепроверка Opera / PriceChecker — 28.10.2026

Рекомендация: оставить два процесса Шины, одного участника на самостоятельную магазинную базу и автоматизировать их регистрацию. Один магазинный пользователь может обслуживать Opera и PC. Отдельный пользователь на каждый проект не нужен. Если магазинные пользователи уже созданы для ВЕДО на том же сервере авторизации, рассмотреть подключение именно этих существующих пользователей к Opera_PC. Это возможность по исходному коду, а не проверенный результат настройки вашей среды.

**Что подтверждено, а что я исправляю в прежних выводах**

1. Документация разрешает каналы разных процессов в одном сервисе интеграции 1С. У всех каналов этого сервиса будут общие идентификатор и секрет. Два сервиса ExchOperaPC/ExchPriceChecker можно сохранить для раздельного управления и диагностики. Обязательность такого разделения ради ключей я ранее преувеличил. Права обычной магазинной ИС должны разрешать оба процесса.
2. ВЕДО при создании ИС создаёт пользователя, затем выполняет `Пользователи.Подключить(ОписаниеПользователя.Ид)`. Возможность подключить существующего глобального пользователя следует из этого вызова. Но совпадение имени, GUID магазина и глобального ID пользователя не установлено. Нужна явная проверенная связь «магазин → пользователь ВЕДО → тот же глобальный пользователь → локальный пользователь Opera_PC».
3. Исходник ВЕДО не доказывает запрет одного пользователя для нескольких ИС. И наличие такого пользователя не доказывает одну общую очередь. Нативный выбор очереди при нескольких магазинных участниках одного пользователя в нашей версии платформы пока не установлен.
4. Успешный тест двух баз подтвердит наблюдаемое поведение этой версии и топологии. Он не докажет изоляцию полномочий, невозможность прочитать чужую очередь, восстановление после обрыва, отсутствие дублей или готовность 500 баз.
5. Ошибка регистрации HTTP 500 пока не объяснена исходным исключением. Health 200 подтверждает доступность проверочного HTTP-метода. Он не проверяет создание пользователя, членство в группах или доставку товаров.
6. `СгенерироватьДанныеЗапросаТокенаДоступа` выпускает данные нового ключа. Метод ВЕДО GET gettoken не является чтением ранее выданного секрета. Его не следует использовать для безвредной диагностики. Выпуск нового ключа также не доказывает отзыв предыдущего.

**Варианты**

| Вариант | Устройство | Оценка для нашей задачи |
| --- | --- | --- |
| Индивидуальные магазинные ИС, автоматический регистратор | Одна ИС и магазинный пользователь для обоих процессов; один или два сервиса в каждой базе | Основной вариант. Две схемы сохраняются независимо от количества магазинов. |
| Те же ИС, пользователи уже существующего ВЕДО | Подключаем проверенного пользователя магазина к Opera_PC, выдаём права двум процессам | Предпочтительное упрощение, если подтверждены общий сервер/список пользователей и связь с магазином. Не меняем рабочие ключи ВЕДО. |
| Один общий пользователь всех магазинов, нативные подключения | Много ИС под одной общей учётной записью | Пока исследовательский вариант. Общие права не дают магазинной изоляции; несколько ключей одного пользователя сами по себе её не создают. Количество магазинных ИС и индивидуальных очередей такой приём не обязан уменьшить. |
| Центральный шлюз, мало участников Шины | Магазины отправляют данные и получают команды через HTTP API шлюза; шлюз подключён к Шине | Реальный способ сократить число нативных участников. Но нужны постоянные адресные очереди шлюза, авторизация магазинов, повторы, подтверждения и отказоустойчивость. Это отдельная разработка и изменение транспортного контракта. |
| Все данные собирает ЦО | ЦО отправляет товары всех магазинов через одного участника | Только если ЦО действительно имеет полные и своевременные цены, остатки и прочие данные каждого магазина. Наличие признака ЦО у тестовой №50 этого не доказывает. |

Два процесса не превращаются в 1000 схем. В них остаются общие группы источников/получателей. Растут записи участников и ресурсы брокера. Отдельные очереди на участника — нормальная часть этой модели; их реальное количество и ёмкость проверяются на установленной версии и нагрузке.

**Как будет работать выбранный вариант**

Подключение магазина:

1. Центральный исполнитель берёт магазин из доверенного списка развёртывания. Скрипт в базе читает текущую СЕ и внешний `СтроковыйИдентификатор`. Это не обязательно UUID ссылки 1С. Имя базы «410» не доказывает, что скопированная база уже настроена на магазин №410. Тестовая копия не должна подключаться как рабочая база исходного магазина.
2. Регистратор под центральными административными полномочиями находит ИС по нормализованному GUID и проверяет владельца. Неизвестного существующего пользователя нельзя автоматически присваивать магазину по одному отображаемому имени.
3. Если подтверждён магазинный пользователь ВЕДО, подключает его к Opera_PC. Иначе создаёт отдельного обычного пользователя магазина. Проверяет ИС и членство в `Opera / MagazyniOpera` и `PC / MagazinyPriceChecker`. Только наличие строки Exch готовность подключения не доказывает.
4. Рабочая база получает обычный ключ только своего пользователя. Административный ключ регистратора остаётся у центрального исполнителя. Для общего пользователя ВЕДО отдельный API-ключ можно рассмотреть как отдельный управляемый credential; сам по себе он не ограничивает общие права пользователя одним приложением.
5. Ответ можно временно передать через временное хранилище 1С. Затем адрес, clientid/clientsecret записываются в штатные `НастройкиСервисаИнтеграции`. Временное хранилище не заменяет постоянные настройки и не переживает завершение сеанса. PowerShell, файл Windows и хранение секрета в Exch не требуются.
6. Настройка проверяется отдельно от доставки: действующий адрес, разрешённые каналы, затем реальное сообщение и адресный ответ. Установка активности и истечение 20 секунд не доказывают наличие соединения. Изменение двух сервисов последовательное, не атомарное.

Регистрация данных после подключения:

1. Подписка изменения товара/цены/остатков регистрирует необходимость обновления номенклатуры. Она не обязана немедленно собирать весь JSON и ходить в сеть внутри записи бизнес-объекта.
2. Фоновое задание собирает full или delta. Текущий код `КХ_ОбменШиныОпера` имеет отдельную регистрацию пакетов каталога и запись пакета в локальный регистр `ОчередьШины`. Для Opera и PC формируются отдельные проектные пакеты с собственными маршрутами и подтверждениями.
3. Перед отправкой тело, batch_id и адреса пакета уже сохранены. Отправитель передаёт пакет в канал нужного процесса. Наличие API-ключа не заменяет регистрацию бизнес-пакета.
4. Шина маршрутизирует по участникам, группам и транспортному RecipientCode. `store_id` внутри JSON нужен обработчикам, но сам по себе не переключает получателя Шины и не удостоверяет отправителя.
5. Бэкенд сохраняет данные устойчиво и только затем отправляет прикладной ACK по обратному процессу, на сохранённый source_node. При повторах не применяет порцию второй раз. Успех транспорта и статус «Отправлено» не означают применения товара бэкендом.
6. ACK Opera подтверждает пакет Opera; ACK PC — пакет PC. Не подтверждённая вторым проектом порция не исчезает из-за успеха первого. Более старые версии не применяются поверх новых. Полный набор публикуется после получения всех порций сессии, а не только порции is_final.

Пакеты `structural_units` обоих проектов в текущем коде лежат во внешней системе `StructuralUnits`. Поэтому пустой список `PriceCheker` не доказывает отсутствие PC-пакетов справочника: у них нужно смотреть project=pricechecker в `StructuralUnits`. Товарные PC-пакеты ищутся отдельно. Это соответствует ранее присланным скриншотам с тремя PC-порциями справочника и пустой товарной очередью PC.

Справочник магазинов лучше публиковать из одного явно назначенного авторитетного источника ЦО в оба проекта. Подключение 500 магазинов не должно запускать 500 полных выгрузок одного и того же общего справочника.

**Что необходимо доделать в регистрации до массового запуска**

- Получать этап и причину исходного HTTP 500 в административной диагностике. Не заменять исправление сервера бесконечными повторами POST.
- Считать создание глобального пользователя/ключа, запись Exch и создание транспортного участника потенциально разными по границам транзакций. После сбоя сначала сверять фактические объекты. Откат локальной транзакции не был доказательством удаления глобального пользователя и ключа.
- Хранить центральное соответствие магазина и проверенного user ID, состояние регистрации и идентификатор выданного ключа без публикации секретов. Для повторов нужен контроль конкуренции по магазину; «сначала проверить существование, затем создать» не заменяет уникальность/блокировку при параллельных запросах.
- Разделить создание, проверку состояния и восстановление доступа. Потеря ответа после создания — отдельный случай. Временное хранилище его не решает. До применения результата нужен контролируемый порядок повторной выдачи/отзыва с проверкой возможностей установленного API; нельзя молча создавать новые ключи при каждом GET или присваивать неизвестного пользователя.
- Не выключать рабочий ВЕДО и не переписывать его настройки ради повторного использования пользователя. Нельзя утверждать, что общий пользователь обеспечит независимый отзыв прав между приложениями.
- Существующие frozen-пакеты и активные full не переводить на новую личность простой заменой настроек. Старый source_node и его обратный маршрут должны обслуживаться до реальных ACK. Отдельно планировать начало работы нового источника после завершения/контролируемого перехода старого.

**Исправления исследовательского комплекта, выполненные локально**

`ПолныйТест/КХ_ТестОбщегоДоступа.bsl`: при неверном адресе магазин и тестовый бэкенд устанавливают `Отказ=Истина`; прежний код только писал FAIL. `Каналы()` останавливает этот клиент при пустом destination или нескольких разных destination одного имени. Это ограничение данного клиента, не объявление запрета платформы.

`ПолныйТест/InfoBases_Добавка.xbsl`: повторный setup больше не заявляет, что членство существующей ИС уже проверено. `ПолныйТест/Порядок.txt`: уточнены область действия ВыполнитьОбработку, отсутствие доказательства остановки по одному флагу активности и пределы приёмки эксперимента. При первом FAIL тест останавливают и исследуют, не добиваются «успеха» случайными повторами.

Ограничения комплекта сохраняются: текущая СЕ определяется в фоновом сеансе; нет постоянного реестра ожидаемых test_id и учёта дублей. Эти ограничения явно отражены в инструкции. Поэтому комплект остаётся исследовательским, не production-регистратором или приёмкой 500 баз.

Проект в пользовательскую Шину не загружался, настройки баз и рабочая очередь не менялись. Локальный разбор не является компиляцией или сквозным тестом 1С/Шины.

# Эксперимент общего пользователя — №50 и №410

ЭКСПЕРИМЕНТ ОБЩЕГО ПОЛЬЗОВАТЕЛЯ — 28.10.2026, исправленная редакция

Цель: один обычный пользователь и один API-ключ для двух ИС магазинов.
Маршрут: магазин -> тестовый бэкенд -> адресованный магазин.
Тестовый ответчик работает отдельным сервисом в базе №50 с ДРУГИМ обычным ключом.
Новые регистры, PowerShell, файлы Windows и дополнительные базы не нужны.
Товарные сборщики, регистры существующей очереди/full и ключи ExchOperaPC/ExchPriceChecker код не изменяет.
Вызов СервисыИнтеграции.ВыполнитьОбработку() обрабатывает ВСЕ активные сервисы области, а не только тестовый.
Поэтому запускать эксперимент следует в тестовых базах с проверенными состояниями остальных сервисов.
Это комплект для запуска в пользовательской среде, а не подтверждённая поддержка общего пользователя данной версией платформы.
Получатель читает текущую СЕ фонового сеанса; её соответствие физической базе нужно проверить отдельно.
Контекст сеанса, журнал тестов и отсутствие чужих сообщений не заменяют постоянную привязку рабочей базы к магазину.

1. ШИНА — СХЕМА
В Основной создать процесс SharedUserTest, видимость ВПроекте, справочник Exch.
Группы Shops и Backend.
Shops -> Канал1СИсточник FromShops -> Канал1СНазначение ToBackend -> Backend.
Backend -> Канал1СИсточник FromBackend -> Канал1СНазначение ToShops -> Shops.
Полное описание: SharedUserTest.yaml, формат исходного проекта.
Процессы Opera и PC не редактировать.
В параметрах только SharedUserTest задать «Максимальное количество повторных доставок», например 3.
Проверить фактическое поведение отказов платформы и раздел «Недоставленные сообщения»: предел Шины не объявляется пределом всех повторов 1С.

2. ШИНА — HTTP И ПЕРВЫЕ ДВЕ ИС
Добавить InfoBases_Добавка.xbsl в существующий модуль InfoBases, сохранив импорт Основной.
В HTTP InfoBases добавить /shared-test-setup, POST -> ПодготовитьОбщийПилот.
Сервис/шаблон/метод — РазрешеноАдминистраторам. Проверить и опубликовать проект.
Через Инфосистемы создать только две тестовые ИС:
TEST_SHARED_50 / 00000000-0000-4000-8000-000000000050 — включить в Shops процесса SharedUserTest;
TEST_BACKEND   / 00000000-0000-4000-8000-000000000003 — включить в Backend процесса SharedUserTest.
Штатный интерфейс создаст им двух обычных связанных пользователей. Административные права им не выдавать.
Выдать каждой по одному API-ключу.
Ключ TEST_SHARED_50 одинаков в базах 50/410; ключ TEST_BACKEND используется только ответчиком базы 50.
TEST_SHARED_410 вручную не создавать: HTTP-метод создаст эту ИС с пользователем TEST_SHARED_50.

3. 1С — ОБЩИЙ МОДУЛЬ И СЕРВИСЫ
В ОБЕИХ базах общий модуль КХ_ТестОбщегоДоступа: Сервер=Да, ВызовСервера=Да,
ВнешнееСоединение=Да, Глобальный=Нет, Привилегированный=Нет, повторное использование=Не использовать.
Вставить КХ_ТестОбщегоДоступа.bsl.
В ОБЕИХ базах сервис интеграции КХ_ТестОбщегоДоступа с каналами опубликованного SharedUserTest:
Komandor_Opera_PC_Основной_SharedUserTest_FromShops — Отправка;
Komandor_Opera_PC_Основной_SharedUserTest_ToShops — Получение.
Модуль сервиса: МодульТестовогоСервиса.bsl. Локальную процедуру назначить событию ОбработкаПолученияСообщения входящего канала.
В базе №50 второй сервис КХ_ТестОбщегоДоступаБэк:
Komandor_Opera_PC_Основной_SharedUserTest_FromBackend — Отправка;
Komandor_Opera_PC_Основной_SharedUserTest_ToBackend — Получение.
Модуль: МодульТестовогоБэка.bsl; назначить процедуру событию получения.
Если конфигурации баз одинаковы, сервис Бэк может присутствовать и в №410, но настраивается и включается только в №50.
При импорте описания каналов сохранить реальные внешние привязки к опубликованному SharedUserTest.
Обновить конфигурации БД (F7), открыть новые сеансы.

4. ПОДГОТОВКА ВТОРОГО АДРЕСА С ОБЩИМ ПОЛЬЗОВАТЕЛЕМ
В №50 выполнить 01_ПодготовитьИС_ИзКонсоли50.txt с административным ключом, уже работавшим с health.
Сервер создаёт TEST_SHARED_410 / 00000000-0000-4000-8000-000000000410 с пользователем TEST_SHARED_50 и включает в Shops.
HTTP-метод не создаёт пользователей и ключи. Все три тестовых кода отличаются от GUID действующих ИС.
Реальные GUID и номера магазинов модуль читает из СЕ автоматически.
Повторный setup не ротирует ключи и не переназначает пользователей. Чужой занятый код возвращает 409.
Ошибка ДобавитьУчастника второй магазинной ИС возвращает stage и исходное описание; не заменять общего пользователя индивидуальным ради успеха.
Первый ответ без ошибки: HTTP 200, created=true, error=""; повторно created=false, error="".
Повтор проверяет существование и пользователя ИС, но не восстанавливает и не подтверждает членство Shops.
HTTP 200 не означает, что очередь или доставка уже проверены. При частичном сбое изучить stage и состояние процесса до повтора.
Запустить SharedUserTest в приложении.

5. ПОДКЛЮЧЕНИЕ
В обеих базах выполнить 02_Настроить_В_ОбеихБазах.txt с ОДИНАКОВЫМ обычным ключом TEST_SHARED_50.
В №50 дополнительно 02б_НастроитьБэк_Только50.txt с ДРУГИМ обычным ключом TEST_BACKEND.
Адрес берётся из рабочего ExchOperaPC. Если в №410 адрес пуст, передать третьим параметром Настроить
точно тот адрес, который используется рабочим ExchOperaPC №50. Предположительный адрес не подставляется.
Допустимый контекст текущей СЕ — №50 или №410. Название базы «410» само по себе контекст не меняет.
Каналы() выводит реальные channel/destination без ключей и токенов. Нет тестовых каналов или пустой destination — настройка останавливается.
Разные destination одного имени канала также останавливают этот клиент: выбора адреса участника он не реализует.
Одинаковый список каналов не доказывает ни общую очередь, ни разделение магазинов, ни наличие членства второй ИС.
Если имена экспортированных каналов отличаются, загрузить актуальное описание в конфигурацию; имена очередей вручную не конструировать.
Подождать обновления кэша до 20 секунд.

6. ОБЫЧНЫЙ ЦИКЛ
В №50 выполнить 03_ПроверитьОтправку.txt, затем в №410.
В журнале регистрации разрешить события КХ.SharedUserTest.* уровней Информация и Ошибка. Один test_id:
SENT + shared_user_probe в исходной базе — тест передан штатному сервису;
BACKEND в №50 — бэкенд получил его с правильными транспортными адресами;
SENT + shared_user_receipt в №50 — бэкенд передал новый тестовый ответ;
PASS в исходной базе — ответ получен своим магазином, проверены транспортные коды и to_store;
FAIL — сообщение получил другой магазин или транспортные адреса неверны;
ERROR — ошибка формата, контекста или штатного API; причина в той же записи.
При FAIL устанавливается Отказ=Истина: чужое сообщение не считается успешно обработанным этим кодом.
После первого FAIL остановить магазинные тестовые получатели, изучить очередь/недоставленные; не продолжать цикл до «удачного» PASS.
Это не бизнес-ACK, статус товарного пакета не меняется.
SENT/HTTP 200 не доказывают доставку: нужны BACKEND и PASS с тем же test_id и отсутствие FAIL/ERROR в обеих базах.
Сверить все отправленные test_id, число приёмов и остатки очередей: код не ведёт постоянный реестр ожидаемых ответов и дублей.

7. ОТКЛЮЧЁННЫЙ МАГАЗИН
В №50 КХ_ТестОбщегоДоступа.Активность(Ложь); тестовый БЭК оставить включённым. Подождать до 20 секунд.
Затем подтвердить фактическое прекращение тестового подключения. ПолучитьАктивность() и истечение 20 секунд сами по себе этого не доказывают.
Если фактическое состояние подключения недоступно, результат этой части считать неопределённым.
Из №410 ТестID = КХ_ТестОбщегоДоступа.Отправить(50);
Бэкенд №50 получает probe и отправляет receipt для №50. №410 не должна получить этот receipt.
В Шине receipt должен ожидать получения участником TEST_SHARED_50.
В №50 КХ_ТестОбщегоДоступа.Активность(Истина); после обновления/обработки ожидается PASS с тем же test_id.
Повторить зеркально: выключить только магазинный сервис №410, из №50 Отправить(410), проверить ожидание и включить №410.
Отключать именно сервис: закрытие окна клиента серверной ИБ не останавливает фонового получателя.
Повторить несколько сообщений: один случайно удачный приём не доказывает разделение получателей.

8. ЗАВЕРШЕНИЕ
В обеих базах КХ_ТестОбщегоДоступа.Активность(Ложь);
В №50 КХ_ТестОбщегоДоступа.АктивностьБэка(Ложь);
Остановить SharedUserTest.
Успех относится к проверенной версии и этой топологии; рабочие товарные сборщики и массовое подключение этим тестом не проверяются.

Локально выполняется ограниченный разбор BSL/YAML и проверка согласованности адресов/обработчиков.
Компилятора Шины/1С и доступа к program58 в среде подготовки нет. Окончательный результат даёт пользовательский запуск.
Эксперимент не проверяет права изоляции, устойчивость при сбоях, восстановление регистрации или производительность 500 магазинов.
